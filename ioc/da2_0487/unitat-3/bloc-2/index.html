1. Del cas de prova al test automàtic

Al bloc anterior hem decidit què provar. Ara farem que l'ordinador repeteixi aquestes comprovacions per nosaltres. Una prova automàtica executa el codi, compara el resultat amb el que esperàvem i ens avisa si el comportament ha canviat.

Recuperem un exemple semblant al que ja coneixem:

JAVA ClassificadorPunts.java 
package proves;

public class ClassificadorPunts {

    public static String etiqueta(int punts) {
        if (punts < 0 || punts > 100) {
            throw new IllegalArgumentException("Puntuació fora de rang");
        }

        if (punts <= 49) return "Insuficient";
        if (punts <= 69) return "Bé";
        if (punts <= 89) return "Notable";
        return "Excel·lent";
    }
}

Un cas de prova manual podria dir: «entrada 50 → resultat esperat “Bé”». Amb JUnit 5 ho podem expressar directament:

JAVA 
@Test
void cinquantaEsBe() {
    assertEquals("Bé", ClassificadorPunts.etiqueta(50));
}
Informació

Automatitzar no substitueix dissenyar.

Si els casos són dolents, JUnit els executarà molt ràpid... però continuaran sent dolents. Primer es decideixen classes, límits i comportaments; després es converteixen en mètodes @Test.

2. Crear una classe JUnit 5 a Eclipse

JUnit 5 està integrat habitualment en els entorns Java moderns. En Eclipse podeu crear una classe de prova des de File → New → JUnit Test Case. Si aquesta opció no apareix directament, utilitzeu File → New → Other... → Java → JUnit → JUnit Test Case.

Per als exercicis d'aquesta unitat ens interessa un esquema molt simple:

  1. Creeu el projecte Java i la classe que voleu provar.
  2. Creeu una classe JUnit 5 al mateix paquet.
  3. Poseu-li un nom que deixi clar què prova, per exemple TestClassificadorPunts.
  4. Afegiu un mètode precedit per @Test per a cada cas que vulgueu identificar per separat.
  5. Executeu la classe amb Run As → JUnit Test.
JAVA TestClassificadorPunts.java 
package proves;

import static org.junit.jupiter.api.Assertions.*;
import org.junit.jupiter.api.Test;

class TestClassificadorPunts {

    @Test
    void zeroEsInsuficient() {
        assertEquals("Insuficient", ClassificadorPunts.etiqueta(0));
    }

    @Test
    void norantaEsExcellent() {
        assertEquals("Excel·lent", ClassificadorPunts.etiqueta(90));
    }
}

Quan l'executeu, la vista de JUnit mostra quants tests s'han executat i quins han passat o fallat. Un resultat verd no significa que el programa sigui perfecte; significa que tots els casos que hem definit han produït el resultat esperat.

Exercici: Primer test
Creeu ClassificadorPunts i TestClassificadorPunts. Afegiu proves per als valors 49 i 50 i comproveu que totes dues passen.
Bàsic 10 min
Veure pistes
  • Cada valor està a un costat diferent del límit.
  • Utilitzeu assertEquals amb el text esperat.

3. Assertions: comprovar resultats i excepcions

Una assertion expressa una condició que ha de complir-se perquè la prova sigui correcta. JUnit 5 ofereix moltes assertions; per a aquesta unitat en necessitem poques però ben enteses.

AssertionQuan és útil?Exemple
assertEquals(esperat, real)Quan sabem quin valor ha de retornar.assertEquals("Bé", etiqueta(50))
assertTrue(condicio)Quan el que volem verificar és una condició booleana.assertTrue(total > 0)
assertFalse(condicio)Quan una condició ha de ser falsa.assertFalse(llista.isEmpty())
assertThrows(Tipus.class, ...)Quan l'èxit consisteix precisament en llançar l'excepció prevista.Entrada fora del rang permès.

Una excepció també pot ser el resultat correcte

Si l'especificació diu que una entrada invàlida ha de produir una excepció, la prova no ha de «passar per alt» l'error. Ha de comprovar que es produeix exactament l'excepció esperada.

JAVA 
@Test
void menysUnEsInvalid() {
    assertThrows(IllegalArgumentException.class,
        () -> ClassificadorPunts.etiqueta(-1));
}

@Test
void centUEsInvalid() {
    assertThrows(IllegalArgumentException.class,
        () -> ClassificadorPunts.etiqueta(101));
}

La part () -> ... és una expressió lambda que permet a JUnit executar el codi i observar si llança l'excepció. No cal dominar les lambdes per utilitzar aquest patró: llegiu-lo com «executa aquesta crida i comprova que acaba amb aquesta excepció».

També podem comprovar el missatge

JAVA 
@Test
void elMissatgeExplicaElProblema() {
    IllegalArgumentException error =
        assertThrows(IllegalArgumentException.class,
            () -> ClassificadorPunts.etiqueta(120));

    assertEquals("Puntuació fora de rang", error.getMessage());
}
Important

No feu un test que només executi el mètode.

Si no hi ha cap assertion, el test pot passar sense haver comprovat el resultat funcional. Cada mètode de prova ha de deixar clar què espera.

4. Una bateria de proves llegible

Quan hi ha diversos casos, el nom dels tests es converteix en documentació. Compareu test1() amb cinquantaIniciaLaClasseBe(): quan falla el segon, ja sabem quin comportament s'ha trencat.

JAVA TestClassificadorPunts.java 
class TestClassificadorPunts {

    @Test
    void menysUnEsInvalid() {
        assertThrows(IllegalArgumentException.class,
            () -> ClassificadorPunts.etiqueta(-1));
    }

    @Test
    void zeroEsInsuficient() {
        assertEquals("Insuficient", ClassificadorPunts.etiqueta(0));
    }

    @Test
    void quarantaNouEncaraEsInsuficient() {
        assertEquals("Insuficient", ClassificadorPunts.etiqueta(49));
    }

    @Test
    void cinquantaIniciaLaClasseBe() {
        assertEquals("Bé", ClassificadorPunts.etiqueta(50));
    }

    @Test
    void norantaIniciaExcellent() {
        assertEquals("Excel·lent", ClassificadorPunts.etiqueta(90));
    }

    @Test
    void centEsValid() {
        assertEquals("Excel·lent", ClassificadorPunts.etiqueta(100));
    }

    @Test
    void centUEsInvalid() {
        assertThrows(IllegalArgumentException.class,
            () -> ClassificadorPunts.etiqueta(101));
    }
}

Aquesta bateria no pretén substituir el disseny complet del bloc anterior. Serveix per veure com els valors justificats passen del paper al codi. En un exercici de disseny, abans d'escriure JUnit hauríeu de poder indicar quina classe d'equivalència i quin camí cobreix cada cas.

Èxit

Regressió gairebé gratis

Quan aquests tests existeixen, després d'una refacció podem executar-los de nou en segons. Si un canvi intern altera el comportament, un test que abans era verd es tornarà vermell. Aquesta és la xarxa de seguretat que utilitzarem al bloc següent.

5. Depurar: aturar, observar i avançar

Quan un test falla, imprimir variables amb System.out.println pot ajudar, però l'IDE ens ofereix una eina molt més precisa: el depurador. El depurador executa el programa de manera controlada i permet aturar-nos en una línia per observar què està passant.

AccióPer a què serveix?
BreakpointAtura l'execució quan arriba a una línia concreta.
Step IntoEntra dins del mètode que s'està cridant.
Step OverExecuta la línia actual sense entrar dins dels mètodes cridats.
Step ReturnContinua fins que acaba el mètode actual i torna al mètode que l'havia cridat.
ResumeContinua l'execució fins al següent breakpoint o fins al final.
VariablesMostra els valors que tenen les variables en aquell instant.

Exemple: una frontera mal programada

Suposeu que per error hem escrit if (punts < 49) en lloc de <= 49. El test amb 49 fallarà. Poseu un breakpoint a la primera condició, executeu Debug As → JUnit Test i observeu:

  1. punts val 49.
  2. La condició punts < 49 és falsa.
  3. El flux continua fins al següent if.
  4. El mètode retorna «Bé» quan la prova esperava «Insuficient».

Ara ja no tenim una sospita: tenim una causa observada.

Informació

Modificar un valor en temps d'execució

La vista de variables d'Eclipse també pot permetre canviar temporalment el valor d'una variable mentre el programa està aturat. És útil per explorar hipòtesis, però no substitueix modificar el codi i tornar a executar les proves: el canvi només afecta aquella sessió de depuració.

Exercici: Troba el límit trencat
Canvieu temporalment punts <= 69 per punts < 69. Executeu els tests, identifiqueu quin falla i utilitzeu el depurador per explicar el recorregut exacte del valor 69.
Intermedi 15 min
Veure pistes
  • Poseu el breakpoint abans de la condició afectada.
  • Mireu el valor de punts i avanceu amb Step Over.

6. De la fallada a una incidència reproduïble

Detectar un error és només la meitat de la feina. Si el volem corregir o comunicar a una altra persona, hem de poder-lo reproduir. Una bona incidència evita frases com «a vegades no funciona» i conserva les dades necessàries per repetir exactament la fallada.

CampExemple útil
IdentificadorINC-014
Versió / commitCommit on s'ha observat l'error.
EntornJDK, sistema operatiu o configuració rellevant.
Passos1. Executar test X. 2. Introduir 49. 3. Observar resultat.
Esperat«Insuficient».
Obtingut«Bé».
EvidènciaNom del test fallit, captura o traça.
EstatOberta, en curs, resolta, verificada.

Quan corregim la incidència, no eliminem el test que l'ha detectada. El mantenim. Així es converteix en una prova de regressió: si el mateix error reapareix en el futur, la bateria tornarà a avisar.

El circuit complet

  1. Un cas de prova defineix què hauria de passar.
  2. JUnit l'executa automàticament.
  3. Si falla, el depurador permet observar el recorregut real.
  4. Documentem la incidència amb passos reproduïbles.
  5. Corregim el codi.
  6. Executem tota la bateria, no només el test que fallava.
