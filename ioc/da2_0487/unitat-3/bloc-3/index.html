1. Refaccionar no és afegir funcionalitats

Un programa pot donar el resultat correcte i, alhora, tenir un codi difícil de llegir, modificar o provar. La refacció consisteix a millorar l'estructura interna del codi sense canviar-ne el comportament extern.

Imagineu un mètode de 80 línies amb càlculs repetits, nombres sense nom i variables com x, y i z. Podem dividir-lo, reanomenar elements i eliminar duplicacions. Si abans una entrada de 100 produïa 121, després de la refacció ha de continuar produint 121.

CanviÉs refacció?Per què?
Canviar x per preuBase.Sí.Millora el codi sense alterar el resultat.
Extreure un càlcul repetit a un mètode.Sí.Canvia l'estructura, no la funcionalitat.
Afegir un descompte nou per a estudiants.No.Canvia el comportament observable.
Corregir un càlcul que retornava un valor erroni.No estrictament.És una correcció funcional; després podem refaccionar.
Informació

La frase que ho resumeix

Refaccionar és canviar com està escrit el programa mantenint què fa el programa.

Per saber si realment hem mantingut el comportament necessitem una xarxa de seguretat: proves que passin abans del canvi i tornin a passar després.

2. Patrons de refacció més útils

Els materials del mòdul recullen diversos patrons habituals. No cal memoritzar-los com una llista desconnectada: cada patró respon a un problema que podem reconèixer en el codi.

PatróSímptomaTransformació
ReanomenarEl nom no explica què representa.x → preuBase.
MoureUn mètode o classe és al lloc equivocat.Traslladar-lo a la classe o paquet que n'assumeix la responsabilitat.
Extreure variable localUna expressió llarga o repetida costa de llegir.Guardar-ne el resultat amb un nom significatiu.
Extreure constantHi ha un «número màgic» repetit.0.21 → IVA.
Convertir variable local en campUna dada ha de formar part de l'estat de l'objecte.La variable passa a ser atribut.
Extreure mètodeUn fragment fa una tasca concreta o es repeteix.Crear un mètode amb un nom que descrigui la tasca.
Extreure interfícieDiverses classes han de poder usar-se a través del mateix contracte.Crear una interfície comuna i fer que les classes la implementin.
Important

No confongueu «extreure mètode» amb copiar i enganxar.

La idea és substituir un fragment per una crida a un únic mètode reutilitzable. Si dupliqueu el codi en un altre lloc, heu empitjorat el problema.

Exercici: Quin patró aplicaries?
Associeu cada situació amb una refacció: apareix 0.21 en quatre línies; una expressió de cinc operacions es repeteix; una variable es diu p; un bloc de 15 línies calcula sempre el mateix concepte.
Bàsic 8 min
Veure pistes
  • Números repetits → constant.
  • Un nom pobre → reanomenar.
  • Una tasca completa → mètode.

3. Un exemple de refacció pas a pas

Partirem d'un mètode que calcula el total d'una compra. Funciona, però barreja decisions, repeteix expressions i utilitza valors sense nom.

JAVA CalculCompra.java — abans 
public static double calcularTotal(double preu, int unitats) {
    double subtotal = preu * unitats;

    if (unitats >= 10) {
        subtotal = subtotal - subtotal * 0.10;
    }

    double total = subtotal + subtotal * 0.21;
    System.out.println("Total amb IVA: " + (subtotal + subtotal * 0.21));
    return total;
}

El comportament és senzill: si hi ha 10 unitats o més, aplica un 10% de descompte i després un 21% d'IVA. Farem canvis petits.

Pas 1. Extreure constants

JAVA 
private static final int MINIM_DESCOMPTE = 10;
private static final double DESCOMPTE_VOLUM = 0.10;
private static final double IVA = 0.21;

Ara el codi explica què significa cada número i un canvi futur es faria en un únic lloc.

Pas 2. Extreure un mètode

JAVA 
private static double aplicarDescompteVolum(double subtotal, int unitats) {
    if (unitats >= MINIM_DESCOMPTE) {
        return subtotal * (1 - DESCOMPTE_VOLUM);
    }
    return subtotal;
}

private static double aplicarIva(double importNet) {
    return importNet * (1 + IVA);
}

Pas 3. El mètode principal explica la història

JAVA CalculCompra.java — després 
public static double calcularTotal(double preuUnitari, int unitats) {
    double subtotal = preuUnitari * unitats;
    double importAmbDescompte = aplicarDescompteVolum(subtotal, unitats);
    double total = aplicarIva(importAmbDescompte);

    System.out.println("Total amb IVA: " + total);
    return total;
}

Observeu que també hem reanomenat preu a preuUnitari i hem creat la variable importAmbDescompte. Són canvis petits, però junts fan que el mètode es pugui llegir gairebé com una frase.

Èxit

Una bona refacció redueix la càrrega mental.

Quan llegiu aplicarIva(importAmbDescompte) no necessiteu reconstruir mentalment una fórmula. El nom explica la intenció i el detall queda encapsulat al mètode corresponent.

4. La xarxa de seguretat: provar abans i després

La regla més important de la refacció és que el comportament s'ha de conservar. Per això el flux recomanat és molt repetitiu:

  1. Executeu les proves i deixeu-les verdes.
  2. Feu una refacció petita.
  3. Compileu i executeu de nou tota la bateria rellevant.
  4. Si continua verda, conserveu el canvi.
  5. Si falla, investigueu o desfeu aquell pas abans d'acumular-ne més.

Tests mínims per al nostre exemple

JAVA 
@Test
void nouUnitatsNoTenenDescompte() {
    assertEquals(108.90, CalculCompra.calcularTotal(10, 9), 0.001);
}

@Test
void deuUnitatsActivenDescompte() {
    assertEquals(108.90, CalculCompra.calcularTotal(10, 10), 0.001);
}

En nombres decimals és habitual utilitzar una tolerància, aquí 0.001, perquè els nombres de coma flotant no sempre es representen de forma exacta.

Informació

Per què provar també després?

Perquè una refacció aparentment innocent pot introduir un error: canviar l'ordre de les operacions, perdre una condició, usar una variable equivocada o modificar sense voler una referència. Les proves converteixen «crec que no he trencat res» en una comprovació repetible.

5. Analitzar el codi abans que falli

Les proves dinàmiques executen el programa amb dades. L'anàlisi estàtica, en canvi, examina el codi sense necessitat d'executar-lo i busca patrons que poden indicar errors, codi mort, duplicació, vulnerabilitats o problemes de mantenibilitat.

Eclipse ja mostra avisos del compilador i permet configurar-ne la severitat. A més, es poden integrar analitzadors especialitzats.

Eina o fontQuè pot detectar?Com interpretar-la?
Compilador / EclipseTipus incompatibles, variables no usades, codi inassolible i molts avisos configurables.És la primera capa; no ignoreu automàticament els warnings.
PMDCodi duplicat o problemàtic, complexitat, males pràctiques i regles de qualitat.Les regles es poden activar, desactivar o ajustar al projecte.
SpotBugsPatrons de bugs probables en bytecode Java.És el successor modern de FindBugs, eina que apareix als materials antics.

Un analitzador no és un oracle. Pot donar falsos positius o avisos que no tenen la mateixa importància en tots els projectes. Per això el RA4 no demana només executar una eina: també cal entendre les possibilitats de configuració.

Un exemple d'avís que sí ens ajuda

JAVA 
public double calcula(double preu) {
    double resultat = preu * 1.21;
    double temporal = preu * 2;  // es calcula però mai s'utilitza
    return resultat;
}

La variable temporal és codi inútil. El compilador o l'IDE pot avisar-nos abans que ningú hagi de trobar el problema executant proves.

Important

«No hi ha warnings» no significa «el programa és correcte».

L'anàlisi estàtica i les proves troben tipus diferents de problemes. Són complementàries: una inspecciona patrons del codi; l'altra comprova comportaments executant-lo.

6. Assistents d'IA: proposta, criteri i verificació

Un assistent d'IA pot proposar una refacció, però la responsabilitat de decidir si és correcta continua sent del programador. En aquesta unitat no ens interessa «demanar-li que ho faci tot», sinó aprendre a descriure el problema, revisar la proposta i demostrar que conserva el comportament.

Un prompt útil té un criteri verificable

TEXT Exemple de prompt 
Analitza aquest mètode Java i proposa refaccions que millorin
la llegibilitat i redueixin duplicació sense canviar el resultat.

Prioritza:
- extreure constants per als números màgics;
- extreure mètodes només quan representin una tasca clara;
- noms més descriptius.

Explica cada canvi per separat. No afegeixis funcionalitats noves.

Després de rebre una proposta, no l'accepteu en bloc. Classifiqueu cada suggeriment:

PreguntaQuè heu de poder respondre?
Quin problema resol?Duplicació, número màgic, nom pobre, mètode massa llarg...
Canvia el comportament?Si sí, ja no és només una refacció.
És més simple?Una abstracció nova no és millor si només complica un cas trivial.
Ho puc explicar?Heu d'entendre el codi que accepteu.
Les proves continuen passant?És la comprovació final del comportament.

Acceptar o descartar també és part de l'exercici

Suposeu que la IA proposa convertir un càlcul de quatre línies en una jerarquia de sis classes amb un patró de disseny. Pot ser tècnicament possible, però per a un programa petit pot ser més complex que el problema original. Una anàlisi crítica explica per què acceptem unes millores i descartem d'altres.

Exercici: Revisor, no copista
Doneu a un assistent el codi inicial de CalculCompra i demaneu tres possibles refaccions. Per a cadascuna, escriviu: problema que resol, canvi proposat, si l'accepteu i com comprovareu que no altera el resultat.
Intermedi 15 min
Veure pistes
  • No valoreu una proposta per la llargada de la resposta.
  • Executeu els tests després de cada canvi acceptat.

7. Javadoc: del comentari a la documentació HTML

Els comentaris interns expliquen decisions locals del codi. Javadoc té un objectiu diferent: descriure l'API de classes i mètodes de manera estructurada i generar documentació HTML automàticament.

Un comentari Javadoc comença amb /** i acaba amb */. Després de la descripció podem utilitzar etiquetes.

EtiquetaÚs
@authorAutor o autors.
@versionVersió documentada.
@paramDescriu un paràmetre d'entrada.
@returnDescriu el valor retornat.
@throws / @exceptionDescriu una excepció que pot llançar el mètode.
@seeRelaciona la documentació amb una altra classe o mètode.
@deprecatedIndica que un element ha quedat obsolet.

Documentem un mètode petit

JAVA 
/**
 * Calcula el preu total d'una compra.
 *
 * @param preuUnitari preu d'una unitat, en euros
 * @param unitats nombre d'unitats comprades
 * @return import final després del descompte i l'IVA
 * @throws IllegalArgumentException si el preu o les unitats són negatius
 */
public static double calcularTotal(double preuUnitari, int unitats) {
    // ...
}

La documentació no ha de repetir literalment la signatura. Ha d'explicar el contracte: què representa cada dada, què retorna i en quines situacions excepcionals pot fallar.

Generar la documentació

Amb el JDK instal·lat, Eclipse ofereix l'opció Project → Generate Javadoc.... L'assistent pot demanar la ubicació de l'executable javadoc del JDK, les classes que volem documentar i la carpeta de sortida.

També es pot entendre el procés fora de l'IDE amb una ordre com aquesta:

BASH 
javadoc -d docs src/proves/*.java

El resultat és un conjunt de pàgines HTML navegables. Aquesta separació és important: el codi conté la font de la documentació i Javadoc genera la presentació final.

Informació

Documentar no és comentar cada línia.

Un comentari que diu // incrementem i davant de i++ no aporta informació. Javadoc és especialment útil per explicar el contracte públic de classes i mètodes: què fan, què necessiten, què retornen i quines excepcions poden produir.

Puc definir refacció sense confondre-la amb una funcionalitat nova
Reconec reanomenar, extreure variable, constant i mètode
Sé per què cal executar proves abans i després
Entenc què aporta una eina d'anàlisi estàtica
Puc justificar críticament si accepto un suggeriment d'IA
Sé escriure @param, @return i @throws
Puc generar documentació Javadoc des d'Eclipse
Exercici: Refacció completa
Creeu un mètode que calculi el cost d'un enviament amb dos números màgics i una expressió repetida. Escriviu primer tests, apliqueu com a mínim dues refaccions en passos separats, torneu a executar la bateria i documenteu el mètode final amb Javadoc.
Avançat 35-45 min
Veure pistes
  • Deixeu els tests verds abans de tocar l'estructura.
  • Feu una refacció cada vegada.
  • La documentació ha d'explicar el contracte, no narrar cada línia.
