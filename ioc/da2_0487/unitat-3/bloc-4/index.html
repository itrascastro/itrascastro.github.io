1. El model mental de Git

Git no és només una còpia de seguretat. És un sistema que conserva versions identificables del projecte i ens permet treballar en línies de desenvolupament diferents sense haver de duplicar carpetes manualment.

Per entendre les ordres bàsiques, imagineu tres zones:

ZonaQuè conté?Pregunta útil
Working treeEls fitxers tal com els esteu editant ara.Què he modificat?
Staging areaEls canvis que heu seleccionat per al pròxim commit.Què vull incloure a la fotografia següent?
Repositori localL'historial de commits.Quines versions he confirmat?
Informació

Una idea que evita moltes confusions

git add no «puja» res a Internet. git commit tampoc. Totes dues operacions treballen amb el repositori local. La comunicació amb un repositori remot arribarà després amb push i pull.

2. Inicialitzar, afegir, revisar i confirmar

Crearem un projecte mínim anomenat reserves. A la terminal, situeu-vos dins la carpeta del projecte abans d'executar les ordres.

BASH 
mkdir reserves
cd reserves
git init -b main

git init crea el repositori local. L'opció -b main indica el nom de la branca inicial. Si la vostra instal·lació ja utilitza main per defecte, el resultat conceptual és el mateix.

Suposeu que creeu aquest fitxer:

JAVA Reserva.java 
public class Reserva {
    private String client;
    private int durada;

    public Reserva(String client, int durada) {
        this.client = client;
        this.durada = durada;
    }

    public int getDurada() {
        return durada;
    }
}

Ara seguiu el recorregut:

BASH 
git status
git add Reserva.java
git status
git commit -m "versió inicial de Reserva"
git status
git log --oneline
OrdreQuè ens diu o fa?
git statusMostra branca actual, fitxers modificats, no seguits i canvis preparats per confirmar.
git addPassa l'estat actual del fitxer a la zona de preparació.
git commit -m "..."Crea un commit amb els canvis preparats.
git log --onelineMostra l'historial de commits en format compacte.
Important

No memoritzeu una seqüència a cegues.

Executeu git status sovint. És l'ordre que millor explica en quin punt sou i què farà el pas següent.

Exercici: Llegeix l'estat
Creeu un fitxer, executeu git status, feu git add i torneu a executar git status. Expliqueu amb una frase què ha canviat entre les dues sortides.
Bàsic 10 min
Veure pistes
  • El fitxer passa de no preparat a preparat.
  • Encara no hi ha cap nou commit fins que feu git commit.

3. Branques i HEAD

Una branca és un nom que apunta a una línia de commits. Ens permet desenvolupar una modificació sense moure immediatament la branca principal.

HEAD ens indica on estem treballant ara. Habitualment apunta a la branca actual, i aquesta branca apunta al seu commit més recent.

BASH 
git branch branca_tipus   # crea la branca
git branch                 # mostra les branques; encara som a main
git switch branca_tipus    # ens hi situem
git branch                 # ara l'asterisc apareix a branca_tipus

L'asterisc que mostra git branch identifica la branca actual. Hem separat expressament els dos passos perquè quedi clar que crear una branca i situar-s'hi són accions diferents. Quan vulgueu fer-les en una sola ordre, podeu utilitzar git switch -c branca_tipus. En materials antics també podeu trobar git checkout; git switch és l'ordre moderna i més específica per canviar de branca.

A branca_tipus canviem la durada perquè admeti fraccions d'hora:

JAVA 
private double durada;

public double getDurada() {
    return durada;
}

I confirmem el canvi:

BASH 
git add Reserva.java
git commit -m "canvia durada a double"
git log --oneline --decorate

Si ara fem git switch main, el fitxer torna a l'estat que tenia al commit de main: l'atribut torna a ser int. No s'ha perdut el canvi; continua guardat a la branca branca_tipus.

Informació

HEAD no és una branca especial.

És la referència que indica la posició actual. Quan canvieu de branca, HEAD passa a seguir aquella branca. Per això en missatges de conflicte veureu HEAD identificant la versió del costat on esteu situats.

4. Fusionar: quan Git només avança el punter

Tornem a main. Des que vam crear branca_tipus, main no ha rebut cap commit nou. L'historial té aquesta forma conceptual:

TEXT 
A  ← main
   B ← branca_tipus

Si des de main executem:

BASH 
git switch main
git merge branca_tipus

Git no necessita combinar dos historials divergents. Simplement pot moure el punter de main de A fins a B. Això s'anomena fast-forward.

TEXT 
A --- B
      ↑
      main
      branca_tipus

No ha desaparegut cap commit i no s'ha inventat cap versió intermèdia: main s'ha posat al dia fins al commit que ja existia.

Èxit

Quan pot fer-se un fast-forward?

Quan la branca de destí no ha avançat per un altre camí des del punt on es va crear la branca que fusionem. En altres paraules, el commit que tenia la branca de destí és avantpassat directe de l'altre.

5. Conflictes: quan Git necessita una decisió humana

Crearem ara una situació diferent. Tornem al punt inicial i imaginem que una segona branca havia canviat les mateixes línies amb una intenció distinta: reanomenar durada a horesReserva.

JAVA 
private int horesReserva;

public int getHoresReserva() {
    return horesReserva;
}

Si aquesta branca es va crear abans de fusionar branca_tipus, després del primer merge tenim dues idees incompatibles sobre la mateixa línia:

  • main ja conté double durada.
  • branca_nom conté int horesReserva.

En intentar:

BASH 
git switch main
git merge branca_nom

Git pot detectar que no sap triar automàticament. El fitxer mostrarà marques semblants a aquestes:

TEXT 
<<<<<<< HEAD
private double durada;
=======
private int horesReserva;
>>>>>>> branca_nom

Resoldre no vol dir escollir un costat a cegues

En aquest exemple volem conservar totes dues millores: el tipus double i el nom horesReserva. Editaríem manualment el fitxer perquè quedi així:

JAVA 
private double horesReserva;

public double getHoresReserva() {
    return horesReserva;
}

Després eliminem totes les marques del conflicte i confirmem la resolució:

BASH 
git add Reserva.java
git status
git commit -m "resol conflicte de durada"
git log --oneline --graph --decorate --all
Important

No confirmeu un conflicte sense compilar i provar.

Git només sap si el text ha quedat resolt. No sap si heu combinat correctament els significats. Després de resoldre una fusió, compileu i executeu les proves abans de considerar-la bona.

Exercici: Resol els dos objectius
En una branca, un atribut int quantitat passa a double quantitat. En una altra, int quantitat passa a int unitats. Escriviu quin hauria de ser el resultat final si volem conservar les dues intencions.
Intermedi 15 min
Veure pistes
  • No escolliu simplement HEAD o l'altra branca.
  • Pregunteu-vos què volia aconseguir cada canvi.

6. .gitignore: què no ha d'entrar al repositori

No tots els fitxers d'una carpeta formen part del projecte que volem versionar. Compilats, logs, credencials locals o directoris generats poden embrutar l'historial o, en el pitjor cas, exposar informació que no s'hauria d'haver confirmat.

El fitxer .gitignore descriu patrons que Git ha d'ignorar quan encara no estan versionats.

TEXT .gitignore 
# Compilats Java
*.class
bin/
target/

# Fitxers temporals
*.log
*.tmp

# Configuració local amb secrets
.env

Després de crear-lo, utilitzeu git status per comprovar que els fitxers generats ja no apareixen com a no seguits.

Important

.gitignore no esborra l'historial.

Si un fitxer ja ha estat confirmat, afegir-lo després a .gitignore no fa desaparèixer les còpies anteriors. Per això és important decidir què no s'ha de versionar abans del primer commit, especialment quan hi ha credencials o secrets.

7. GitHub i Git des d'Eclipse

Git és el sistema de control de versions. GitHub és un servei que pot allotjar un repositori remot. El repositori local continua existint al vostre ordinador; el remot permet compartir canvis i sincronitzar-los.

Ordres bàsiques amb un remot

BASH 
git remote add origin URL_DEL_REPOSITORI
git push -u origin main

# Més endavant
git pull
git push
OperacióIdea simplificada
pushEnvia commits locals al repositori remot.
pullRecupera canvis del remot i els integra a la branca local corresponent.
fetchActualitza la informació del remot sense integrar automàticament els canvis a la branca de treball.

Eclipse integra Git mitjançant EGit. Les mateixes idees apareixen en opcions com Team, la vista Git Staging, el canvi de branca, Merge, Pull i Push. La interfície pot canviar lleugerament entre versions, però el model mental és el mateix:

  • seleccionem canvis per al staging;
  • creem commits locals;
  • canviem o creem branques;
  • fusionem historials;
  • sincronitzem amb el remot.
Informació

Terminal i IDE no són dos Git diferents.

Si feu git status a la terminal i després obriu Git Staging a Eclipse, totes dues eines estan mirant el mateix repositori. Aprendre les ordres ajuda a entendre què està fent la interfície gràfica.

8. Pràctica guiada de principi a fi

Aquesta pràctica està pensada perquè pugueu afrontar després un exercici semblant amb altres noms, atributs i missatges.

1. Creeu l'estat inicial

  1. Creeu una carpeta control_reserves.
  2. Inicialitzeu Git amb una branca principal.
  3. Afegiu Reserva.java amb int durada.
  4. Consulteu git status, afegiu el fitxer i feu el primer commit.

2. Primera branca: canvi de tipus

  1. Creeu branca_tipus i situeu-vos-hi.
  2. Canvieu int durada a double durada.
  3. Actualitzeu getter, setter o constructor si és necessari.
  4. Feu un commit descriptiu.

3. Segona branca: canvi de nom

La segona branca ha de partir de l'estat inicial, no de la primera modificació. El seu objectiu serà reanomenar durada a horesReserva mantenint encara el tipus original.

4. Fusioneu en l'ordre adequat

  1. Torneu a main i fusioneu branca_tipus.
  2. Expliqueu per què Git pot fer un fast-forward.
  3. Intenteu fusionar branca_nom.
  4. Inspeccioneu les marques del conflicte.
  5. Resoleu-lo amb double horesReserva.
  6. Compileu, proveu i confirmeu la resolució.

5. Expliqueu l'historial

BASH 
git log --oneline --graph --decorate --all

No us limiteu a capturar la pantalla. Heu de poder explicar què representen les línies del gràfic, on es van separar les branques, per què la primera fusió era senzilla i per què la segona necessitava una decisió humana.

Sé diferenciar working tree, staging i commit
Puc explicar què fan git init, add, status i commit
Entenc què representa HEAD
Puc crear i canviar de branca
Sé reconèixer un fast-forward
Entenc per què apareix un conflicte
Sé interpretar les marques <<<<<<<, ======= i >>>>>>>
Puc resoldre un conflicte conservant idees de les dues branques
Sé per a què serveix .gitignore
Distingeixo commit local, push i pull
Exercici: Simulació final de Git
Repetiu tota la pràctica amb una classe Producte: una branca canvia stock d'int a long i una altra reanomena stock a unitatsDisponibles. Feu els commits, les fusions, resoleu el conflicte i expliqueu l'historial amb git log --graph.
Avançat 35-45 min
Veure pistes
  • La segona branca ha de néixer abans d'incorporar el canvi de la primera.
  • Després del conflicte, el resultat ha de conservar el nou tipus i el nou nom.
  • Useu git status en cada etapa.
