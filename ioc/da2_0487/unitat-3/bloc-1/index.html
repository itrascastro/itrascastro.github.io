1. Provar és buscar evidències

Executar un programa una vegada i veure que «sembla funcionar» no és una prova suficient. Una prova ben dissenyada parteix d'una pregunta concreta: quin comportament vull comprovar i quines dades em permeten demostrar-lo?

Imagineu un mètode que classifica una puntuació de 0 a 100. Si només el provem amb 72 i retorna «Notable», encara no sabem què passa amb 0, 49, 50, 89, 90, 100 o amb un valor impossible com 130. El repte no és executar moltes vegades, sinó escollir bé els casos.

ConceptePregunta que respon
VerificacióHem construït correctament el producte segons el disseny i les especificacions tècniques?
ValidacióEl producte final compleix el que necessitava l'usuari o client?
Cas de provaAmb quina entrada, en quines condicions i amb quin resultat esperat comprovarem una funcionalitat?
DepuracióSi una prova falla, on i per què es produeix el comportament incorrecte?
Informació

Idea clau

Una prova no demostra que el programa no tingui cap error. El que fa és aportar evidència sobre comportaments concrets. Com millor escollits estan els casos, més probabilitats tenim de detectar errors importants amb un nombre raonable de proves.

Exercici: Provar o simplement executar?
Un mètode calcula el preu d'una entrada: menors de 12 anys paguen 5 €, de 12 a 64 paguen 10 € i a partir de 65 paguen 6 €. Proposeu quatre valors d'entrada que donin informació realment diferent.
Bàsic 6 min
Veure pistes
  • Busqueu canvis de comportament.
  • Els valors propers als límits solen ser especialment útils.

2. Mapa dels tipus de proves

No totes les proves busquen el mateix. Algunes miren una funció aïllada; d'altres comproven si diversos components encaixen, si el sistema resisteix càrrega o si el client accepta el producte. El resum següent concentra el que necessiteu per orientar-vos.

TipusQuè comprova?Moment o idea principal
UnitàriesClasses, funcions, algorismes i dades aïllades.Durant el desenvolupament; normalment les fa el programador.
FuncionalsQue una funcionalitat implementa el requisit esperat.Es mira el comportament observable, habitualment amb enfocament de capsa negra.
IntegracióRelacions i interfícies entre components.Després de tenir peces provades individualment.
De sistemesAssoliment dels requeriments del sistema desenvolupat.Comproven el sistema com un conjunt durant el desenvolupament.
De càrregaRendiment i integritat amb volum o condicions semblants a les reals.Quan el sistema ja està prou complet per sotmetre'l a càrrega.
D'acceptacióQue el producte complet és acceptable per al client o usuari.Alfa: entorn del desenvolupador. Beta: entorn del client.
De sistemaIntegració del sistema final en l'entorn de l'usuari.Pot incloure rendiment, resistència, robustesa, seguretat, usabilitat i instal·lació.
De regressióQue un canvi no ha trencat comportaments que abans funcionaven.Es repeteixen proves que ja havien passat.
De fumQue les funcions essencials continuen vives.Conjunt ràpid abans de dedicar temps a proves més profundes.

Capsa negra i capsa blanca no són nivells

Són enfocaments. En una prova de capsa negra decidim les entrades a partir de l'especificació i observem les sortides sense necessitar conèixer el codi intern. En una prova de capsa blanca sí que mirem la implementació i intentem recórrer les decisions i els camins interns.

Important

No confongueu «prova de sistema» amb «prova de sistemes».

Els materials del mòdul utilitzen totes dues expressions amb sentits diferents. Per a l'EAC, seguiu la classificació treballada aquí: «de sistemes» comprova l'assoliment dels requeriments durant el desenvolupament; «de sistema» comprova la integració final en l'entorn de l'usuari i pot incloure rendiment, robustesa, seguretat o instal·lació.

Exercici: Quin tipus buscaria?
Associeu cada situació a un tipus de prova: comprovar un mètode calculaIVA(); verificar que API i base de dades es comuniquen; repetir proves després de canviar el càlcul; comprovar el sistema amb 10.000 peticions; deixar que el client el provi al seu entorn.
Bàsic 8 min
Veure pistes
  • Penseu en la mida de la peça que es prova.
  • La regressió apareix després d'un canvi.
  • Beta significa entorn del client.

3. Què ha de contenir un cas de prova

Un cas de prova útil ha de poder-lo executar una altra persona i arribar a la mateixa conclusió. «Provar amb 50» és massa poc. Cal deixar clar què provem, amb quina entrada i què esperem obtenir.

CampExemple
IdentificadorCP-04
Mètode o funcionalitatClassificadorPunts.etiqueta(int)
ObjectiuComprovar el canvi de «Insuficient» a «Bé».
PrecondicionsAplicació iniciada; no cal cap dada prèvia.
Entrada50

Resultat obtingutS'emplena després d'executar.
EstatCorrecte / fallit / pendent.

Informació

Esperat abans d'executar

El resultat esperat s'ha de decidir a partir de l'especificació, no després de veure què retorna el programa. Si primer executeu i després decidiu que «això devia ser el correcte», la prova deixa de ser una comprovació independent.

En projectes reals el format pot ser més complet, però aquesta estructura ja obliga a pensar en les tres peces essencials: entrada, acció i resultat esperat.

4. Classes d'equivalència

Si un mètode tracta milers de valors de la mateixa manera, no té sentit provar-los tots. La tècnica de classes d'equivalència agrupa entrades que, segons l'especificació i el codi que analitzem, haurien de rebre el mateix tractament. Després triem representants de cada classe.

Treballarem amb aquest exemple:

JAVA ClassificadorPunts.java 
public static String etiqueta(int punts) {
    if (punts < 0 || punts > 100) {
        throw new IllegalArgumentException("Puntuació fora de rang");
    }

    if (punts <= 49) return "Insuficient";
    if (punts <= 69) return "Bé";
    if (punts <= 89) return "Notable";
    return "Excel·lent";
}

Primer identifiquem les condicions d'entrada i de sortida. L'entrada vàlida va de 0 a 100. Fora d'aquest interval s'ha de produir una excepció. Dins l'interval hi ha quatre tractaments diferents.

ClasseRangTipusTractament
C1punts < 0InvàlidaExcepció.
C20..49Vàlida«Insuficient».
C350..69Vàlida«Bé».
C470..89Vàlida«Notable».
C590..100Vàlida«Excel·lent».
C6punts > 100InvàlidaExcepció.
Èxit

Regla pràctica

Si dos valors provoquen exactament el mateix recorregut i el mateix tipus de resultat, probablement poden pertànyer a la mateixa classe. Si en algun punt canvia la resposta, apareix una nova classe.

5. Valors límit i casos representatius

Els errors apareixen sovint a les fronteres: usar < en lloc de <=, començar un interval un valor massa tard o acceptar un valor que ja hauria de ser invàlid. Per això, després de definir les classes, busquem primer valor, últim valor i un valor intermedi quan tingui sentit.

ClasseValors especialment útilsPer què?
C1: < 0-1 i, per exemple, -50-1 toca el límit; l'altre representa l'interior d'un interval sense límit inferior.
C2: 0..490, 25, 49Primer, intermedi i últim.
C3: 50..6950, 60, 69Comproven els dos canvis de frontera.
C4: 70..8970, 80, 89Mateixa idea.
C5: 90..10090, 95, 100Inclou el màxim vàlid.
C6: > 100101 i, per exemple, 150101 és el primer valor invàlid superior.

No sempre necessitareu executar tots aquests valors. El disseny de proves busca un conjunt petit però justificat que representi totes les classes, cobreixi els límits importants i, si fem capsa blanca, recorri tots els camins independents que ens interessen.

Exercici: De rangs a casos
Un sensor accepta humitat de 0 a 100. De 0 a 29 retorna «seca», de 30 a 69 «correcta» i de 70 a 100 «alta»; fora de rang genera una excepció. Definiu classes d'equivalència i proposeu valors límit i intermedis.
Intermedi 12 min
Veure pistes
  • Comenceu per les condicions d'entrada i sortida.
  • Hi ha dos rangs invàlids i tres tractaments vàlids.

6. Capsa blanca, flux de control i McCabe

Les classes d'equivalència ens ajuden a escollir dades segons el comportament. Amb capsa blanca fem un pas més: mirem l'estructura interna i comprovem si els casos seleccionats recorren les decisions del codi.

Complexitat ciclomàtica

En el material del mòdul s'utilitza la fórmula de McCabe:

TEXT 
CC = nombre de branques - nombre de nodes + 2

En un graf connectat, la complexitat ciclomàtica indica quants camins independents formen el conjunt bàsic. En codi estructurat senzill també podem fer servir com a comprovació ràpida la idea «nombre de decisions + 1», sempre que tractem cada decisió de la mateixa manera que al graf.

Un camí independent és un recorregut que incorpora almenys una branca que encara no havia aparegut als camins seleccionats. L'objectiu no és memoritzar una seqüència concreta de números: és poder demostrar que el joc de proves fa passar el programa per totes les alternatives rellevants.

El procediment que heu de saber repetir

  1. Llegiu l'especificació i identifiqueu entrades i sortides.
  2. Definiu les classes d'equivalència.
  3. Trieu representants, valors límit i intermedis.
  4. Dibuixeu el flux de control del mètode.
  5. Compteu nodes i branques i calculeu la complexitat ciclomàtica.
  6. Escriviu un conjunt de camins independents.
  7. Marqueu quin cas de prova cobreix cada camí.
  8. Si queda un camí sense cobrir, afegiu un cas.
Important

No forceu la fórmula sobre un dibuix ambigu.

Primer decidiu com representeu cada decisió i dibuixeu totes les branques. Després compteu. Si canvieu la manera de representar una condició composta a mig càlcul, nodes, branques i resultat deixaran de ser coherents.

Exercici: Mini simulació de disseny
Dissenyeu les proves d'un mètode que rep el percentatge d'ocupació d'un aparcament (0..100) i retorna «lliure» fins a 49, «alt» fins a 89 i «complet» de 90 a 100; fora de rang genera excepció. Incloeu classes, límits, diagrama, complexitat i cobertura de camins.
Avançat 25-35 min
Veure pistes
  • No programeu JUnit encara: primer dissenyeu.
  • Els dos intervals invàlids també compten.
  • Un bon disseny explica per què cada dada està al conjunt.
