1. Programació estructurada

La programació estructurada parteix d'una idea potent: podem construir programes complexos combinant tres estructures de control bàsiques i dividint els problemes grans en problemes més petits.

EstructuraPreguntaJava típic
SeqüènciaQuè passa primer i què passa després?Instruccions una darrere l'altra.
SeleccióQuin camí segueixo segons una condició?if / else, switch.
IteracióQuè he de repetir?for, while.
JAVA 
double preu = 100.0;                 // seqüència

if (preu >= 100) {                    // selecció
    preu = preu * 0.90;
}

for (int i = 0; i < 3; i++) {         // iteració
    System.out.println(preu);
}

Disseny descendent: divideix i venceràs

En lloc d'escriure un mètode de cent línies, podem separar responsabilitats: llegirDades(), validarDades(), calcularPreu() i mostrarResultat(). Cada part resol un problema més petit i es pot provar de forma més clara.

Informació

Què no forma part del teorema de l'estructura?

Els salts incondicionals com GOTO no són una quarta estructura bàsica. El model estructurat es basa en seqüència, selecció i iteració.

Exercici: Tres peces
Escriviu pseudocodi per llegir cinc notes, comptar quantes estan aprovades i mostrar «majoria aprovada» si el recompte és 3 o més. Marqueu on hi ha seqüència, selecció i iteració.
Bàsic 8 min
Veure pistes
  • Necessiteu un comptador.
  • La repetició es fa cinc vegades.
  • La decisió final només té dos camins.

2. POO: cinc idees clau

La programació orientada a objectes modela el programa com un conjunt d'objectes que combinen dades i comportament. El material agrupa els principis centrals en cinc idees.

ConceptePregunta útilExemple
AbstraccióQuines característiques són essencials?De Client ens interessen nom i correu, no el color dels ulls.
EncapsulacióQuè exposo i què amago?Atributs private, mètodes públics.
ModularitatQuina responsabilitat té cada peça?Classes separades que es poden modificar amb poc impacte.
JerarquiaQuin tipus és una especialització d'un altre?Vehicle → Bicicleta.
PolimorfismePot la mateixa operació tenir comportaments diferents?calcularPreu() implementat de manera diferent segons el tipus.
JAVA Compte.java 
public class Compte {
    private double saldo;          // encapsulat

    public void ingressar(double import) {
        if (import > 0) {
            saldo += import;
        }
    }

    public double getSaldo() {
        return saldo;
    }
}

Aquí Compte és una abstracció, saldo queda encapsulat i la classe forma un mòdul amb una responsabilitat clara.

Exercici: Quin principi estàs aplicant?
Associeu cada situació a un concepte: fer saldo private; separar Factura i Client; crear Cotxe com a subclasse de Vehicle; definir només les dades rellevants d'un Producte.
Bàsic 7 min
Veure pistes
  • Penseu en ocultar, separar, especialitzar i simplificar.

3. Herència, sobrecàrrega i sobreescriptura

Aquests tres termes solen aparèixer junts i és fàcil barrejar-los. La clau és mirar què canvia.

Herència

Una classe filla rep atributs i mètodes accessibles de la classe pare i pot afegir o especialitzar comportament.

JAVA 
class Vehicle {
    public void arrencar() {
        System.out.println("Vehicle en marxa");
    }
}

class BicicletaElectrica extends Vehicle {
    // hereta arrencar()
}

Sobrecàrrega: mateix nom, paràmetres diferents

JAVA 
int sumar(int a, int b) {
    return a + b;
}

double sumar(double a, double b) {
    return a + b;
}

Sobreescriptura: mateixa signatura heretada, nova implementació

JAVA 
class Vehicle {
    public void descriure() {
        System.out.println("Vehicle");
    }
}

class Bicicleta extends Vehicle {
    @Override
    public void descriure() {
        System.out.println("Bicicleta");
    }
}
ConcepteMateix nom?Mateixos paràmetres?Necessita herència?
HerènciaNo és la pregunta principal.No és la pregunta principal.Sí, relaciona classe pare i filla.
SobrecàrregaSí.No.No necessàriament.
SobreescripturaSí.Sí, mateixa signatura.Sí, redefineix un mètode heretat.
Exercici: Overload o override?
Digueu si hi ha sobrecàrrega o sobreescriptura en dos casos: (1) imprimir(String) i imprimir(int); (2) una subclasse torna a definir mostrar() amb la mateixa signatura que la classe pare.
Bàsic 8 min
Veure pistes
  • Paràmetres diferents: penseu en overload.
  • Mètode heretat amb la mateixa signatura: penseu en override.

4. Paradigmes funcional i lògic

No tots els programes s'organitzen al voltant de sentències imperatives o objectes. El material presenta també els paradigmes funcional i lògic.

Funcional: transformar valors

La idea és veure el càlcul com una composició de funcions: la sortida d'una operació es converteix en l'entrada de la següent. Lisp és un dels exemples clàssics que apareixen al material.

JAVA 
// Mateixa idea expressada en Java amb funcions simples
static int doble(int x) {
    return x * 2;
}

static int sumaUn(int x) {
    return x + 1;
}

// sumaUn(doble(3)) -> 7

Lògic: fets + regles + consulta

En el paradigma lògic descrivim fets i regles; un motor d'inferència intenta deduir conclusions. Prolog és l'exemple típic del material.

Fet: la temperatura és 39 °C.
Regla: si la temperatura és superior a 37 °C, hi ha febre.
Consulta: hi ha febre?

Aquesta és la pista més directa per reconèixer el paradigma lògic: aplicar regles lògiques per inferir conclusions a partir de dades.

Exercici: Reconèixer el paradigma
Expliqueu quin paradigma encaixa millor amb: (a) una cadena de funcions que transforma una llista; (b) una base de fets i regles que decideix si una incidència és prioritària.
Bàsic 6 min
Veure pistes
  • Transformació/composició apunta a funcional.
  • Fets, regles i inferència apunten a lògic.

5. Fases de desenvolupament amb Mètrica 3

Programar és només una part del desenvolupament d'un sistema. El material utilitza Mètrica 3 per presentar cinc fases seqüencials.

FasePregunta principalResultat que heu de retenir
1. Estudi de viabilitatVal la pena continuar?Analitza necessitats i viabilitat econòmica, tècnica, legal i operativa.
2. Anàlisi del sistema d'informacióQuè ha de fer exactament?Especificació detallada, catàleg de requisits i models.
3. Disseny del sistema d'informacióCom estarà construït?Arquitectura, entorn tecnològic, components, proves i implantació.
4. ConstruccióCom el convertim en programari provat?Codi, components, proves unitàries i d'integració, manuals i procediments.
5. Implantació i acceptacióCom arriba a producció i s'accepta?Implantació, proves d'acceptació, pas a producció i preparació del manteniment.
Informació

Truc per no confondre anàlisi i disseny

Anàlisi = què necessita el sistema. Disseny = com el construirem. Si la frase parla d'«especificació detallada del sistema» i catàleg de requisits, el material la situa a l'anàlisi.

Exercici: Posa cada decisió a la seva fase
Classifiqueu cinc accions: decidir si el projecte és viable; recollir requisits; definir l'arquitectura; programar i fer proves unitàries; fer proves d'acceptació amb l'usuari.
Intermedi 10 min
Veure pistes
  • Seguiu l'ordre de les cinc preguntes de la figura.
  • No confongueu requisits amb arquitectura.
