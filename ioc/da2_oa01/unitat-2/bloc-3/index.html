1.2. Marc conceptual

1.2.1. Què és la vinculació bidireccional

La vinculació bidireccional és un mecanisme que sincronitza automàticament les dades entre el model (component) i la vista (plantilla) en ambdós sentits: quan l'usuari modifica un control HTML, el valor s'actualitza al component; quan el component modifica el valor, el control HTML es reactualitza. Angular implementa aquesta funcionalitat amb la directiva [(ngModel)], que combina property binding [ngModel] (component → vista) i event binding (ngModelChange) (vista → component) en una sola expressió.

1.2.2. Problema sense vinculació bidireccional

Imagineu que voleu crear un formulari per afegir nous elements al catàleg. L'usuari escriu al camp "Títol" i voleu mostrar una previsualització en temps real a sota del formulari. Sense vinculació bidireccional, hauríeu de gestionar manualment la sincronització en ambdós sentits.

Situació abans (sense [(ngModel)]):

TYPESCRIPT 
// Component amb sincronització manual - NO RECOMANAT
export class App {
  titolElement = '';
  categoriaElement = 'Components UI';
  preuElement = 0;
  // Mètode per actualitzar des de la vista cap al component
  actualitzarTitol(event: Event): void {
    const input = event.target as HTMLInputElement;
    this.titolElement = input.value;
  }
  actualitzarCategoria(event: Event): void {
    const select = event.target as HTMLSelectElement;
    this.categoriaElement = select.value;
  }
  actualitzarPreu(event: Event): void {
    const input = event.target as HTMLInputElement;
    this.preuElement = Number(input.value);
  }
  // I així per cada camp... 😱
}
HTML 
<!-- Plantilla amb vinculació manual verbose -->
<form>
<label>
Títol
<input type="text" [value]="titolElement" (input)="actualitzarTitol($event)" />
</label>
<label>
Categoria
<select [value]="categoriaElement" (change)="actualitzarCategoria($event)" >
<option value="Components UI">Components UI</option>
<option value="Paletes">Paletes</option>
</select>
</label>
<label>
Preu
<input type="number" [value]="preuElement" (input)="actualitzarPreu($event)" />
</label>
</form>
<!-- Previsualització -->
<div class="preview">
<p>Títol: {{ titolElement }}</p>
<p>Categoria: {{ categoriaElement }}</p>
<p>Preu: {{ preuElement }}</p>
</div>

Problemes que genera aquesta aproximació:

1. Codi verbose i repetitiu
Per cada camp del formulari heu de crear un mètode que extregui el valor de l'esdeveniment, el converteixi si cal (string a number) i l'assigni a la propietat corresponent. Si teniu 10 camps, necessiteu 10 mètodes.

2. Gestió manual de tipus
En una gestió manual, la propietat value dels controls de text és sempre una cadena i cal convertir-la a number o altres tipus; els checkboxes exposen l'estat a checked. És fàcil oblidar alguna conversió. (Angular Forms fa aquestes conversions per vosaltres mitjançant els seus value accessors, com veureu tot seguit.)

3. Sincronització unidireccional complexa
Si necessiteu modificar el valor des del component (per exemple, reiniciar el formulari o carregar dades existents), heu de gestionar manualment l'actualització del DOM amb [value].

4. Dificultat per mantenir
Afegir un nou camp requereix: (1) crear la propietat, (2) crear el mètode d'actualització, (3) vincular [value] i (input) correctament. És fàcil oblidar algun pas.

5. No integrat amb formularis Angular
Aquesta aproximació manual no aprofita les capacitats de validació, estat dels controls (pristine, dirty, touched) ni altres funcionalitats del sistema de formularis d'Angular.

1.2.3. Solució amb vinculació bidireccional [(ngModel)]

Angular proporciona FormsModule amb la directiva [(ngModel)] que simplifica dràsticament la gestió de formularis:

TYPESCRIPT 
// Component net amb FormsModule - RECOMANAT
import { Component } from '@angular/core';
import { CommonModule } from '@angular/common';
import { FormsModule } from '@angular/forms';
@Component({
  selector: 'app-root',
  imports: [CommonModule, FormsModule],
  templateUrl: './app.component.html'
})
export class App {
  // Només propietats, sense mètodes de sincronització
  formulariElement = {
    titol: '',
    categoria: 'Components UI',
    preu: 0
  };
}
HTML 
<!-- Plantilla concisa amb [(ngModel)] -->
<form>
<label>
Títol
<input type="text" name="titol" [(ngModel)]="formulariElement.titol" />
</label>
<label>
Categoria
<select name="categoria" [(ngModel)]="formulariElement.categoria">
<option value="Components UI">Components UI</option>
<option value="Paletes">Paletes</option>
</select>
</label>
<label>
Preu
<input type="number" name="preu" [(ngModel)]="formulariElement.preu" />
</label>
</form>
<!-- Previsualització automàtica -->
<div class="preview">
<p>Títol: {{ formulariElement.titol }}</p>
<p>Categoria: {{ formulariElement.categoria }}</p>
<p>Preu: {{ formulariElement.preu }}</p>
</div>

Avantatges d'aquesta aproximació:

  • Codi dràsticament més curt: 15 línies de plantilla en lloc de 30+, sense cap mètode de sincronització al component.
  • Sincronització automàtica bidireccional: qualsevol canvi a l'input s'actualitza al model, i viceversa, sense codi addicional.
  • Conversió de tipus automàtica: type="number" converteix automàticament a number, type="checkbox" a boolean, etc.
  • Previsualització en temps real sense esforç: la interpolació {{ formulariElement.titol }} es reactualitza automàticament.
  • Integrat amb Angular Forms: accés a estat dels controls, validació, i altres funcionalitats avançades.
  • Mantenible i escalable: afegir un nou camp només requereix afegir-lo al model i a la plantilla amb [(ngModel)].

1.2.6. Quan usar formularis template-driven (amb [(ngModel)])

Els formularis template-driven ([(ngModel)]) són una bona opció quan:

  • El formulari és simple amb pocs camps (orientativament, menys d'una desena): afegir element, cerca bàsica, formulari de contacte.
  • Les validacions són bàsiques: required, minlength, maxlength, pattern, email (validacions HTML estàndard).
  • No necessiteu lògica complexa de validació creuada (camps que depenen uns dels altres).
  • Voleu prototipatge ràpid: template-driven és més ràpid per començar.
  • El formulari no té lògica dinàmica complexa: no afegiu/eliminau camps programàticament.

NO useu template-driven quan:

  • El formulari és molt complex (15+ camps amb múltiples seccions): millor usar reactive forms.
  • Necessiteu validacions complexes personalitzades que depenen de múltiples camps.
  • El formulari canvia dinàmicament: afegiu/eliminau camps segons condicions.
  • Voleu testejar el formulari aïllat del component: reactive forms són més testables.
  • Necessiteu control programàtic total: subscriure's a canvis, desactivar camps dinàmicament, etc.

1.2.7. Integració amb el projecte Catàleg d'elements

Al projecte del catàleg, utilitzareu formularis template-driven per:

  • Formulari d'alta d'elements: afegir nous elements amb títol, categoria, preu, descripció.
  • Cerca i filtres: formulari per cercar elements per categoria, rang de preu, disponibilitat.
  • Configuració de previsualització: checkbox per mostrar/amagar previsualització en temps real.

Aquesta aproximació us permet crear formularis funcionals ràpidament sense codi complex, mantenint la separació entre dades (component) i vista (plantilla), i preparant el terreny per afegir validacions a la següent lectura.

1.3. Model mental

Penseu en la vinculació bidireccional [(ngModel)] com un cable bidireccional que connecta el control HTML (input, select, etc.) amb la propietat del component:

  • Direcció 1 (Component → Vista): Quan el component assigna un valor (p.ex. formulariElement.titol = 'Nou títol'), el control HTML es reactualitza automàticament mostrant "Nou títol".
  • Direcció 2 (Vista → Component): Quan l'usuari escriu al control HTML, el valor es sincronitza automàticament a la propietat del component sense cap mètode manual.

1.3.1. Expansió de [(ngModel)]

La sintaxi [(ngModel)] és sugar syntax (sintaxi abreujada) per:

HTML 
<!-- Forma abreujada (recomanada) -->
<input [(ngModel)]="nom" />
<!-- Forma expandida (equivalent) -->
<input [ngModel]="nom" (ngModelChange)="nom = $event" />

Angular combina property binding [ngModel] (component → vista) i event binding (ngModelChange) (vista → component) en una sola directiva.

1.3.2. Component contenidor

El component actua com a font única de veritat per les dades del formulari. Conserva l'objecte formulariElement amb tots els camps, gestiona l'historial d'entrades (entradesFormulari[]), i coordina l'enviament del formulari sense refrescar la pàgina.

1.3.3. Flux complet del formulari

  1. Inicialització: El component crea formulariElement amb valors per defecte.
  2. Entrada d'usuari: L'usuari modifica controls → [(ngModel)] sincronitza automàticament → propietats actualitzades.
  3. Previsualització: La interpolació {{ formulariElement.titol }} es reactualitza automàticament.
  4. Enviament: L'usuari prem botó → (ngSubmit) intercepta → component copia dades → afegeix a historial.
  5. Reinici: Component assigna valors per defecte a formulariElement → controls HTML es reinicien automàticament.

1.3.4. FormsModule i name obligatori

Angular necessita FormsModule per proporcionar les directives ngModel i ngForm. L'atribut name és obligatori perquè Angular identifica cada control dins del formulari. Sense name, Angular no pot registrar el control i llançarà un error que ho diu literalment: If ngModel is used within a form tag, either the name attribute must be set or the form control must be defined as 'standalone' in ngModelOptions.

1.3.5. Diferència template-driven vs reactive

  • Template-driven ([(ngModel)]): La configuració del formulari es fa majoritàriament a la plantilla (HTML). Simple i ràpid per formularis bàsics.
  • Reactive (FormBuilder): La configuració del formulari es fa al component (TypeScript). Més control i testejable per formularis complexos.

En aquesta lectura utilitzeu template-driven perquè és més intuïtiu per començar, i a lectures posteriors veureu reactive forms quan necessiteu més control.

Èxit
Clau: [(ngModel)] actua com un cable bidireccional automàtic entre component i vista, eliminant la necessitat de codi de sincronització manual.
1.4. Vinculació unidireccional vs bidireccional: diferències

1.4.1. Objectiu

Comprendre les diferències fonamentals entre vinculació unidireccional (property binding i event binding separats) i vinculació bidireccional ([(ngModel)] combinat).

1.4.2. Contingut

Angular ofereix tres tipus principals de vinculació de dades:

1.4.3. Interpolació {{ }}

La més bàsica: mostra valors del component a la plantilla (només component → vista).

TYPESCRIPT 
// Component
nom = 'Angular';
HTML 
<!-- Plantilla -->
<h1>{{ nom }}</h1>
<!-- Mostra: Angular -->

Direcció: Component → Vista (unidireccional)
Cas d'ús: Mostrar dades sense interacció.

1.4.4. Property binding [propietat]

Assigna valors del component a propietats HTML (només component → vista).

TYPESCRIPT 
// Component
urlImatge = 'logo.png';
estatDisponible = false;
HTML 
<!-- Plantilla -->
<img [src]="urlImatge" />
<button [disabled]="!estatDisponible">Comprar</button>

Direcció: Component → Vista (unidireccional)
Cas d'ús: Controlar propietats HTML dinàmicament.

1.4.5. Event binding (event)

Escolta esdeveniments HTML i executa mètodes del component (només vista → component).

TYPESCRIPT 
// Component
incrementar(): void {
  this.comptador++;
}
HTML 
<!-- Plantilla -->
<button (click)="incrementar()">+1</button>

Direcció: Vista → Component (unidireccional)
Cas d'ús: Respondre a interaccions d'usuari.

1.4.6. Vinculació bidireccional [(ngModel)]

Combina property binding i event binding en una sola directiva (component ↔ vista).

TYPESCRIPT 
// Component
nom = 'Angular';
HTML 
<!-- Plantilla -->
<input [(ngModel)]="nom" name="nom" />
<p>Nom: {{ nom }}</p>

Direcció: Component ↔ Vista (bidireccional)
Cas d'ús: Formularis on usuari modifica dades que també es mostren.

Quan l'usuari escriu "Vue" a l'input:

  1. Event binding detecta el canvi → actualitza nom = 'Vue'
  2. Property binding detecta el canvi de nom → actualitza l'input i el paràgraf
  3. Resultat: tot sincronitzat automàticament

1.4.7. Comparativa visual amb exemple pràctic

Escenari: Camp de cerca amb previsualització.

Amb vinculació unidireccional (verbose):

TYPESCRIPT 
// Component
cerca = '';
actualitzarCerca(event: Event): void {
  this.cerca = (event.target as HTMLInputElement).value;
}
HTML 
<!-- Plantilla -->
<input [value]="cerca" (input)="actualitzarCerca($event)" />
<p>Cercant: {{ cerca }}</p>

Amb vinculació bidireccional (concís):

TYPESCRIPT 
// Component
cerca = '';
// No cal mètode!
HTML 
<!-- Plantilla -->
<input [(ngModel)]="cerca" name="cerca" />
<p>Cercant: {{ cerca }}</p>

Diferències clau:

  • Codi: -5 línies (sense mètode ni event handling)
  • Sincronització: Automàtica en ambdós sentits
  • Mantenibilitat: Més fàcil afegir camps (només model + plantilla)
Èxit
Clau: La vinculació bidireccional [(ngModel)] combina [property] i (event) en una sola directiva, simplificant formularis amb sincronització automàtica en ambdós sentits.

1.4.8. Resultat esperat

Enteneu les diferències entre interpolació, property binding, event binding i vinculació bidireccional, i sabeu quan utilitzar cadascuna.

1.5. Sintaxi de vinculació bidireccional: combinació de [ ] i ( )

1.5.1. Objectiu

Dominar la sintaxi de [(ngModel)], entendre com funciona internament i aprendre a expandir-la quan calgui personalitzar el comportament.

1.5.2. Contingut

La sintaxi [(propietat)] s'anomena banana in a box (plàtan en una caixa) per la seva forma visual: [()]. És syntactic sugar (sucre sintàctic) que Angular expandeix automàticament.

1.5.3. Forma abreujada (recomanada)

HTML 
<input type="text" name="nom" [(ngModel)]="formulariElement.nom" />

Angular interpreta això com: "sincronitza bidirecionalment formulariElement.nom amb aquest input".

1.5.4. Forma expandida (equivalent)

HTML 
<input type="text" name="nom" [ngModel]="formulariElement.nom" (ngModelChange)="formulariElement.nom = $event" />

Desglossament:

  1. [ngModel]="formulariElement.nom": Property binding. El valor del component s'assigna a l'input (component → vista).
  2. (ngModelChange)="formulariElement.nom = $event": Event binding. Quan l'usuari escriu, l'esdeveniment emés actualitza el component (vista → component).
  3. $event: Conté el nou valor escrit per l'usuari.

1.5.5. Quan utilitzar la forma expandida

Normalment useu la forma abreujada [(ngModel)], però la forma expandida és útil quan necessiteu:

Cas 1: Executar lògica addicional quan canvia el valor

HTML 
<input type="text" name="cerca" [ngModel]="cerca" (ngModelChange)="actualitzarCerca($event)" />
TYPESCRIPT 
actualitzarCerca(nouValor: string): void {
  this.cerca = nouValor;
  console.log('Cercant:', nouValor);
  // Lògica addicional: cridar API de cerca, actualitzar estadístiques, etc.
}

Cas 2: Transformar el valor abans d'assignar-lo

HTML 
<input type="text" name="nom" [ngModel]="nom" (ngModelChange)="nom = $event.toUpperCase()" />

Això converteix automàticament l'entrada a majúscules mentre l'usuari escriu.

Cas 3: Validació o restricció personalitzada

HTML 
<input type="number" name="preu" [ngModel]="preu" (ngModelChange)="actualitzarPreu($event)" />
TYPESCRIPT 
actualitzarPreu(nouPreu: number): void {
  // Restringir a valors positius
  this.preu = nouPreu < 0 ? 0 : nouPreu;
}

1.5.6. Errors comuns de sintaxi

HTML 
<!-- ERROR: Parèntesis invertits -->
<input ([ngModel])="nom" />
<!-- ERROR: Només claudàtors (property binding, no bidireccional) -->
<input [ngModel]="nom" />
<!-- ERROR: Només parèntesis (no existeix) -->
<input (ngModel)="nom" />
<!-- CORRECTE: Claudàtors dins parèntesis -->
<input [(ngModel)]="nom" name="nom" />
Èxit
Clau: La sintaxi [(ngModel)] combina [ngModel] i (ngModelChange) en banana in a box, i es pot expandir quan necessiteu lògica personalitzada.

1.5.7. Resultat esperat

Domineu la sintaxi de vinculació bidireccional, enteneu com funciona internament, i sabeu quan utilitzar la forma expandida.

1.6. Importar mòdul de formularis: configuració necessària

1.6.1. Objectiu

Aprendre a configurar FormsModule correctament en components standalone i entendre els requisits per utilitzar [(ngModel)].

1.6.2. Contingut

Per utilitzar vinculació bidireccional amb [(ngModel)], cal importar FormsModule d'Angular. Aquest mòdul proporciona les directives ngModel, ngForm i funcionalitats relacionades amb formularis template-driven.

1.6.3. Importació en components standalone

Des d'Angular 19 els components són standalone per defecte. La configuració és:

TYPESCRIPT 
// src/app/app.component.ts
import { Component } from '@angular/core';
import { CommonModule } from '@angular/common';
import { FormsModule } from '@angular/forms'; // ← IMPORTAR
@Component({
  selector: 'app-root',
  imports: [
    CommonModule,  // Pipes i directives compatibles; el control de flux @if/@for no requereix import
    FormsModule    // Per [(ngModel)] i formularis ← AFEGIR
  ],
  templateUrl: './app.component.html',
  styleUrl: './app.component.scss'
})
export class App {
  formulariElement = {
    titol: '',
    categoria: 'Components UI',
    preu: 0
  };
}

Punts clau:

  1. Import al principi: import { FormsModule } from '@angular/forms';
  2. Afegir a imports: array dins de @Component decorator
  3. Necessari per cada component: Si teniu múltiples components amb formularis, cada un ha d'importar FormsModule

1.6.4. Error comú: Oblidar importar FormsModule

Si utilitzeu [(ngModel)] sense importar FormsModule, obteniu aquest error:

TEXT 
Error: NG8002: Can't bind to 'ngModel' since it isn't a known property of 'input'.

Solució:

TYPESCRIPT 
imports: [CommonModule, FormsModule] // ← Afegir FormsModule

1.6.5. Error comú: Oblidar atribut name

Si utilitzeu [(ngModel)] dins d'un <form> sense l'atribut name, obteniu:

TEXT 
Error: If ngModel is used within a form tag, either the name attribute must be set
or the form control must be defined as 'standalone' in ngModelOptions.

Per què Angular necessita name?

Angular crea automàticament un objecte NgForm per cada <form> a la plantilla. Aquest objecte registra tots els controls amb [(ngModel)] utilitzant el valor de l'atribut name com a clau. Sense name, Angular no pot identificar el control dins del formulari.

Exemple correcte:

HTML 
<form>
<!-- CORRECTE: cada control té name únic -->
<input type="text" name="titol" [(ngModel)]="formulariElement.titol" />
<input type="number" name="preu" [(ngModel)]="formulariElement.preu" />
<select name="categoria" [(ngModel)]="formulariElement.categoria">
<option value="ui">Components UI</option>
</select>
</form>

Exemple incorrecte:

HTML 
<form>
<!-- ERROR: sense name dins d'un <form> → "name attribute must be set" -->
<input type="text" [(ngModel)]="formulariElement.titol" />
<input type="number" [(ngModel)]="formulariElement.preu" />
</form>

1.6.6. Controls fora de <form> i l'opció standalone

L'atribut name serveix per registrar el control al NgForm del <form> que el conté. Per tant, fora d'un <form> no hi ha cap formulari on registrar-se i name no és necessari:

HTML 
<!-- Fora de <form>: funciona sense name -->
<input type="text" [(ngModel)]="cerca" />

Dins d'un <form> teniu dues opcions: posar-hi name (l'habitual: el control passa a formar part del formulari, amb el seu estat de validesa) o bé declarar-lo standalone perquè no es registri al formulari pare, per exemple un camp de cerca dins del mateix <form> que no s'ha d'enviar:

HTML 
<form (ngSubmit)="enviar()">
  <input type="text" name="titol" [(ngModel)]="element.titol" />
  <!-- No forma part del NgForm: no compta per a la validesa ni per a resetForm() -->
  <input type="text" [(ngModel)]="filtreRapid" [ngModelOptions]="{standalone: true}" />
</form>

Fora d'un formulari, standalone: true no té cap efecte.

1.6.7. FormsModule vs ReactiveFormsModule

Angular té dos mòduls de formularis:

Mòdul Enfocament Quan usar
FormsModule Template-driven Formularis simples (3-10 camps), prototipatge ràpid
ReactiveFormsModule Model-driven Formularis complexos, validacions avançades, control programàtic

En aquesta lectura utilitzeu FormsModule perquè és més intuïtiu per començar. A unitats posteriors veureu ReactiveFormsModule per a casos més avançats.

Èxit
Clau: Cal importar FormsModule d'@angular/forms i afegir-lo a l'array imports del component. Cada control amb [(ngModel)] necessita atribut name únic dins d'un <form>.

1.9. Exemple pràctic: formulari de cerca amb múltiples camps

1.9.1. Objectiu

1.9.2. Model de cerca

TYPESCRIPT 
// Component
export class App {
  // Model de cerca
  filtreCerca = {
    text: '',
    categoria: '',
    preuMaxim: 200,
    nomesDisponibles: false
  };
  // Dades del catàleg (exemple)
  elementsCataleg = [
    {
      id: 2,
      titol: 'Catàleg de colors corporatius',
      categoria: 'Paletes',
      preu: 49.9,
      disponible: true
    },
    {
      id: 3,
      titol: 'Iconografia consistent',
      categoria: 'Icones',
      preu: 89.5,
      disponible: true
    },
    {
      id: 4,
      titol: 'Sistema de tipografia',
      categoria: 'Tipografia',
      preu: 29.0,
      disponible: false
    }
  ];
  // Getter per filtrar elements en temps real
  get elementsFiltrats() {
    return this.elementsCataleg.filter(element => {
      // Filtre per text (títol)
      const coincideixText = !this.filtreCerca.text ||
        element.titol.toLowerCase().includes(this.filtreCerca.text.toLowerCase());
      // Filtre per categoria
      const coincideixCategoria = !this.filtreCerca.categoria ||
        element.categoria === this.filtreCerca.categoria;
      // Filtre per preu màxim
      const coincideixPreu = element.preu <= this.filtreCerca.preuMaxim;
      // Filtre per disponibilitat
      const coincideixDisponibilitat = !this.filtreCerca.nomesDisponibles ||
        element.disponible;
      return coincideixText && coincideixCategoria && coincideixPreu && coincideixDisponibilitat;
    });
  }
  // Mètode per reiniciar filtres
  reiniciarFiltres(): void {
    this.filtreCerca = {
      text: '',
      categoria: '',
      preuMaxim: 200,
      nomesDisponibles: false
    };
  }
}

1.10. Gestió d'enviament: prevenir comportament per defecte

1.10.1. Objectiu

Aprendre a gestionar l'enviament del formulari amb (ngSubmit), prevenir el refresc de la pàgina, i processar les dades capturades.

1.10.2. Problema: comportament per defecte del formulari

HTML 
<!-- Formulari HTML tradicional (refresca la pàgina) -->
<form>
<input type="text" name="titol" [(ngModel)]="formulariElement.titol" />
<button type="submit">Guardar</button>
</form>

Què passa:

  1. L'usuari prem "Guardar"
  2. El navegador envia el formulari (per defecte a la URL actual)
  3. La pàgina es refresca → perds tot l'estat de l'aplicació

1.10.3. Solució: directiva (ngSubmit)

HTML 
<!-- Formulari Angular (no refresca) -->
<form (ngSubmit)="enviaFormulari()">
<input type="text" name="titol" [(ngModel)]="formulariElement.titol" />
<button type="submit">Guardar</button>
</form>
TYPESCRIPT 
// Component
enviaFormulari(): void {
  console.log('Formulari enviat!', this.formulariElement);
  // Processar dades aquí
}

Què passa:

  1. L'usuari prem "Guardar"
  2. Angular intercepta l'esdeveniment submit
  3. Angular prevé el comportament per defecte (no refresca)
  4. Angular executa enviaFormulari()
  5. La pàgina no es refresca → estat preservat

1.10.4. Avantatges de (ngSubmit)

  • Prevé automàticament el refresc de pàgina
  • No cal cridar event.preventDefault() manualment
  • Integrat amb el sistema de formularis d'Angular (estat valid/invalid)

1.10.5. Processar les dades enviades

TYPESCRIPT 
// Component
export class App {
  formulariElement = {
    titol: '',
    categoria: 'Components UI',
    preu: 0,
    descripcio: ''
  };
  entradesFormulari: any[] = [];
  enviaFormulari(): void {
    // 1. Validació bàsica (opcional)
    if (!this.formulariElement.titol) {
      alert('El títol és obligatori');
      return;
    }
    // 2. Crear còpia de les dades (IMPORTANT)
    const novaEntrada = { ...this.formulariElement };
    // 3. Afegir a l'historial
    this.entradesFormulari.unshift(novaEntrada);
    // 4. Feedback a l'usuari
    console.log('Element afegit:', novaEntrada);
    console.log('Total elements:', this.entradesFormulari.length);
    // 5. Reiniciar formulari (següent punt)
    this.reiniciarFormulari();
  }
  reiniciarFormulari(): void {
    this.formulariElement = {
      titol: '',
      categoria: 'Components UI',
      preu: 0,
      descripcio: ''
    };
  }
}

2.2. Marc conceptual

2.2.1. Què són les validacions de formulari

Les validacions són regles que comprovem abans d'acceptar dades d'un formulari. Defineixen requisits com ara "el títol ha de tenir mínim 4 caràcters" o "l'email ha de seguir el patró usuari@domini.com". Angular proporciona validacions integrades per atributs HTML que es sincronitzen automàticament amb l'estat del control, i també permet crear validacions personalitzades quan les integrades no cobreixen el cas.

2.2.2. Problema sense validacions

Situació abans:

HTML 
<!-- Formulari sense validacions -->
<form (ngSubmit)="enviaFormulari()">
<input type="text" name="titol" [(ngModel)]="formulariElement.titol">
<input type="number" name="preu" [(ngModel)]="formulariElement.preu">
<button type="submit">Guardar</button>
</form>

Problemes que genera:

1. Dades incoherents al catàleg
L'usuari pot enviar un títol buit o un preu negatiu (-50 €). Aquestes dades arriben al servei sense filtrar i generen errors al backend o elements inútils al catàleg.

2. Experiència d'usuari confusa
Sense feedback visual, l'usuari no sap si ha comès errors fins que el servidor respon (potser 2-3 segons després). Durant aquest temps, l'aplicació sembla "penjada" i l'usuari no entén què ha fallat.

3. Sobrecàrrega del servidor
Cada intent d'enviament genera una petició HTTP, fins i tot amb dades òbviament invàlides. Si 20 alumnes proven el formulari sense validacions, es generen centenars de peticions innecessàries que el servidor ha de processar i rebutjar.

4. Pèrdua de confiança de l'usuari
Si el formulari accepta dades evidentment errònies i després falla de manera inesperada, l'usuari perd confiança en l'aplicació. Una validació preventiva demostra professionalitat i atenció al detall.

2.2.3. Solució amb validacions integrades

Angular proporciona validacions per atributs HTML que funcionen automàticament amb formularis template-driven:

HTML

2.3. Model mental

2.3.1. Una sola font de veritat per a les regles

Definiu els valors de validació (mínims, màxims, patrons) a la classe del component i referencieu-los a la plantilla. Així, si heu de canviar el mínim del títol de 4 a 5 caràcters, només toqueu un lloc.

2.3.2. Estats del control com a semàfor

Cada control té tres "llums": valid (verd, tot correcte), invalid (vermell, hi ha errors), i pending (groc, en validacions asíncrones). Combineu aquests estats amb touched o dirty per decidir quan encendre la llum d'error.

2.3.3. Mostrar errors després de la interacció

No mostreu errors immediatament. Espereu que l'usuari surti del camp (touched) o el modifiqui (dirty). Això evita saturar-lo amb avisos vermells abans que hagi tingut oportunitat de completar l'entrada.

El botó només permet l'acció quan el formulari complet és vàlid. Actueu de forma defensiva: si formulariElementForm.invalid, desactiveu el botó i eviteu l'enviament al mètode enviaFormulari.

2.4.1. Objectiu

Comprendre la importància de les validacions des de la perspectiva de l'usuari i del sistema.

2.4.2. Contingut

Les validacions serveixen dos propòsits fonamentals: millorar l'experiència d'usuari i garantir la integritat de les dades. Des de la perspectiva de l'usuari, un formulari sense validacions és com conduir sense senyals: no saps si vas bé fins que tens un accident. Imagineu que ompliu un formulari llarg, premeu "Enviar", i després de 3 segons rebeu un missatge genèric d'error del servidor sense cap pista de què ha fallat. Frustrant, oi? Les validacions preventives eviten aquest problema: us avisen abans d'enviar que el títol és massa curt o el preu està fora de rang.

Des de la perspectiva del sistema, les validacions actuen com a primera línia de defensa. Si permeteu que dades incoherents arribin al servidor (títols buits, preus negatius, emails mal formats), genereu una cadena de problemes: errors al backend, registres inútils a la base de dades, dificultat per depurar, i sobrecàrrega de peticions HTTP innecessàries. Cada formulari sense validacions és una porta oberta a dades brossa.

A més, les validacions milloren la percepció de qualitat de l'aplicació. Un formulari que mostra missatges clars i estils visuals (camps vermells/verds) transmet professionalitat i atenció al detall. En contrast, un formulari que accepta qualsevol cosa i després falla inesperadament genera desconfiança.

En el context del catàleg d'elements, validar el formulari assegura que tots els elements afegits tenen dades coherents i útils per a l'equip. Un títol buit o un preu de -50 € no aporten valor i només generen confusió. Les validacions són un contracte de qualitat que beneficia tant l'usuari actual com els futurs col·laboradors del projecte.

2.5.1. Objectiu

2.5.2. Validacions integrades principals

Angular proporciona un conjunt de validacions per atributs HTML que funcionen automàticament amb formularis template-driven:

1. required — Camp obligatori
Marca el camp com a obligatori. Si l'usuari no introdueix cap valor, el control és invalid.

HTML 
<input type="text" name="titol" required [(ngModel)]="formulariElement.titol">

Ús típic: tots els camps essencials (títol, preu, categoria).

2. minlength i maxlength — Longitud de text
Defineixen la longitud mínima i màxima de caràcters per a camps de text.

HTML 
<input type="text" name="titol" minlength="4" maxlength="60" [(ngModel)]="formulariElement.titol">

Ús típic: títols (mínim 4, màxim 60), descripcions (mínim 10, màxim 200).

3. min i max — Rang numèric
Defineixen el valor mínim i màxim per a camps de tipus number.

HTML

Ús típic: preus (mínim 5 €, màxim 500 €), edats (mínim 18, màxim 99), quantitats (mínim 1, màxim 100).

4. pattern — Expressió regular personalitzada
Valida el valor contra una expressió regular. Útil per a formats específics com codis postals, telèfons o DNI.

HTML 
<input type="text" name="codiPostal" pattern="[0-9]{5}" [(ngModel)]="formulariElement.codiPostal">

Ús típic: codis postals ([0-9]{5}), telèfons ([0-9]{9}), DNI ([0-9]{8}[A-Z]).

Valida que el valor segueixi el format bàsic d'un email (usuari@domini.com).

2.6. Estats dels controls: valid, invalid, touched, pristine, dirty

2.6.1. Objectiu

Dominar els estats dels controls per decidir quan mostrar missatges d'error i aplicar estils.

2.6.2. Estats de validesa

1. valid — Totes les validacions passen
El control compleix totes les regles de validació.

HTML 
<input #campTitol="ngModel" ...>
@if (campTitol.valid) {
<p>Correcte</p>
}

2. invalid — Alguna validació falla
El control no compleix almenys una regla. L'objecte errors conté els detalls dels errors actius.

HTML 
@if (campTitol.invalid) {
<p>Hi ha errors</p>
}

2.6.3. Estats d'interacció

3. touched — L'usuari ha sortit del camp
Angular marca el control com touched quan l'usuari entra al camp i després en surt (per exemple, amb tab o clic fora).

HTML 
@if (campTitol.invalid && campTitol.touched) {
<p>Corregiu els errors</p>
}

4. untouched — L'usuari encara no ha tocat el camp
Estat inicial. El control és untouched fins que l'usuari hi entra.

5. dirty — L'usuari ha modificat el valor
Angular marca el control com dirty quan l'usuari canvia el valor (escriu o esborra text).

HTML 
@if (campTitol.invalid && campTitol.dirty) {
<p>Corregiu els errors</p>
}

6. pristine — Valor original, no modificat
Contrari de dirty. El control és pristine si conserva el valor inicial.

2.6.4. Seqüència d'estats

Imagineu un camp amb required minlength="4":

  1. Inicial: untouched, pristine, invalid (perquè required i està buit).
  2. Usuari entra al camp: encara untouched, pristine, invalid.
  3. Usuari escriu "App" (3 caràcters): dirty, invalid (falta 1 caràcter).
  4. Usuari surt del camp amb tab: touched, dirty, invalid → ara mostrem l'error.
  5. Usuari torna i escriu "Apps" (4 caràcters): touched, dirty, valid → error desapareix.

2.6.5. Taula resum d'estats

Estat Significat Quan passa Ús típic
valid Totes les validacions OK Valor compleix regles Mostrar feedback positiu
invalid Alguna validació falla Valor no compleix regles Mostrar missatges d'error
touched Usuari ha sortit del camp Després de blur (perd focus) Activar errors després d'interacció
untouched Usuari no ha tocat el camp Estat inicial Amagar errors fins que toqui
dirty Usuari ha modificat el valor Després de qualsevol canvi Alternativa a touched per errors
pristine Valor original, sense canvis Estat inicial o després de reset Comparar amb dirty

2.6.6. Per què combinar invalid amb touched o dirty?

Si només useu invalid, els errors es mostren immediatament quan el formulari es carrega, encara que l'usuari no hagi tocat res. Això satura l'usuari amb avisos vermells abans que tingui oportunitat d'omplir el formulari. La combinació invalid && (touched || dirty) garanteix que els errors només apareixen després que l'usuari hagi interactuat amb el camp.

Èxit
Clau: Combineu invalid amb touched o dirty per mostrar errors només després de la interacció de l'usuari, evitant saturar-lo amb avisos prematurs.

2.8. Desactivar botó d'enviament si formulari no és vàlid

2.8.1. Objectiu

Bloquejar l'enviament del formulari quan hi ha errors i gestionar correctament la submissió.

2.8.2. Pas 1: Referenciar el formulari

A la plantilla, afegiu la directiva ngForm al <form> i assigneu-li una referència:

HTML 
<form #formulariElementForm="ngForm" (ngSubmit)="enviaFormulari(formulariElementForm)">
<!-- controls aquí -->
<button type="submit" [disabled]="formulariElementForm.invalid">Guardar element</button>
</form>

2.8.3. Pas 2: Desactivar el botó amb [disabled]

Vinculeu la propietat disabled del botó a l'estat invalid del formulari:

HTML 
<button type="submit" [disabled]="formulariElementForm.invalid">Guardar element</button>

Resultat: el botó queda desactivat (grisat, no clicable) si algun control del formulari és invalid. Quan tots els controls són valid, el botó s'activa automàticament.

2.8.4. Pas 3: Gestionar la submissió defensivament

Tot i que el botó està desactivat, és recomanable afegir una comprovació defensiva al mètode enviaFormulari:

TYPESCRIPT 
import { NgForm } from '@angular/forms';
enviaFormulari(formulari: NgForm): void {
  // Comprovació defensiva: si el formulari és invàlid, atura l'execució
  if (formulari.invalid) {
    formulari.control.markAllAsTouched(); // Marca tots els controls com touched
    return;
  }
  // Si arribem aquí, el formulari és vàlid
  const novaEntrada = { ...this.formulariElement };
  this.entradesFormulari.unshift(novaEntrada);
  // Reiniciar el formulari amb valors per defecte
  formulari.resetForm({
    titol: '',
    categoria: 'Components UI',
    preu: 0,
    descripcio: '',
    disponible: true
  });
}

Explicació de markAllAsTouched(): Si l'usuari intenta enviar el formulari amb errors (per exemple, prement Enter), aquest mètode marca tots els controls com touched. Així, els blocs de missatges d'error condicionals es mostren immediatament, indicant a l'usuari quins camps requereixen atenció.

Èxit
Clau: Desactiveu el botó amb [disabled]=formulariElementForm.invalid i afegiu una comprovació defensiva al mètode enviaFormulari amb markAllAsTouched() per mostrar tots els errors si l'usuari intenta enviar.

2.11. Millor moment per mostrar errors: touched vs dirty

3.2. Marc conceptual

3.2.1. Què és l'accessibilitat web

L'accessibilitat web garanteix que totes les persones, independentment de les seves capacitats físiques, sensorials o cognitives, puguin percebre, comprendre, navegar i interactuar amb una aplicació web. En el context dels formularis, això significa que usuaris amb diversitat funcional (ceguesa, baixa visió, mobilitat reduïda, dificultats cognitives) han de poder completar el formulari amb les seves eines habituals: lectors de pantalla (VoiceOver, NVDA, JAWS), navegació només amb teclat, magnificadors de pantalla, o controls per veu.

3.2.2. Problema sense accessibilitat

Situació abans:

Imagineu un formulari sense etiquetes semàntiques ni atributs ARIA, tal com el teníeu abans de la lectura 2.3.1:

HTML 
<form (ngSubmit)="enviaFormulari()">
<input type="text" placeholder="Títol" [(ngModel)]="formulariElement.titol">
<input type="number" placeholder="Preu" [(ngModel)]="formulariElement.preu">
@if (campTitol.invalid) {
<div style="color: red;">Error!</div>
}
<button type="submit">Guardar</button>
</form>

Problemes que genera:

1. Usuaris de lector de pantalla completament perduts

Un usuari amb VoiceOver (macOS) o NVDA (Windows) només escolta "camp d'edició, buit" quan arriba al primer input. No rep cap pista de què ha d'introduir: títol? preu? descripció? Ha de confiar exclusivament en el placeholder, que desapareix en escriure i que molts lectors no anuncien correctament. És com demanar-li que ompli un formulari amb els ulls tancats sense cap instrucció verbal.

2. Errors invisibles per a tecnologies assistives

El missatge "Error!" només es mostra amb color vermell (style="color: red;"). Un usuari cec no percep aquest canvi visual i no rep cap notificació que hi ha un error. Pot intentar enviar el formulari repetidament sense entendre per què no funciona. Els lectors de pantalla necessiten role="alert" i aria-live per anunciar canvis dinàmics al contingut.

3. Navegació amb teclat caòtica o impossible

Si el formulari no respecta l'ordre natural del DOM i té elements amb tabindex mal configurat (per exemple, tabindex="5" al botó i tabindex="1" al tercer camp), l'usuari que navega amb Tab salta entre camps de manera totalment impredictible. Això genera confusió i frustració, especialment per a persones amb mobilitat reduïda que depenen exclusivament del teclat.

4. Focus invisible per a usuaris amb baixa visió

Molts frameworks CSS anullen l'estil de focus predeterminat (outline: none;) sense proporcionar una alternativa visible. Un usuari amb baixa visió que magnifica la pantalla al 200% no sap quin camp està actiu i ha d'endevinar on escriu. Això converteix l'ompliment del formulari en un joc d'atzar.

5. Ajudes textuals desconnectades

Si afegiu un text d'ajuda sota un camp (<p>Useu un títol descriptiu</p>) però no el vinculeu amb aria-describedby, el lector de pantalla no l'anuncia quan l'usuari arriba al camp. L'ajuda queda "muda" i invisible per a qui més la necessita.

6. Dificultats per complir normatives

Molts organismes públics i empreses privades estan obligats legalment a complir les WCAG (Web Content Accessibility Guidelines). Un formulari inaccessible pot comportar sancions, demandes judicials i exclusió de licitacions públiques. A més, demostra manca de responsabilitat social corporativa.

3.2.3. Solució amb accessibilitat

Aplicar bones pràctiques d'accessibilitat transforma el formulari en una eina inclusiva i usable per a tothom. Les millores clau són: associar cada control amb una etiqueta semàntica (<label for="campTitol">), utilitzar atributs ARIA per descriure ajudes i errors (aria-describedby, role="alert", aria-live), respectar l'ordre natural de tabulació, proporcionar focus visible amb contrast suficient, i provar el formulari amb teclat i lectors de pantalla.

Avantatges concrets:

  • Inclusió real: qualsevol persona pot completar el formulari de manera autònoma, sense dependre d'ajuda externa.
  • Experiència d'usuari millorada per a tothom: les etiquetes clares i els missatges descriptius beneficien també usuaris sense diversitat funcional, especialment en contextos d'estrès o distraccions.
  • Compliment normatiu: aquestes pràctiques cobreixen criteris de les WCAG 2.1/2.2 (la conformitat AA s'avalua sobre el conjunt complet de criteris aplicables), i redueixen riscos legals i reputacionals.
  • SEO i posicionament: els cercadors valoren positivament l'accessibilitat com a indicador de qualitat del contingut.
  • Mantenibilitat: un codi semàntic ben estructurat facilita futurs canvis i reús de components.

3.2.4. Exemple real: Formulari inaccessible vs Formulari accessible

ABANS (formulari inaccessible):

HTML 
<form (ngSubmit)="enviaFormulari()">
<input type="text" placeholder="Títol" name="titol" [(ngModel)]="formulariElement.titol" #campTitol="ngModel">
@if (campTitol.invalid && campTitol.touched) {
<div style="color: red;">Error!</div>
}
<input type="number" placeholder="Preu" name="preu" [(ngModel)]="formulariElement.preu" #campPreu="ngModel">
@if (campPreu.invalid && campPreu.touched) {
<div style="color: red;">Error!</div>

</form>

Problemes visibles:

  • Cap <label> associat als inputs → lector de pantalla anuncia "camp d'edició, buit"
  • Missatges d'error només amb color → invisibles per a usuaris cecs
  • No hi ha aria-describedby, role="alert" ni aria-live → errors no anunciats
  • Focus no personalitzat → pot ser invisible amb alguns navegadors

DESPRÉS (formulari accessible):

HTML 
<form #formulariElementForm="ngForm" (ngSubmit)="enviaFormulari(formulariElementForm)">
<fieldset>
<legend>Dades bàsiques de l'element</legend>
<label for="campTitolInput">Títol de l'element</label>
<input id="campTitolInput" type="text" name="titol" required minlength="4" [(ngModel)]="formulariElement.titol" #campTitol="ngModel" aria-describedby="ajudaTitol errorsTitol" [attr.aria-invalid]="campTitol.invalid && campTitol.touched">
<p id="ajudaTitol" class="ajuda">Useu un títol descriptiu i únic (4-60 caràcters).</p>
@if (campTitol.invalid && campTitol.touched) {
<div id="errorsTitol" class="missatges-error" role="alert">
@if (campTitol.errors?.['required']) {
<p>Indiqueu el títol de l'element.</p>
}
@if (campTitol.errors?.['minlength']) {
<p>El títol ha de tenir mínim 4 caràcters.</p>
}
</div>
}
<label for="campPreuInput">Preu (€)</label>
<input id="campPreuInput" type="number" name="preu" required min="5" [(ngModel)]="formulariElement.preu" #campPreu="ngModel" aria-describedby="ajudaPreu errorsPreu" [attr.aria-invalid]="campPreu.invalid && campPreu.touched">
<p id="ajudaPreu" class="ajuda">Preu entre 5 i 500 €.</p>
@if (campPreu.invalid && campPreu.touched) {
<div id="errorsPreu" class="missatges-error" role="alert">
@if (campPreu.errors?.['required']) {
<p>Indiqueu el preu.</p>
}
@if (campPreu.errors?.['min']) {
<p>El preu mínim és 5 €.</p>
}
</div>
}
</fieldset>
<button type="submit" [disabled]="formulariElementForm.invalid">Guardar element</button>
</form>

Millores visibles:

  • Cada input té <label for="..."> associat → lector anuncia "Títol de l'element, camp d'edició requerit"
  • Ajudes vinculades amb aria-describedby="ajudaTitol" → lector les anuncia automàticament
  • Errors amb role="alert" → anuncis immediats (el rol ja implica aria-live="assertive")
  • aria-invalid="true" quan hi ha errors → lector informa de l'estat invàlid
  • <fieldset> i <legend> per agrupar controls relacionats → context clar

Què canvia per a l'usuari:

  • Identificació dels camps: cada control s'anuncia amb el seu nom, tipus i estat; no cal endevinar què s'hi ha d'escriure
  • Errors: s'anuncien quan apareixen i s'expliquen; l'usuari sap què corregir sense veure el color vermell
  • Autonomia: el formulari es pot completar amb teclat o lector de pantalla sense ajuda externa
  • Cost: unes quantes desenes de línies d'atributs ARIA, label i fieldset, sense canviar la lògica

3.2.8. Característiques principals de l'accessibilitat en formularis

1. Etiquetes semàntiques obligatòries

Cada control (input, select, textarea) ha de tenir una etiqueta visible (<label>) associada per l'atribut for. Això permet als lectors de pantalla anunciar el propòsit del camp quan l'usuari hi arriba amb el focus. Exemple: <label for="email">Correu electrònic</label> <input id="email" type="email">.

2. Atributs ARIA per a context addicional

Quan un camp necessita ajudes, descripcions o missatges d'error, utilitzeu aria-describedby per vincular-los. Això garanteix que el lector de pantalla els anuncia automàticament. Exemple: <input aria-describedby="ajudaEmail errorsEmail">.

3. Anuncis dinàmics amb role="alert" i aria-live

Els missatges d'error que apareixen després de validacions han de ser anunciats immediatament. role="alert" converteix un <div> en una regió d'alerta que els lectors detecten automàticament. aria-live="assertive" força l'anunci immediat (per errors urgents), mentre que "polite" espera que l'usuari acabi la tasca actual.

4. Ordre de tabulació lògic i predictible

Respecteu l'ordre natural del DOM (d'esquerra a dreta, de dalt a baix). Eviteu tabindex positius (tabindex="3") que trenquen l'ordre natural. Utilitzeu tabindex="0" només per elements no focusables per defecte (divs personalitzats) i tabindex="-1" per elements que no han de rebre focus amb Tab però que poden ser enfocats programàticament.

5. Focus visible amb contrast suficient

Definiu un estil de focus personalitzat que superi el contrast 3:1 contra el fons (bona pràctica recollida al criteri 2.4.13 Focus Appearance de WCAG 2.2, nivell AAA). Un borde blau gruixut amb box-shadow és una bona opció. Mai utilitzeu outline: none; sense proporcionar una alternativa clarament visible.

6. Agrupació semàntica amb fieldset i legend

Per a formularis llargs amb múltiples seccions, utilitzeu <fieldset> per agrupar controls relacionats i <legend> per donar-los un títol. Això proporciona context addicional als lectors de pantalla: "Dades bàsiques, grup, 3 elements".

7. Validació accessible amb aria-invalid

Quan un camp té errors, afegiu aria-invalid="true" perquè el lector de pantalla anunciï "invàlid" en arribar al camp. Això complementa els missatges d'error i ajuda l'usuari a identificar ràpidament camps problemàtics.

8. Proves manuals amb eines reals

L'única manera de garantir l'accessibilitat és provar el formulari amb teclat (només Tab, Shift+Tab, Enter, Space) i amb lectors de pantalla (VoiceOver a macOS, NVDA a Windows). Les eines automàtiques (Lighthouse, axe DevTools) detecten errors evidents però no poden validar l'experiència real.

3.4. Per què l'accessibilitat és important: usuaris amb diversitat funcional

3.4.1. Objectiu

Comprendre la importància de l'accessibilitat des de la perspectiva dels usuaris amb diversitat funcional i del compliment normatiu.

3.4.2. Contingut

L'accessibilitat no és un luxe opcional ni una millora cosmètica: és un dret fonamental que garanteix que totes les persones puguin accedir a la informació i serveis digitals de manera equitativa. Quan desenvolupeu un formulari, us esteu adreçant potencialment a persones amb ceguesa, baixa visió, daltonisme, sordesa (si el formulari inclou vídeos o àudio), mobilitat reduïda (que depenen de teclat, controls per veu o interruptors adaptats), dificultats cognitives (que necessiten instruccions clares i missatges senzills), o combinacions d'aquestes condicions.

Dades del context real:

Segons l'Organització Mundial de la Salut (OMS), aproximadament el 15% de la població mundial té alguna forma de diversitat funcional. A Catalunya, això representa més de 1 milió de persones. Si el vostre formulari no és accessible, esteu excloent automàticament una part significativa del vostre públic potencial.

Escenaris reals on l'accessibilitat és crítica:

1. Registre a un curs universitari

Una estudiant amb ceguesa utilitza el lector de pantalla JAWS per registrar-se a un curs. Si el formulari no té labels associats, només escolta "camp d'edició, buit" i ha d'endevinar què ha d'escriure. Pot perdre el termini d'inscripció per culpa d'un formulari mal dissenyat.

2. Sol·licitud d'ajudes públiques

Un ciutadà amb mobilitat reduïda als braços només pot utilitzar el teclat. Si el formulari requereix arrossegar un fitxer amb el ratolí o té un ordre de tabulació caòtic, no pot completar la sol·licitud i perd l'accés a ajudes econòmiques essencials.

3. Compra en línia

Una persona amb baixa visió magnifica la pantalla al 300%. Si el focus no és visible o els missatges d'error són només colors sense text, no pot saber on està escrivint ni què ha fallat. Acaba abandonant la compra per frustració.

Aspecte legal i normatiu:

Molts països (incloent-hi Espanya amb el Reial Decret 1112/2018) obliguen els organismes públics i empreses grans a complir les WCAG 2.1 nivell AA (Web Content Accessibility Guidelines). El no compliment pot comportar sancions econòmiques, demandes judicials per discriminació, i exclusió de licitacions públiques. A més, demostra una manca de responsabilitat social corporativa que pot danyar greument la reputació de l'empresa.

Beneficis per a tothom:

Les millores d'accessibilitat no només ajuden usuaris amb diversitat funcional. Un formulari amb etiquetes clares, instruccions contextuals i missatges d'error descriptius beneficia també:

  • Persones grans amb habilitats digitals limitades
  • Usuaris en entorns amb distraccions (transport públic, oficines sorolloses)
  • Persones que naveguen amb la mà no dominant (per lesió temporal)
  • Qualsevol que utilitzi el formulari en una pantalla petita (mòbil) o amb connexió lenta
Èxit
Clau: l'accessibilitat no és caritat; és una inversió en qualitat, inclusió i compliment normatiu que beneficia tots els usuaris i protegeix l'organització de riscos legals.

3.4.3. Resultat esperat

Reconeixeu la importància de l'accessibilitat com a dret fonamental, compreneu els escenaris reals on és crítica, i enteneu les implicacions legals del no compliment.

3.5. Etiquetes (labels): sempre associar amb inputs, atribut for

3.5.1. Objectiu

Dominar l'associació correcta de labels amb controls utilitzant l'atribut for i comprendre per què és fonamental.

3.5.2. Contingut

La manera més bàsica i efectiva de fer un formulari accessible és associar cada control amb una etiqueta visible (<label>). Aquest patró funciona per a <input>, <select>, <textarea> i garanteix que els lectors de pantalla anuncien correctament el propòsit del camp.

Sintaxi correcta:

HTML 
<label for="campTitolInput">Títol de l'element</label>
<input id="campTitolInput" type="text" name="titol" [(ngModel)]="formulariElement.titol">

Com funciona:

  • L'atribut for del <label> conté el valor de l'id de l'<input>.
  • Quan l'usuari fa clic a la label, el navegador enfoca automàticament l'input associat (millora l'experiència tàctil en mòbils).
  • Els lectors de pantalla anuncien "Títol de l'element, camp d'edició" quan l'usuari arriba al control amb Tab.

Error comú: label sense atribut for

HTML 
<label>Títol de l'element</label>
<input id="campTitolInput" type="text">

Encara que visualment sembla correcte, el lector de pantalla no associa la label amb l'input perquè no hi ha connexió explícita. Anuncia només "camp d'edició, buit".

Error comú: només placeholder

HTML 
<input type="text" placeholder="Títol de l'element">

Els placeholders no són accessibles:

  • Desapareixen quan l'usuari comença a escriure (pèrdua del context).
  • Molts lectors de pantalla els ignoren o els anuncien de manera inconsistent.
  • Usuaris amb problemes de memòria poden oblidar què havien de posar.

Patró correcte amb label sempre visible:

HTML 
<label for="campTitolInput">Títol de l'element</label>
<input id="campTitolInput" type="text" name="titol" required minlength="4" [(ngModel)]="formulariElement.titol" #campTitol="ngModel" placeholder="Ex: Botó primari amb icona">

La label és sempre visible, el placeholder només dóna un exemple opcional.

Casos especials:

1. Labels per a checkboxes i radio buttons

HTML 
<input type="checkbox" id="disponibleCheck" name="disponible" [(ngModel)]="formulariElement.disponible">
<label for="disponibleCheck">Disponible al catàleg</label>

Nota: l'ordre pot variar (input abans o després de la label) segons el disseny, però l'associació for/id és obligatòria.

2. Labels per a selects

HTML 
<label for="categoriaSelect">Categoria</label>
<select id="categoriaSelect" name="categoria" [(ngModel)]="formulariElement.categoria">
<option value="Components UI">Components UI</option>
<option value="Paletes">Paletes</option>
</select>

3. Labels per a textarea

HTML 
<label for="descripcioTextarea">Descripció breu</label>
<textarea id="descripcioTextarea" name="descripcio" rows="3" [(ngModel)]="formulariElement.descripcio"></textarea>

Taula resum labels obligatòries:

Tipus de control Estructura obligatòria Exemple d'anunci (lector)
<input type="text"> <label for="id">...</label> <input id="id"> "Títol, camp d'edició"
<input type="email"> <label for="id">...</label> <input id="id" type="email"> "Correu electrònic, camp d'edició"
<input type="number"> <label for="id">...</label> <input id="id" type="number"> "Preu, camp numèric"
<textarea> <label for="id">...</label> <textarea id="id"> "Descripció, àrea de text"
<select> <label for="id">...</label> <select id="id"> "Categoria, botó desplegable"
<input type="checkbox"> <input id="id" type="checkbox"> <label for="id">...</label> "Disponible, casella de selecció, no marcada"
<input type="radio"> <input id="id" type="radio"> <label for="id">...</label> "Opció A, botó d'opció, no seleccionat"
Èxit
Clau: l'associació <label for="id"> amb <input id="id"> és la base de l'accessibilitat i ha d'estar present en el 100% dels controls del formulari.

3.5.3. Resultat esperat

Sabeu crear labels correctament associades a tots els tipus de controls i compreneu per què els placeholders no són substituts vàlids.

3.6. Atributs ARIA bàsics: aria-label, aria-describedby, aria-required

3.6.1. Objectiu

Utilitzar atributs ARIA per proporcionar context addicional quan les etiquetes visibles no són suficients.

3.6.2. Contingut

ARIA (Accessible Rich Internet Applications) és un conjunt d'atributs HTML que milloren l'accessibilitat de components dinàmics i complexos. Els atributs més importants per a formularis són aria-label, aria-describedby, aria-required i aria-invalid.

1. aria-describedby — Vincular ajudes i errors

Aquest atribut permet associar un o més elements (textos d'ajuda, missatges d'error) amb un control. El lector de pantalla els anuncia automàticament quan l'usuari arriba al camp.

Exemple:

HTML 
<label for="campTitolInput">Títol de l'element</label>
<input id="campTitolInput" type="text" name="titol" required [(ngModel)]="formulariElement.titol" aria-describedby="ajudaTitol errorsTitol">
<p id="ajudaTitol" class="ajuda">Useu un títol descriptiu i únic (4-60 caràcters).</p>
@if (campTitol.invalid && campTitol.touched) {
<div id="errorsTitol">
<p>El títol ha de tenir mínim 4 caràcters.</p>
</div>
}

Anunci del lector de pantalla:

"Títol de l'element, camp d'edició requerit, Useu un títol descriptiu i únic (4-60 caràcters)."

Si hi ha errors, també anuncia: "El títol ha de tenir mínim 4 caràcters."

Notes:

  • Podeu vincular múltiples ids separats per espais: aria-describedby="ajuda1 ajuda2 error1".
  • Els elements vinculats no cal que siguin visibles sempre (per exemple, els errors només apareixen quan campTitol.invalid), però han de tenir id únic.

2. aria-label — Etiqueta invisible

Utilitzeu aquest atribut quan no hi ha una label visible (per exemple, botons només amb icona) però necessiteu proporcionar context al lector de pantalla.

Exemple:

HTML 
<button type="button" aria-label="Tancar diàleg">
<svg><!-- icona X --></svg>
</button>

Anunci del lector: "Tancar diàleg, botó"

Important: NO utilitzeu aria-label en inputs normals que ja tenen <label>. Això sobrescriu la label visible i pot crear confusió.

Error comú:

HTML 
<label for="campTitol">Títol</label>
<input id="campTitol" aria-label="Títol de l'element">
<!-- El lector ignora la label visible i anuncia només "Títol de l'element" -->

Correcte:

HTML 
<label for="campTitol">Títol de l'element</label>
<input id="campTitol">
<!-- El lector anuncia la label visible -->

3. aria-required — Indicar camps obligatoris

Aquest atribut informa els lectors de pantalla que el camp és obligatori. En controls HTML natius, required ja s'exposa a les tecnologies assistives als navegadors actuals, de manera que aria-required és redundant: pot ser útil en patrons personalitzats o per compatibilitat, però no cal afegir-lo sistemàticament.

Exemple:

HTML 
<input type="text" required aria-required="true">

Anunci del lector: "Camp d'edició requerit"

Nota: Angular permet vincular dinàmicament:

HTML 
<input [attr.aria-required]="campTitol.hasError('required')">

4. aria-invalid — Indicar errors

Aquest atribut informa que el valor del camp és invàlid. Afegiu-lo dinàmicament quan hi ha errors.

Exemple:

HTML 
<input type="text" [attr.aria-invalid]="campTitol.invalid && campTitol.touched">

Anunci del lector: "Camp d'edició invàlid" (quan aria-invalid="true")

Taula resum atributs ARIA bàsics:

Atribut Funció Exemple Quan usar
aria-describedby Vincula ajudes/errors aria-describedby="ajuda error" Sempre que hi ha textos d'ajuda o errors
aria-label Etiqueta invisible aria-label="Tancar" Botons només icona, controls sense label visible
aria-required Camp obligatori aria-required="true" Controls personalitzats o compatibilitat; en controls natius required és suficient
aria-invalid Valor invàlid [attr.aria-invalid]="campTitol.invalid" Quan hi ha errors de validació

Exemple complet amb tots els atributs:

HTML 
<label for="campEmailInput">Correu electrònic</label>
<input id="campEmailInput" type="email" name="email" required [(ngModel)]="formulariElement.email" #campEmail="ngModel" aria-describedby="ajudaEmail errorsEmail" [attr.aria-required]="true" [attr.aria-invalid]="campEmail.invalid && campEmail.touched">
<p id="ajudaEmail" class="ajuda">Utilitzarem aquest correu per enviar confirmacions.</p>
@if (campEmail.invalid && campEmail.touched) {
<div id="errorsEmail" role="alert">
@if (campEmail.errors?.['required']) {
<p>Indiqueu el correu electrònic.</p>
}
@if (campEmail.errors?.['email']) {
<p>El format del correu no és vàlid.</p>
}
</div>
}
Èxit
Clau: utilitzeu aria-describedby per vincular ajudes i errors, aria-label només per elements sense label visible, i aria-invalid per indicar errors dinàmicament.

3.6.3. Resultat esperat

Sabeu utilitzar els 4 atributs ARIA bàsics per millorar el context dels controls i compreneu quan aplicar cada un.

3.7. Ordre de tabulació: tabindex i navegació amb teclat

3.7.1. Objectiu

Garantir un ordre de tabulació lògic i predictible, utilitzant tabindex només quan calgui.

3.7.2. Contingut

La navegació amb teclat és essencial per a usuaris que no poden utilitzar el ratolí: persones amb mobilitat reduïda, ceguesa, o simplement usuaris que prefereixen la velocitat del teclat. L'ordre de tabulació (seqüència en què el focus passa entre elements en prémer Tab) ha de seguir l'ordre visual del formulari: d'esquerra a dreta, de dalt a baix, sense salts inesperats.

Ordre natural del DOM

Per defecte, els navegadors respecten l'ordre en què els elements apareixen al codi HTML (DOM). Això significa que si el vostre HTML està ben estructurat, l'ordre de tabulació ja serà correcte sense cap configuració addicional.

Exemple correcte (ordre natural):

HTML 
<form>
<label for="camp1">Camp 1</label>
<input id="camp1">
<label for="camp2">Camp 2</label>
<input id="camp2">
<label for="camp3">Camp 3</label>
<input id="camp3">
<button type="submit">Guardar</button>
</form>

Ordre de tabulació: Camp 1 → Camp 2 → Camp 3 → Botó Guardar

Problema: ordre visual vs ordre del DOM

Si utilitzeu CSS per canviar l'ordre visual (Flexbox amb order, Grid amb posicionament), podeu crear un desajust entre el que veu l'usuari i l'ordre de tabulació.

Exemple problemàtic:

HTML 
<style>
.formulari { display: flex; flex-direction: column; }
.camp2 { order: 3; }
.camp3 { order: 2; }
</style>
<div class="formulari">
<input class="camp1"> <!-- Visual: 1 -->
<input class="camp2"> <!-- Visual: 3 (però DOM: 2) -->
<input class="camp3"> <!-- Visual: 2 (però DOM: 3) -->
</div>

Ordre visual: Camp 1 → Camp 3 → Camp 2

Ordre tabulació: Camp 1 → Camp 2 → Camp 3 (confusió)

Solució: ajusteu l'ordre del HTML perquè coincideixi amb l'ordre visual, o utilitzeu tabindex amb precaució.

L'atribut tabindex

tabindex controla si un element és focusable i el seu ordre de tabulació:

  • tabindex="0": l'element és focusable i segueix l'ordre natural del DOM.
    • Ús típic: fer focusables elements que no ho són per defecte (divs, spans personalitzats).
    • Exemple: <div tabindex="0" role="button">Clic aquí</div>
  • tabindex="-1": l'element NO és tabulable amb Tab, però pot rebre focus programàticament amb JavaScript.
    • Ús típic: diàlegs modals, seccions que l'usuari no ha d'enfocar directament però que poden rebre focus per codi.
    • Exemple: <div tabindex="-1" id="dialeg">Contingut del diàleg</div>
  • tabindex="1", "2", "3", etc. (valors positius): força un ordre específic.
    • EVITEU-HO: és molt difícil de mantenir i trenca l'ordre natural. Només per a casos molt específics i ben documentats.

Error comú: tabindex positius

HTML 
<input tabindex="3">
<input tabindex="1">
<input tabindex="2">
<button tabindex="4">Guardar</button>

Ordre de tabulació: Input 1 (tabindex="1") → Input 2 (tabindex="2") → Input 0 (tabindex="3") → Botó (tabindex="4")

Això és confús i difícil de mantenir. Si afegiu un nou camp, heu de renumerar tots els tabindex.

Solució correcta: ordre natural del DOM

HTML 
<input> <!-- tabindex implícit: 0 -->
<input> <!-- tabindex implícit: 0 -->
<input> <!-- tabindex implícit: 0 -->
<button>Guardar</button> <!-- tabindex implícit: 0 -->

Ordre de tabulació: Input 1 → Input 2 → Input 3 → Botó

Elements focusables per defecte

Aquests elements són automàticament focusables sense necessitat de tabindex:

  • <input>, <textarea>, <select>, <button>
  • <a href="..."> (només si té href)
  • Elements amb contenteditable="true"

Elements NO focusables per defecte

Aquests elements necessiten tabindex="0" per ser focusables:

  • <div>, <span>, <p>, <section>, etc.
  • <a> sense href

Exemple: botó personalitzat amb div

HTML 
<div tabindex="0" role="button" (click)="tancar()" (keydown.enter)="tancar()" (keydown.space)="tancar()">
Tancar
</div>

Verificació de l'ordre de tabulació

Prova manual:

  1. Obriu el formulari al navegador.
  2. Premeu Tab repetidament sense usar el ratolí.
  3. Anoteu l'ordre en què es van enfocant els elements.
  4. Comproveu que l'ordre coincideix amb l'ordre visual esperat.

Script de diagnòstic (opcional):

JAVASCRIPT 
// A la consola del navegador
document.querySelectorAll('input, textarea, select, button, a[href]').forEach((el, i) => {
  el.setAttribute('data-tab-order', i + 1);
  console.log(`${i + 1}: ${el.tagName} - ${el.name || el.id || '(sense nom)'}`);
});

Taula resum tabindex:

Valor Comportament Ús típic Recomanació
No especificat Ordre natural del DOM Elements focusables per defecte Preferible sempre
tabindex="0" Focusable, ordre natural Divs/spans personalitzats Quan calgui
tabindex="-1" No tabulable, focus per codi Diàlegs, seccions ocultes Casos específics
tabindex="1+" Ordre forçat (Mai) Evitar sempre
Èxit
Clau: manteniu l'ordre natural del DOM i eviteu tabindex positius; utilitzeu tabindex="0" només per elements personalitzats que han de ser focusables.

3.7.3. Resultat esperat

Compreneu com funciona l'ordre de tabulació, sabeu verificar-lo manualment, i enteneu quan utilitzar tabindex correctament.

3.8. Focus visible: indicadors clars quan element està seleccionat

3.8.1. Objectiu

Proporcionar un indicador visual clar i amb contrast suficient per mostrar quin element té el focus.

3.8.2. Contingut

El focus visible és essencial per a usuaris que naveguen amb teclat o que tenen baixa visió. Sense un indicador clar, és impossible saber quin element està actiu i on s'escriurà el text. Molts frameworks CSS moderns eliminen l'outline predeterminat del navegador (outline: none;) per raons estètiques, però això crea un problema greu d'accessibilitat si no es proporciona una alternativa.

Comportament predeterminat del navegador

Per defecte, els navegadors mostren un contorn (outline) al voltant dels elements enfocats:

  • Chrome/Edge: borde blau prim (2px)
  • Firefox: borde puntejat negre
  • Safari: borde blau gruixut amb ombra

Aquest comportament ja és accessible, però sovint es considera poc atractiu visualment. Si decidiu personalitzar-lo, heu de proporcionar una alternativa igualment visible.

Error greu: eliminar l'outline sense alternativa

CSS 
input:focus,
button:focus {
  outline: none; /* PERILLÓS: elimina el focus visible */
}

Resultat: usuaris amb teclat no poden veure on estan

Solució correcta: outline personalitzat o box-shadow

Opció 1: Mantenir outline amb color personalitzat

SCSS 
input:focus,
textarea:focus,
select:focus,
button:focus {
  outline: 3px solid #2563eb; // Blau, gruix 3px
  outline-offset: 2px; // Separació del control
}

Opció 2: Substituir outline per box-shadow (més flexible)

SCSS 
input,
textarea,
select,
button {
  outline: none; // Eliminem l'outline predeterminat
  transition: box-shadow 0.2s ease-in-out, border-color 0.2s ease-in-out;
}
input:focus,
textarea:focus,
select:focus,
button:focus {
  border-color: #2563eb; // Borde blau
  box-shadow: 0 0 0 3px rgba(37, 99, 235, 0.35); // Ombra blava difuminada
}

Avantatges de box-shadow:

  • Més control sobre l'aparença (color, mida, difuminat)
  • No afecta el layout (no suma al width/height)
  • Es pot combinar amb transicions suaus

Contrast i visibilitat segons WCAG

Un contrast mínim de 3:1 entre l'indicador de focus i el fons és la referència del criteri 2.4.13 Focus Appearance de les WCAG 2.2 (nivell AAA; el nivell AA només exigeix que el focus sigui visible, 2.4.7). Per exemple:

  • Focus blau #2563eb sobre fons blanc #ffffff: contrast ~8:1
  • Focus groc clar #ffeb3b sobre fons blanc: contrast ~1.5:1

Eina de verificació: utilitzeu el contrast checker de les DevTools del navegador (Elements → Styles → Color picker → Contrast ratio).

Estats addicionals: focus + invalid

Combineu l'estil de focus amb els estats de validació per donar més context visual:

SCSS 
// Focus normal (camp vàlid o neutre)
input:focus {
  border-color: #2563eb;
  box-shadow: 0 0 0 3px rgba(37, 99, 235, 0.35);
}
// Focus + invàlid
input.ng-invalid.ng-touched:focus {
  border-color: #dc2626; // Vermell
  box-shadow: 0 0 0 3px rgba(220, 38, 38, 0.35); // Ombra vermella
}
// Focus + vàlid
input.ng-valid.ng-touched:focus {
  border-color: #16a34a; // Verd
  box-shadow: 0 0 0 3px rgba(22, 163, 74, 0.35); // Ombra verda
}

Verificació del focus visible:

  1. Obriu el formulari al navegador.
  2. Premeu Tab per moure-us entre controls.
  3. Confirmeu que sempre veieu un indicador clar (borde blau gruixut + ombra).
  4. Proveu amb diferents combinacions: camp neutre, camp invàlid, camp vàlid.
Èxit
Clau: mai elimineu l'outline sense proporcionar una alternativa amb contrast ≥ 3:1; combineu estils de focus amb estats de validació per màxim feedback visual.

3.8.3. Resultat esperat

Sabeu crear indicadors de focus visibles i accessibles, compreneu els requisits de contrast, i enteneu com combinar focus amb estats de validació.

3.9. Missatges d'error accessibles: anuncis per a lectors de pantalla

3.9.1. Objectiu

Configurar missatges d'error que s'anunciïn automàticament als lectors de pantalla utilitzant role="alert" i aria-live.

3.9.2. Contingut

Els missatges d'error visuals (text vermell, icones) no són suficients per a usuaris amb ceguesa. Els lectors de pantalla necessiten anuncis explícits quan apareixen errors, utilitzant els atributs role="alert" i aria-live.

Per què els lectors no detecten errors automàticament?

Els lectors de pantalla no vigilen constantment tots els canvis del DOM. Només anuncien canvis en regions específiques marcades com a "actives" (live regions). Sense aquesta marca, un error que apareix dinàmicament passa desapercebut fins que l'usuari torna a visitar el camp amb Tab.

Problema sense role="alert":

HTML 
@if (campTitol.invalid && campTitol.touched) {
<div style="color: red;">
Indiqueu el títol de l'element.
</div>
}

L'usuari omple el camp incorrectament i prem Tab. El missatge d'error apareix visualment però el lector de pantalla no anuncia res. L'usuari continua al següent camp sense saber que hi ha un error.

Solució amb role="alert" i aria-live:

HTML 
@if (campTitol.invalid && campTitol.touched) {
<div role="alert" class="missatges-error">
<p>Indiqueu el títol de l'element.</p>
</div>
}

Quan el missatge apareix, el lector de pantalla l'anuncia immediatament: "Indiqueu el títol de l'element."

Atributs clau:

1. role="alert"

  • Marca l'element com a regió d'alerta urgent.
  • Els lectors de pantalla l'anuncien automàticament quan apareix.
  • Equival a aria-live="assertive" + aria-atomic="true": no cal afegir-los explícitament.

2. aria-live

  • Controla com els lectors de pantalla anuncien canvis dinàmics.
  • Valors:
    • "off": no anuncia canvis (per defecte).
    • "polite": anuncia canvis quan l'usuari acaba la tasca actual (per exemple, després d'acabar de llegir una frase).
    • "assertive": anuncia canvis immediatament, interrompent la tasca actual.

Quan utilitzar cada valor:

  • "assertive" (urgent): errors de validació, confirmacions d'enviament, alertes de seguretat.
  • "polite" (no urgent): actualitzacions de llistes, notificacions informatives, comptadors.

Exemple complet amb múltiples errors:

HTML 
<label for="campTitolInput">Títol de l'element</label>
<input id="campTitolInput" type="text" name="titol" required minlength="4" maxlength="60" [(ngModel)]="formulariElement.titol" #campTitol="ngModel" aria-describedby="ajudaTitol errorsTitol" [attr.aria-invalid]="campTitol.invalid && campTitol.touched">
<p id="ajudaTitol" class="ajuda">Useu un títol descriptiu i únic (4-60 caràcters).</p>
@if (campTitol.invalid && (campTitol.dirty || campTitol.touched)) {
<div id="errorsTitol" class="missatges-error" role="alert">
@if (campTitol.errors?.['required']) {
<p>{{ missatgesError.titol.required }}</p>
}
@if (campTitol.errors?.['minlength']) {
<p>{{ missatgesError.titol.minlength }}</p>
}
@if (campTitol.errors?.['maxlength']) {
<p>{{ missatgesError.titol.maxlength }}</p>
}
</div>
}

Anunci del lector quan l'usuari surt del camp amb error:

"Títol de l'element, camp d'edició invàlid. Indiqueu el títol de l'element. El títol ha de tenir mínim 4 caràcters."

Bones pràctiques per a missatges accessibles:

1. Missatges clars i específics

Incorrecte: "Error!"
Correcte: "Indiqueu el títol de l'element."

2. Instruccions de correcció

Incorrecte: "Camp invàlid."
Correcte: "El títol ha de tenir mínim 4 caràcters."

3. Missatges breus (1-2 línies)

Els lectors de pantalla llegeixen tot el contingut del role="alert". Missatges massa llargs saturen l'usuari.

Incorrecte: "El camp títol és obligatori i ha de contenir entre 4 i 60 caràcters. Els caràcters especials estan permesos però eviteu-ne l'ús excessiu. Recordeu que aquest títol serà visible públicament al catàleg i ha de ser descriptiu perquè altres usuaris puguin entendre de què es tracta. Consulteu la guia d'estil per a més informació."

Correcte: "Indiqueu el títol de l'element (4-60 caràcters)."

4. Un sol contenidor d'errors per camp

No creeu múltiples role="alert" per al mateix camp. Això genera anuncis duplicats.

Incorrecte:

HTML 
@if (campTitol.errors?.['required']) {
<div role="alert">Error 1</div>
}
@if (campTitol.errors?.['minlength']) {
<div role="alert">Error 2</div>
}

Correcte:

HTML 
@if (campTitol.invalid && campTitol.touched) {
<div role="alert">
@if (campTitol.errors?.['required']) {
<p>Error 1</p>
}
@if (campTitol.errors?.['minlength']) {
<p>Error 2</p>
}
</div>
}

5. Vinculeu errors amb aria-describedby

A més del role="alert", afegiu l'id del contenidor d'errors a l'aria-describedby del control. Això garanteix que els errors també s'anuncien quan l'usuari torna al camp.

HTML 
<input aria-describedby="ajudaTitol errorsTitol">
<div id="errorsTitol" role="alert">...</div>

Verificació amb lector de pantalla:

macOS (VoiceOver):

  1. Activeu VoiceOver: Cmd + F5
  2. Navegueu pel formulari amb Tab
  3. Ompliu un camp incorrectament i sortiu amb Tab
  4. Escolteu l'anunci: "Indiqueu el títol de l'element"

Windows (NVDA):

  1. Instal·leu NVDA (gratuït): https://www.nvaccess.org/download/
  2. Activeu-lo: Ctrl + Alt + N
  3. Navegueu amb Tab i escolteu els anuncis

Taula resum atributs per a errors accessibles:

Atribut Funció Valor recomanat Obligatori
role Marca regió d'alerta "alert" Sí
aria-live Control d'anuncis "assertive" (errors) Redundant amb role="alert"
id Identificador únic "errorsCampX" Sí (per aria-describedby)
aria-describedby (al control) Vincula errors al camp aria-describedby="... errorsX" Sí
Èxit
Clau: utilitzeu role="alert" per anunciar errors automàticament (ja implica aria-live="assertive"; per a canvis no urgents, aria-live="polite"), manteniu missatges breus i específics, i vinculeu-los al control amb aria-describedby.

3.10. Provar accessibilitat: navegar només amb teclat

3.10.1. Objectiu

Realitzar proves manuals d'accessibilitat navegant només amb teclat i utilitzant un lector de pantalla bàsic.

3.10.2. Contingut

La manera més efectiva de verificar l'accessibilitat d'un formulari és provar-lo amb les mateixes eines que utilitzen usuaris amb diversitat funcional: teclat i lectors de pantalla. Les eines automàtiques (Lighthouse, axe DevTools) detecten errors evidents (labels sense for, contrast baix), però no poden validar l'experiència real.

Prova 1: Navegació només amb teclat

Objectiu: completar el formulari des de zero fins a l'enviament sense tocar mai el ratolí ni la pantalla tàctil.

Passos:

  1. Obriu el formulari al navegador (http://localhost:4200).
  2. Feu clic fora del navegador per desactivar qualsevol focus inicial.
  3. Premeu Tab per entrar al formulari.
  4. Ompliu cada camp utilitzant només:
    • Tab: moure al següent element
    • Shift + Tab: tornar a l'element anterior
    • Lletres/números: escriure als camps de text
    • Space: marcar/desmarcar checkboxes
    • Fletxes amunt/avall: seleccionar opcions a <select>
    • Enter: activar botons, enviar formulari
  5. Intenteu enviar el formulari amb errors (alguns camps buits).
  6. Verifiqueu que el focus torna automàticament al primer camp amb error o que es mostra un missatge clar.
  7. Corregiu els errors i torneu a enviar amb Enter.

Què buscar:

  • L'ordre de tabulació és lògic (visual).
  • El focus és sempre visible (borde blau gruixut).
  • Tots els controls són accessibles amb teclat.
  • Els missatges d'error apareixen quan sortiu d'un camp invàlid.
  • El botó d'enviament es pot activar amb Enter o Space.
  • Salts inesperats entre camps.
  • Elements clicables que no responen a Enter o Space.
  • Focus invisible o poc clar.

Prova 2: Lector de pantalla bàsic

macOS (VoiceOver):

  1. Activeu VoiceOver: Cmd + F5
  2. Navegueu amb Tab pel formulari.
  3. Escolteu els anuncis: "Títol de l'element, camp d'edició requerit, Useu un títol descriptiu..."
  4. Ompliu un camp incorrectament i sortiu amb Tab.
  5. Verifiqueu que escolteu: "Indiqueu el títol de l'element."
  6. Desactiveu VoiceOver: Cmd + F5

Windows (NVDA - gratuït):

  1. Descarregueu NVDA: https://www.nvaccess.org/download/
  2. Instal·leu-lo i activeu-lo: Ctrl + Alt + N
  3. Navegueu amb Tab pel formulari.
  4. Escolteu els anuncis similars als de VoiceOver.
  5. Desactiveu NVDA: Insert + Q

Què buscar:

  • Cada camp anuncia: nom (label), tipus (camp d'edició), estat (requerit), ajuda.
  • Els errors s'anuncien quan apareixen.
  • El lector anuncia "invàlid" quan hi ha errors (aria-invalid="true").
  • Anunci "camp d'edició, buit" sense nom.
  • Errors no anunciats.
  • Ajudes no anunciades.

Prova 3: Eines automàtiques (complementàries)

Lighthouse (Chrome DevTools):

  1. Obriu DevTools: F12
  2. Aneu a la pestanya "Lighthouse"
  3. Seleccioneu "Accessibility" i "Desktop"
  4. Premeu "Generate report"
  5. Reviseu els errors detectats (labels sense for, contrast baix, etc.)

axe DevTools (extensió):

  1. Instal·leu l'extensió axe DevTools al navegador
  2. Obriu DevTools → pestanya "axe DevTools"
  3. Premeu "Scan All of My Page"
  4. Reviseu els errors i advertències

Nota: aquestes eines detecten errors tècnics però no validen l'experiència d'usuari. Una etiqueta pot estar tècnicament correcta (<label for="camp">) però ser poc clara ("Camp 1" vs "Títol de l'element").

3.11. Resum de millors pràctiques d'accessibilitat

3.11.1. Objectiu

Consolidar els conceptes vistos amb una checklist de millors pràctiques reutilitzable per a futurs formularis.

3.11.2. Contingut

Després d'aplicar totes les tècniques d'accessibilitat, disposeu d'un patró reutilitzable per a qualsevol formulari del projecte. Aquestes són les 10 millors pràctiques essencials:

1. Etiquetes visibles sempre associades

Cada control té <label for="id"> amb l'id corresponent.
Mai utilitzeu només placeholders.

2. Agrupació semàntica

Utilitzeu <fieldset> + <legend> per agrupar controls relacionats.
No agrupeu només amb divs sense semàntica.

3. Ajudes vinculades

Textos d'ajuda vinculats amb aria-describedby="ajudaX".
Ajudes desconnectades que els lectors ignoren.

4. Errors anunciables

Missatges d'error amb role="alert" (i aria-live="polite" per a informació no urgent).
Errors només visuals (color vermell).

5. Estat invàlid comunicat

[attr.aria-invalid]="camp.invalid && camp.touched"
Estat invàlid no comunicat als lectors.

6. Ordre de tabulació natural

Respectar l'ordre del DOM, evitar tabindex positius.
Salts inesperats o ordre caòtic.

7. Focus sempre visible

Borde blau gruixut + box-shadow amb contrast ≥ 3:1.
outline: none; sense alternativa.

8. Missatges clars i breus

"Indiqueu el títol (4-60 caràcters)."
"Error!" o textos massa llargs.

3.17. Repàs de conceptes
Definició

Accessibilitat web: Garanteix que totes les persones puguin percebre, comprendre, navegar i interactuar amb una aplicació, independentment de les seves capacitats o tecnologies assistives.

Definició

Etiquetes semàntiques (<label>): Elements HTML que s'associen a controls (<input>, <select>, <textarea>) amb l'atribut for, anunciant el propòsit del camp als lectors de pantalla.

Definició

Atribut aria-describedby: Vincula ajudes textuals i missatges d'error a un control, garantint que els lectors de pantalla els anunciïn automàticament.

Definició

role="alert": Marca un element com a regió d'alerta urgent, fent que els lectors de pantalla l'anunciïn immediatament quan apareix.

Definició

aria-live: Controla com els lectors anuncien canvis dinàmics; "assertive" interromp immediatament, "polite" espera que l'usuari acabi la tasca.

Definició

aria-invalid: Indica que el valor d'un control és invàlid, anunciant "invàlid" als lectors de pantalla.

Definició

Focus visible: Indicador visual clar (borde + ombra) amb contrast ≥ 3:1 que mostra quin element està actiu durant la navegació amb teclat.

Definició

Ordre de tabulació: Seqüència en què el focus passa entre elements en prémer Tab; ha de seguir l'ordre visual del formulari (d'esquerra a dreta, de dalt a baix).

Definició

tabindex: Atribut que controla si un element és focusable i el seu ordre; utilitzeu "0" per elements personalitzats, "-1" per elements no tabulables, i eviteu valors positius.

Definició

<fieldset> + <legend>: Elements semàntics per agrupar controls relacionats amb un títol, proporcionant context addicional als lectors de pantalla.

Definició

Proves manuals d'accessibilitat: Navegació només amb teclat (Tab, Enter, Space) i proves amb lectors de pantalla (VoiceOver, NVDA) per validar l'experiència real d'usuaris amb diversitat funcional.

Definició

WCAG (Web Content Accessibility Guidelines): Estàndard internacional que defineix requisits d'accessibilitat; nivell AA és el requisit legal per a organismes públics i empreses grans.
