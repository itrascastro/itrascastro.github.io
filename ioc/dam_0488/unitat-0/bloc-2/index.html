1. Classes i objectes: representar dades

Fins ara hem treballat amb variables separades: un text per al nom, un decimal per al preu i un enter per a les unitats. Aquesta tècnica és útil quan el programa és petit, però aviat costa saber quines dades formen part del mateix element.

Una classe ens permet descriure un tipus propi. Un objecte és una instància concreta d'aquesta classe. La classe diu quines dades i quines operacions pot tenir; l'objecte conserva els valors d'un cas real.

Figura

Del grup de variables al model

En lloc de mantenir tres variables desconnectades, podem descriure un producte amb una classe:

CSHARP Producte.cs 
public class Producte
{
    public string Nom { get; set; } = "";
    public decimal Preu { get; set; }
    public int Unitats { get; set; }
}

Ara Producte és un tipus que el programa pot utilitzar igual que utilitza string o decimal. Les tres propietats descriuen l'estat d'un producte, però encara no hi ha cap producte concret creat.

Crear objectes amb new

Per crear una instància fem servir new. Cada objecte té els seus propis valors, encara que tots provenen de la mateixa classe:

CSHARP Programa.cs 
Producte teclat = new Producte
{
    Nom = "Teclat",
    Preu = 24.90m,
    Unitats = 12
};

Producte ratoli = new Producte
{
    Nom = "Ratolí",
    Preu = 14.50m,
    Unitats = 20
};

teclat i ratoli són dos objectes diferents. Canviar teclat.Unitats no modifica les unitats de ratoli. La classe és compartida; l'estat és propi de cada objecte.

Comportament dins de la classe

Una classe no només agrupa dades. També pot contenir operacions que tenen sentit per a l'objecte. Això permet mantenir una regla a prop de les dades que utilitza:

CSHARP Producte.cs 
public class Producte
{
    public string Nom { get; set; } = "";
    public decimal Preu { get; private set; }

    public void CanviaPreu(decimal nouPreu)
    {
        if (nouPreu < 0)
        {
            throw new ArgumentOutOfRangeException(nameof(nouPreu));
        }

        Preu = nouPreu;
    }
}

La propietat Preu pot consultar-se des de fora, però només es modifica mitjançant CanviaPreu. No cal aplicar encapsulació completa a totes les dades des del primer exercici, però sí entendre que una classe pot protegir les seves regles.

Figura

El constructor com a punt de partida

Quan un objecte necessita dades obligatòries per existir, podem expressar-ho amb un constructor. Així evitem crear objectes incomplets sense adonar-nos-en:

CSHARP Producte.cs 
public class Producte
{
    public string Nom { get; }
    public decimal Preu { get; private set; }

    public Producte(string nom, decimal preu)
    {
        if (string.IsNullOrWhiteSpace(nom) || preu < 0)
        {
            throw new ArgumentException("Dades del producte no vàlides.");
        }

        Nom = nom.Trim();
        Preu = preu;
    }
}

En exemples petits també és correcte utilitzar l'inicialitzador d'objectes. La decisió depèn de si el model necessita obligar a complir una regla abans de poder-se crear.

Objectes dins de col·leccions

Quan tenim més d'un producte, els guardem en una col·lecció. La llista conté objectes, no només textos o nombres:

CSHARP Programa.cs 
List<Producte> productes = new()
{
    new Producte("Teclat", 24.90m),
    new Producte("Ratolí", 14.50m)
};

A partir d'aquesta llista, el formulari podrà mostrar una graella, cercar un objecte o editar-ne un. Aquest és el pont que utilitzarem a les seccions següents.

2. Diverses finestres i responsabilitats separades

Una aplicació real rarament cap en una sola finestra. Podem tenir una pantalla principal, una finestra per editar un producte i una altra per consultar-ne el detall. Crear més d'un formulari és fàcil; el repte és fer que cada finestra tingui una responsabilitat clara.

La finestra principal coordina la navegació i mostra informació general. Una finestra secundària se centra en una tasca concreta. Les dades i les regles no haurien de quedar repartides arbitràriament entre els botons.

Figura

Crear una segona finestra

Des de l'Explorador de solucions, afegeix un nou element de tipus Windows Forms i posa-li un nom que expliqui la seva funció, per exemple ProductesForm. El nom és important: quan el projecte creixi, permetrà trobar la finestra sense haver d'obrir tots els fitxers.

La finestra principal pot obrir-la quan l'usuari prem un botó. Per començar, utilitzarem una finestra modal: l'usuari treballa amb la finestra secundària i torna a la principal quan la tanca.

CSHARP Form1.cs 
private void btnProductes_Click(object? sender, EventArgs e)
{
    using var finestra = new ProductesForm();
    finestra.ShowDialog(this);
}

ShowDialog no és només una altra manera d'escriure Show. Indica que la finestra secundària és una conversa que s'ha de completar abans de continuar amb la principal. Per a pantalles independents, més endavant podrem estudiar una finestra no modal amb Show.

Comunicació entre formularis

Obrir una finestra no vol dir que la finestra principal hagi de manipular-ne tots els controls. La comunicació ha de passar per una dada o una operació explícita.

Per exemple, una finestra d'edició pot retornar el producte seleccionat quan l'usuari prem Accepta:

CSHARP ProductesForm.cs 
public Producte? ProducteResultat { get; private set; }

private void btnAccepta_Click(object? sender, EventArgs e)
{
    string nom = txtNom.Text.Trim();

    if (string.IsNullOrWhiteSpace(nom))
    {
        MessageBox.Show("Escriu el nom del producte.");
        return;
    }

    ProducteResultat = new Producte { Nom = nom };
    DialogResult = DialogResult.OK;
}

La finestra principal només necessita saber si el diàleg s'ha acceptat i quina dada ha retornat:

CSHARP Form1.cs 
using var finestra = new ProductesForm();

if (finestra.ShowDialog(this) == DialogResult.OK &&
    finestra.ProducteResultat is Producte producte)
{
    lblResultat.Text = $"Producte: {producte.Nom}";
}

Aquest patró evita que Form1 busqui directament un TextBox d'una altra finestra. La finestra secundària sap recollir i validar la seva informació; la principal decideix què fer amb el resultat.

3. Llistes, DataGridView i filtres

Quan una aplicació deixa de treballar amb un sol producte, necessitem una col·lecció. Una llista ens permet guardar diversos objectes del mateix tipus i recórrer-los per mostrar-los, cercar-los o modificar-los.

En aquesta secció farem una primera aplicació de gestió en memòria: una finestra mostrarà productes en un DataGridView i un quadre de text permetrà filtrar-los. Encara no desarem res en fitxers ni en una base de dades; primer hem d'entendre el circuit de dades.

Figura

Una llista de productes

Partim del model Producte de la secció anterior i creem una llista inicial. Cada element és un objecte independent, però tots comparteixen el mateix tipus.

CSHARP ProductesForm.cs 
private readonly List<Producte> productes = new()
{
    new Producte { Nom = "Teclat", Preu = 24.90m },
    new Producte { Nom = "Ratolí", Preu = 14.50m },
    new Producte { Nom = "Pantalla", Preu = 189.00m }
};

La llista és la font de dades. El formulari no hauria de mantenir tres variables separades ni escriure una fila a mà per cada producte: això duplicaria informació i faria difícil afegir-ne un de nou.

Mostrar la llista en una graella

Al dissenyador, afegeix un DataGridView amb el nom dgvProductes. El mètode següent connecta la llista amb la graella. Per a una aplicació petita és una solució fàcil de seguir: cada vegada que canvia el filtre, reconstruïm la vista amb els elements que corresponen.

CSHARP ProductesForm.cs 
private void RefrescaGraella(IEnumerable<Producte> origen)
{
    dgvProductes.DataSource = null;
    dgvProductes.DataSource = origen.ToList();
}

Crida RefrescaGraella(productes) després de InitializeComponent() o quan el formulari ja estigui preparat. La graella mostrarà les propietats públiques del model com a columnes.

Informació

Aquesta primera tècnica prioritza que entenguis el recorregut de la dada. Quan el projecte tingui més volum, estudiarem BindingSource, notificacions de canvi i configuració explícita de columnes.

Cercar sense destruir la llista original

Un filtre no ha d'eliminar productes de la llista. Ha de construir una vista temporal amb els que compleixen la condició i tornar a pintar la graella.

Figura

Afegeix un TextBox anomenat txtCerca i associa el seu esdeveniment TextChanged amb aquest mètode:

CSHARP ProductesForm.cs 
private void txtCerca_TextChanged(object? sender, EventArgs e)
{
    string text = txtCerca.Text.Trim();

    IEnumerable<Producte> resultat = productes;

    if (text.Length > 0)
    {
        resultat = productes.Where(producte =>
            producte.Nom.Contains(text, StringComparison.OrdinalIgnoreCase));
    }

    RefrescaGraella(resultat);
}

Quan el quadre és buit, mostrem tota la llista. Quan conté text, només mostrem els noms que el contenen. El mètode no coneix cap botó ni cap posició de la graella: només aplica una regla de selecció.

Afegir un producte i actualitzar la vista

Per afegir un producte, llegeix els controls, valida les dades, crea l'objecte i incorpora'l a la llista. Després torna a aplicar el filtre actual perquè el producte aparegui només si correspon.

CSHARP ProductesForm.cs 
private void btnAfegeix_Click(object? sender, EventArgs e)
{
    string nom = txtNom.Text.Trim();

    if (!decimal.TryParse(txtPreu.Text, out decimal preu) ||
        string.IsNullOrWhiteSpace(nom))
    {
        MessageBox.Show("Indica un nom i un preu vàlid.");
        return;
    }

    productes.Add(new Producte { Nom = nom, Preu = preu });
    txtNom.Clear();
    txtPreu.Clear();
    RefrescaGraella(productes);
}

En aquest primer exemple, el botó actualitza tota la graella. És una decisió conscient: preferim un flux fàcil de seguir abans d'introduir mecanismes de notificació més avançats.

Més endavant separarem la consulta de la persistència i veurem com conservar el catàleg fora de la memòria del programa. Un filtre pot preparar dades per exportar-les, però exportar no és el mateix que desar l'estat de l'aplicació.

4. CRUD: afegir, consultar, editar i eliminar

Una pantalla que només mostra dades encara no és una aplicació de gestió. El cicle CRUD resumeix les quatre operacions que apareixen una vegada i una altra:

OperacióQuè vol dirExemple al catàleg
CreateCrear una dada nova.Afegir un producte.
ReadConsultar dades existents.Mostrar els productes a la graella.
UpdateModificar una dada existent.Canviar el preu d'un producte.
DeleteEliminar una dada.Treure un producte del catàleg.
Figura

La regla més important és l'ordre: primer llegim i validem les dades del formulari; només després modifiquem la llista. Si la validació falla, la dada original no s'ha de tocar.

Compartir la validació

Afegir i editar necessiten validar el mateix nom i el mateix preu. Per no duplicar codi, extraurem aquesta lectura a un mètode:

CSHARP ProductesForm.cs 
private bool IntentaLlegirProducte(
    out string nom,
    out decimal preu)
{
    nom = txtNom.Text.Trim();

    if (string.IsNullOrWhiteSpace(nom) ||
        !decimal.TryParse(txtPreu.Text, out preu) ||
        preu < 0)
    {
        MessageBox.Show("Indica un nom i un preu vàlid.");
        return false;
    }

    return true;
}
Figura

El mètode retorna false quan la dada no és vàlida i deixa preparada una resposta per a l'usuari. Els handlers poden sortir immediatament i concentrar-se en l'operació CRUD.

Afegir i consultar

La consulta ja la tenim resolta amb RefrescaGraella. Per afegir, creem un objecte nou només després que la validació hagi funcionat:

CSHARP ProductesForm.cs 
private void btnAfegeix_Click(object? sender, EventArgs e)
{
    if (!IntentaLlegirProducte(out string nom, out decimal preu))
    {
        return;
    }

    productes.Add(new Producte { Nom = nom, Preu = preu });
    RefrescaGraella(productes);
    NetejaFormulari();
}

Després de l'alta, refresquem la graella i deixem el formulari preparat per a una nova operació. El mètode de neteja també és una petita responsabilitat reutilitzable:

CSHARP ProductesForm.cs 
private void NetejaFormulari()
{
    txtNom.Clear();
    txtPreu.Clear();
    txtNom.Focus();
}

Seleccionar i editar

Per editar, necessitem saber quin producte ha seleccionat l'usuari. Quan canvia la fila activa, copiem les dades de l'objecte als controls del formulari:

CSHARP ProductesForm.cs 
private Producte? producteSeleccionat;

private void dgvProductes_SelectionChanged(object? sender, EventArgs e)
{
    if (dgvProductes.CurrentRow?.DataBoundItem is not Producte producte)
    {
        producteSeleccionat = null;
        return;
    }

    producteSeleccionat = producte;
    txtNom.Text = producte.Nom;
    txtPreu.Text = producte.Preu.ToString();
}

El botó d'edició reutilitza la mateixa validació. Si no hi ha cap fila seleccionada, no hi ha cap objecte que es pugui modificar.

CSHARP ProductesForm.cs 
private void btnEdita_Click(object? sender, EventArgs e)
{
    if (producteSeleccionat is null ||
        !IntentaLlegirProducte(out string nom, out decimal preu))
    {
        return;
    }

    producteSeleccionat.Nom = nom;
    producteSeleccionat.Preu = preu;
    RefrescaGraella(productes);
}

Eliminar amb una confirmació

Eliminar és una operació diferent d'amagar una fila amb un filtre. Treu l'objecte de la font de dades i demana confirmació abans de fer-ho:

CSHARP ProductesForm.cs 
private void btnElimina_Click(object? sender, EventArgs e)
{
    if (producteSeleccionat is null)
    {
        return;
    }

    DialogResult resposta = MessageBox.Show(
        $"Vols eliminar {producteSeleccionat.Nom}?",
        "Confirmar eliminació",
        MessageBoxButtons.YesNo);

    if (resposta != DialogResult.Yes)
    {
        return;
    }

    productes.Remove(producteSeleccionat);
    producteSeleccionat = null;
    RefrescaGraella(productes);
    NetejaFormulari();
}

La confirmació no substitueix la validació, però evita una eliminació accidental. Quan treballem amb dades reals, aquesta decisió és encara més important.

Un circuit CRUD que es pugui repetir

  1. L'usuari escriu o selecciona una dada.
  2. El formulari valida els camps necessaris.
  3. El codi executa una única operació sobre la llista.
  4. La vista es refresca i torna a mostrar l'estat actual.
  5. El formulari queda preparat per a la següent operació.

Aquesta seqüència és més important que copiar cada handler. Si l'entens, podràs adaptar-la a alumnes, llibres, comandes o qualsevol altra dada amb una estructura semblant.

Èxit

Una pantalla CRUD està ben encaminada quan una entrada incorrecta no canvia dades, una edició afecta l'objecte seleccionat i una eliminació només passa després de confirmar-la.
