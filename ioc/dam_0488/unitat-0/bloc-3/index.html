1. Persistència: guardar i recuperar dades

Fins ara el catàleg viu només mentre l'aplicació està oberta. Quan tanquem la finestra, la llista desapareix perquè estava guardada a la memòria del procés. La persistència consisteix a conservar les dades en un suport que puguem tornar a llegir més endavant.

Abans d'escriure codi, distingim dues responsabilitats:

  • la interfície decideix quan cal carregar o desar;
  • la persistència sap en quin format i en quin fitxer es guarden les dades.
Figura

Triar un format amb criteri

FormatQuan és útilLimitació principal
JSONGuardar l'estat d'una col·lecció d'objectes i recuperar-lo mantenint la seva estructura.Cal controlar els errors de lectura i el contingut que s'hi desa.
CSVIntercanviar dades amb un full de càlcul o una altra eina.Les files i columnes no expressen bé les relacions ni els objectes complexos.
Base de dadesTreballar amb moltes dades, cerques i concurrència.Requereix una infraestructura i decisions que encara no necessitem.

Per conservar el nostre catàleg començarem amb JSON. CSV quedarà com a format d'exportació, no com una excusa per posar tota la lectura i l'escriptura dins del formulari.

Un repositori petit per a Producte

Un repositori és una classe que encapsula com es guarden i es recuperen les dades. La resta de l'aplicació pot treballar amb una llista sense conèixer si el suport és JSON, CSV o una base de dades.

CSHARP ProducteRepository.cs 
using System.Text.Json;

public sealed class ProducteRepository
{
    private readonly string path;

    public ProducteRepository(string path)
    {
        this.path = path;
    }

    public void Save(IReadOnlyCollection<Producte> productes)
    {
        string json = JsonSerializer.Serialize(
            productes,
            new JsonSerializerOptions { WriteIndented = true });

        File.WriteAllText(path, json);
    }

    public List<Producte> Load()
    {
        if (!File.Exists(path))
        {
            return new List<Producte>();
        }

        string json = File.ReadAllText(path);
        return JsonSerializer.Deserialize<List<Producte>>(json)
            ?? new List<Producte>();
    }
}

El repositori no sap res de botons, etiquetes ni graelles. Només rep objectes i els transforma en text o torna a convertir el text en objectes.

Connectar la persistència amb el formulari

El formulari pot tenir un repositori i utilitzar-lo en els moments adequats. El camí del fitxer és una decisió de configuració; no s'ha d'escampar per tots els handlers.

CSHARP ProductesForm.cs 
private readonly ProducteRepository repositori = new(
    Path.Combine(AppContext.BaseDirectory, "dades", "productes.json"));

private List<Producte> productes = new();

private void Form1_Load(object? sender, EventArgs e)
{
    productes = repositori.Load();
    RefrescaGraella(productes);
}

private void btnDesa_Click(object? sender, EventArgs e)
{
    repositori.Save(productes);
    MessageBox.Show("Dades desades.");
}

El flux és fàcil de seguir: en carregar, llegim; després de modificar, desem. La pantalla continua sent responsable de coordinar l'experiència, però el repositori concentra l'accés al fitxer.

Errors que cal tractar

Un fitxer pot no existir, estar bloquejat o contenir un JSON mal format. No hem de convertir aquests casos en una llista buida silenciosament: podríem ocultar una pèrdua de dades.

CSHARP ProductesForm.cs 
private List<Producte> CarregaAmbMissatge()
{
    try
    {
        return repositori.Load();
    }
    catch (IOException)
    {
        MessageBox.Show("No s'han pogut llegir les dades.");
    }
    catch (JsonException)
    {
        MessageBox.Show("El fitxer de dades no té un format vàlid.");
    }

    return new List<Producte>();
}

En una aplicació real també hauríem de registrar l'error i oferir una recuperació segura. En aquest bloc ens centrarem a no confondre una incidència de persistència amb un catàleg legítimament buit.

CSV per exportar, no per amagar decisions

Si volem enviar el catàleg a un full de càlcul, podem generar un CSV, però primer hem de decidir l'ordre de les columnes, el separador, l'escapament dels textos i el format dels decimals. Un CSV sense aquestes decisions pot obrir-se diferent segons l'eina.

La regla pràctica és:

  1. JSON per conservar l'estat de l'aplicació;
  2. CSV per intercanviar una taula amb altres eines;
  3. un repositori separat per poder canviar de format sense reescriure els formularis.
Èxit

Si pots tancar i tornar a obrir l'aplicació recuperant els mateixos productes, i si el formulari no conté codi de serialització, ja has separat correctament la interfície de la persistència.

Pràctica guiada: catàleg persistent

Incorpora un repositori JSON al catàleg CRUD. Carrega les dades quan s'obre el formulari, desa-les després d'una alta, edició o eliminació i mostra un missatge comprensible si el fitxer no es pot llegir.

2. Instal·lar i preparar PostgreSQL

Abans de connectar una aplicació, cal tenir clar què estem instal·lant. PostgreSQL és el servidor de base de dades; pgAdmin és una eina gràfica per administrar-lo; psql és el client de línia d'ordres. No són tres bases de dades diferents.

Aquesta preparació és per a desenvolupament local. No és una guia per muntar un servidor públic ni per exposar PostgreSQL a Internet.

Figura

Escollir la instal·lació

Per començar, utilitza l'instal·lador oficial del sistema operatiu i selecciona les eines que necessitarem:

  1. el servidor PostgreSQL;
  2. pgAdmin, si vols treballar amb una interfície gràfica;
  3. les eines de línia d'ordres, inclòs psql;
  4. la documentació local, si l'instal·lador l'ofereix.

Tria una versió actual i compatible amb l'entorn del curs, però no escriguis el número de versió dins dels exemples. El material ha de continuar sent útil quan canviï la versió del servidor.

Comprovar que el servidor està actiu

Obre pgAdmin i comprova que el servidor local apareix registrat. Si prefereixes la terminal, executa psql --version per verificar que el client està disponible. Aquest comandament només mostra la versió instal·lada; encara no prova que el servidor accepti connexions.

Per provar la connexió, utilitza el client amb el servidor local i el compte de desenvolupament. No incloguis la contrasenya en l'historial de comandaments si la terminal ofereix un mecanisme segur per demanar-la.

TEXT Terminal 
psql \
  --host localhost \
  --port 5432 \
  --username usuari_local \
  --dbname postgres

El port de l'exemple és el habitual. Si durant la instal·lació n'has triat un altre, utilitza el que aparegui a la configuració local. No canviïs el port a cegues per solucionar un error: primer comprova quin procés l'està utilitzant.

Crear una base de dades de pràctiques

No treballarem directament sobre la base de dades administrativa. Crea una base pròpia per al projecte i reserva el compte administrador per a tasques de preparació:

Configurar la cadena de connexió només en local

La nostra aplicació llegirà la cadena de connexió de la variable DAM0488_DB_CONNECTION. Així el codi pot ser compartit sense incloure contrasenyes:

3. Persistència real amb PostgreSQL

Un fitxer és suficient per començar, però una aplicació que creix necessita consultar, filtrar i actualitzar dades amb garanties. PostgreSQL ens permet veure el mateix catàleg com una base de dades real, sense canviar la idea principal: el formulari coordina, el repositori parla amb l'emmagatzematge.

No començarem connectant directament un botó a una base de dades. Primer definirem l'estructura, després la configuració i finalment el repositori. Cada pas té una responsabilitat que es pot provar per separat.

Figura

Definir la taula abans d'escriure consultes

Una taula de productes necessita una identitat estable i regles bàsiques. Les restriccions de la base de dades són una segona línia de defensa: la interfície valida per ajudar l'usuari, però la base també ha de protegir les dades.

SQL schema.sql 
CREATE TABLE productes (
    id integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    nom text NOT NULL,
    preu numeric(10, 2) NOT NULL CHECK (preu >= 0),
    unitats integer NOT NULL CHECK (unitats >= 0)
);
ColumnaDecisióMotiu
idIdentitat generada i clau primària.Permet distingir dos productes amb el mateix nom.
nomNOT NULL.Un producte sense nom no és útil per al catàleg.
preuDecimal amb dos decimals i no negatiu.Evita representar diners amb double i rebutja valors impossibles.
unitatsEnter no negatiu.La base reforça la regla que ja valida el formulari.

Per relacionar el model amb aquesta taula, afegirem una propietat Id al Producte. L'identificador el proporciona PostgreSQL en crear la fila; el nom, el preu i les unitats formen la resta de l'estat que editem des de l'aplicació.

CSHARP Producte.cs 
public int Id { get; set; }
public string Nom { get; set; } = "";
public decimal Preu { get; set; }
public int Unitats { get; set; }

La cadena de connexió no s'ha d'escriure dins de Form1.cs ni publicar-se al repositori. En desenvolupament la podem llegir d'una variable d'entorn o d'un fitxer local ignorat pel control de versions.

Durant la pràctica pots utilitzar un valor local amb el teu servidor de desenvolupament, però no el copiïs a un exemple compartit. El material només ha d'ensenyar el nom de la configuració, no una contrasenya real.

Un repositori amb consultes parametrizades

El paquet Npgsql és el client de .NET per a PostgreSQL. El formulari no ha de conèixer-lo: el repositori obre la connexió, executa una consulta i transforma el resultat en objectes Producte.

CSHARP ProducteDbRepository.cs 
using Npgsql;

public sealed class ProducteDbRepository
{
    private readonly string connectionString;

    public ProducteDbRepository(string connectionString)
    {
        this.connectionString = connectionString;
    }

    public List<Producte> GetAll()
    {
        const string sql = """
            SELECT id, nom, preu, unitats
            FROM productes
            ORDER BY nom;
            """;

        using var connection = new NpgsqlConnection(connectionString);
        connection.Open();

        using var command = new NpgsqlCommand(sql, connection);
        using NpgsqlDataReader reader = command.ExecuteReader();

        var resultat = new List<Producte>();

        while (reader.Read())
        {
            resultat.Add(new Producte
            {
                Id = reader.GetInt32(0),
                Nom = reader.GetString(1),
                Preu = reader.GetDecimal(2),
                Unitats = reader.GetInt32(3)
            });
        }

        return resultat;
    }
}

La consulta no concatena valors introduïts per l'usuari. Quan una operació necessiti dades, les afegirem com a paràmetres:

CSHARP ProducteDbRepository.cs 
public void Add(Producte producte)
{
    const string sql = """
        INSERT INTO productes (nom, preu, unitats)
        VALUES (@nom, @preu, @unitats);
        """;

    using var connection = new NpgsqlConnection(connectionString);
    connection.Open();

    using var command = new NpgsqlCommand(sql, connection);
    command.Parameters.AddWithValue("nom", producte.Nom);
    command.Parameters.AddWithValue("preu", producte.Preu);
    command.Parameters.AddWithValue("unitats", producte.Unitats);
    command.ExecuteNonQuery();
}
Important

No construeixis SQL amb interpolació de cadenes. Les consultes parametritzades protegeixen les dades i deixen clar quins valors formen part de l'operació.

Completar el CRUD de la base de dades

Les operacions d'edició i eliminació segueixen el mateix patró, però sempre han d'identificar l'objecte per la seva clau id, no pel nom. El nom pot repetir-se; l'identificador no.

CSHARP ProducteDbRepository.cs 
public void Update(Producte producte)
{
    const string sql = """
        UPDATE productes
        SET nom = @nom, preu = @preu, unitats = @unitats
        WHERE id = @id;
        """;

    ExecuteProducteCommand(sql, producte);
}

public void Delete(int id)
{
    const string sql = "DELETE FROM productes WHERE id = @id;";

    using var connection = new NpgsqlConnection(connectionString);
    connection.Open();
    using var command = new NpgsqlCommand(sql, connection);
    command.Parameters.AddWithValue("id", id);
    command.ExecuteNonQuery();
}

Per evitar repetir la preparació d'un UPDATE, el repositori pot extreure un mètode privat com ExecuteProducteCommand:

CSHARP ProducteDbRepository.cs 
private void ExecuteProducteCommand(
    string sql,
    Producte producte)
{
    using var connection = new NpgsqlConnection(connectionString);
    connection.Open();

    using var command = new NpgsqlCommand(sql, connection);
    command.Parameters.AddWithValue("id", producte.Id);
    command.Parameters.AddWithValue("nom", producte.Nom);
    command.Parameters.AddWithValue("preu", producte.Preu);
    command.Parameters.AddWithValue("unitats", producte.Unitats);
    command.ExecuteNonQuery();
}

La idea important no és memoritzar cada línia, sinó identificar quina part és infraestructura i quina part és la regla de l'operació.

Gestionar connexions i errors

Una base de dades pot estar aturada, la taula pot no existir o la xarxa local pot fallar. El formulari ha de rebre un error comprensible; no ha de mostrar una excepció tècnica completa ni continuar com si no hagués passat res.

  • obre i tanca les connexions amb using;
  • no mantinguis una connexió oberta durant tota la vida del formulari;
  • captura els errors al límit adequat i conserva el detall tècnic al registre de desenvolupament;
  • després d'un write, torna a llegir o verifica el resultat abans d'informar que ha funcionat.

Pràctica guiada: catàleg amb PostgreSQL

4. Executar, depurar i verificar el catàleg

Ja tenim les peces del mateix projecte: un model Producte, una interfície Windows Forms, una col·lecció que alimenta la graella i dos repositoris possibles. Ara cal executar-les en ordre i comprovar que les dades recorren el circuit complet. Aquesta verificació és part del desenvolupament, no una tasca opcional per al final.

Figura

El circuit que hem de poder seguir

Quan l'usuari desa un producte, no hauria d'haver-hi un salt misteriós entre el botó i la base de dades. El recorregut és aquest:

  1. el controlador de l'esdeveniment llegeix els controls i valida els valors;
  2. crea o actualitza un objecte Producte;
  3. la lògica de l'aplicació demana al repositori que el desi;
  4. el repositori escriu en JSON o PostgreSQL segons la configuració;
  5. la pantalla torna a carregar la col·lecció i actualitza el DataGridView.

Si una dada no arriba al pas següent, el depurador ens ha de permetre descobrir en quin punt s'ha perdut. Per això no posarem tota la lògica dins del Click: cada responsabilitat ha de tenir un lloc observable.

Posar un punt d'aturada útil

Comença pel handler que confirma l'alta o l'edició. Posa-hi un punt d'aturada just després de construir el producte i inicia l'aplicació en mode de depuració. Quan el programa s'aturi, comprova:

  • que Nom no és buit i conserva el text esperat;
  • que Preu és un decimal i no un text sense validar;
  • que Unitats és un enter no negatiu;
  • que l'identificador es conserva quan edites una fila existent;
  • que el repositori que s'està executant és el que has configurat.

Avança pas a pas fins a la crida a Save, Add o Update. Si el valor és correcte abans de la crida i incorrecte després, l'error està al repositori o a l'esquema. Si ja arriba malament al repositori, torna al formulari i a la validació.

Una mateixa pantalla, dos repositoris

La pantalla no ha de canviar per passar de JSON a PostgreSQL. El que canvia és la implementació que rep la responsabilitat de persistir les dades. Una interfície petita fa explícit aquest contracte:

CSHARP IProducteRepository.cs 
public interface IProducteRepository
{
    List<Producte> Load();
    void Save(IReadOnlyCollection<Producte> productes);
}

El repositori JSON i el repositori PostgreSQL poden implementar el mateix contracte. El formulari només necessita una referència a IProducteRepository; no ha de saber si darrere hi ha un fitxer o una connexió.

CSHARP ProductesForm.cs 
private readonly IProducteRepository repositori;

public ProductesForm(IProducteRepository repositori)
{
    InitializeComponent();
    this.repositori = repositori;
}

Per a la pràctica, pots iniciar el formulari amb el repositori JSON i, quan aquest flux funcioni, substituir-lo pel de PostgreSQL. Si has de modificar handlers de botons per fer el canvi, encara hi ha detalls de persistència barrejats amb la interfície.

Prova mínima reproduïble

Executa la mateixa seqüència cada vegada que canviïs el model, el formulari o el repositori. Anota el resultat abans de donar la funcionalitat per acabada:

PasAccióResultat esperat
1Obre l'aplicació sense dades prèvies.La graella es mostra buida i no hi ha cap error.
2Afegeix un producte vàlid.La fila apareix amb els valors introduïts.
3Tanca i torna a obrir.El producte continua disponible.
4Edita només el preu i desa.La mateixa fila conserva el seu identificador i el nou preu.
5Intenta desar un preu o unes unitats invàlides.La validació atura l'operació i no corromp les dades.

Quan una prova falla

No tapis el problema retornant una llista buida o mostrant sempre «Desat correctament». Conserva el missatge tècnic per al depurador, informa l'usuari amb un missatge útil i torna a l'últim punt en què les dades eren correctes.

  • si falla només el primer arrencada, comprova el fitxer o l'esquema inicial;
  • si falla l'edició, comprova que no hagis perdut l'Id;
  • si falla PostgreSQL però funciona JSON, revisa la cadena de connexió i la taula;
  • si la graella mostra dades antigues, comprova quan la tornes a carregar després d'un write.
Èxit

El circuit està verificat quan pots seguir una alta, una edició i una eliminació amb el depurador, recuperar les dades després de reiniciar i distingir un error de validació d'un error de persistència.

Pràctica guiada: prova abans de continuar

Repeteix la prova mínima amb el repositori JSON i després amb PostgreSQL. Per a cada pas, anota quin objecte rep el formulari, quin mètode del repositori s'executa i quin resultat es mostra a la graella. Inclou una prova amb dades invàlides i una amb el servidor de base de dades aturat.

5. Errors habituals i recuperació

Una aplicació de dades no es considera acabada perquè funcioni quan tot va bé. També ha de deixar clar què ha fallat, evitar perdre informació i permetre tornar a un estat conegut. En aquest projecte distingirem tres situacions: les dades introduïdes no són vàlides, el suport no està disponible o el suport conté dades que no podem interpretar.

Figura

No confondre un error amb una llista buida

Si el fitxer JSON no existeix en el primer arrencada, una llista buida és correcta. Si el fitxer existeix però està mal format, retornar una llista buida amaga un problema i pot provocar que l'usuari desi damunt de les dades anteriors. El repositori ha de diferenciar els dos casos:

CSHARP ProducteRepository.cs 
public List<Producte> Load()
{
    if (!File.Exists(path))
    {
        return new List<Producte>();
    }

    string json = File.ReadAllText(path);
    List<Producte>? productes = JsonSerializer.Deserialize<List<Producte>>(json);

    return productes
        ?? throw new InvalidDataException("El fitxer no conté una llista vàlida.");
}

La pantalla pot capturar l'error i mostrar una instrucció concreta: conservar el fitxer original, revisar-lo o recuperar una còpia. No ha d'esborrar-lo automàticament ni substituir-lo per una llista buida.

Desar sense deixar un fitxer a mig escriure

Un tancament inesperat mentre escrivim pot deixar un JSON incomplet. Una estratègia senzilla és escriure primer en un fitxer temporal i substituir el fitxer definitiu només quan l'escriptura ha acabat:

CSHARP ProducteRepository.cs 
public void Save(IReadOnlyCollection<Producte> productes)
{
    string temporal = path + ".tmp";
    string json = JsonSerializer.Serialize(
        productes,
        new JsonSerializerOptions { WriteIndented = true });

    File.WriteAllText(temporal, json);
    File.Move(temporal, path, overwrite: true);
}

Aquesta tècnica no substitueix una còpia de seguretat, però redueix el risc de deixar el fitxer principal a mig construir. Si el programa falla, el fitxer temporal s'ha de revisar i netejar en un moment controlat; no s'ha de carregar com si fos la font oficial sense comprovar-lo.

Quan PostgreSQL no respon

Un error de connexió no és el mateix que una validació incorrecta. El formulari pot informar que no s'ha pogut accedir a la base de dades, però no ha d'afirmar que l'alta, l'edició o l'eliminació s'han completat.

SímptomaComprovaResposta de l'aplicació
Connection refusedQue el servei estigui iniciat, el host sigui local i el port coincideixi.«No s'ha pogut connectar. Revisa el servidor local.»

Recuperar-se sense improvisar

Quan aparegui un error, segueix sempre el mateix ordre:

  1. atura l'operació que ha fallat i no la repeteixis a cegues;
  2. conserva el fitxer o les dades originals;
  3. anota si l'error és de validació, de connexió o de format;
  4. corregeix la causa i torna a executar la prova mínima;
  5. verifica després del write que el resultat real coincideix amb el que mostra la pantalla.

En PostgreSQL, una còpia de seguretat i un esquema versionat formen part del projecte quan les dades són importants. En aquesta unitat no muntarem encara un sistema de migracions, però sí que aprendrem a no canviar la taula manualment sense documentar-ho.

Important

No esborris el fitxer de dades ni recreïs la taula per fer desaparèixer un error. Primer conserva l'estat, identifica la causa i explica quina recuperació has aplicat.

Èxit

El projecte està preparat per créixer quan pots diferenciar un catàleg buit d'un fitxer corrupte, un error de validació d'un error de connexió i un write confirmat d'un write que ha fallat.

Pràctica guiada: provocar i recuperar errors

Prova el catàleg amb un fitxer JSON inexistent, un JSON mal format, una dada invàlida i PostgreSQL aturat. Per a cada cas, descriu què veu l'usuari, quin error conserva el depurador i quina acció de recuperació és segura.
