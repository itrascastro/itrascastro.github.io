1. El projecte d'exemple d'aquesta unitat

Aquesta unitat es construeix al voltant d'una petita aplicació de control per veu per a un taller mecànic, TallerVeu. Permet crear i tancar fitxes de reparació dient ordres en veu alta, i llegir en veu alta les reparacions pendents. Igual que a les altres unitats, no és el mateix exercici que es demanarà a l'activitat avaluable, però treballa exactament les mateixes tècniques: reconeixement de veu, síntesi de veu, distribució amb instal·lador, i un pla de proves real.

Informació

Què conté aquest projecte

Sis ordres de veu ("nova reparació", "marca acabada", "llegeix pendents", "atura la lectura", "ajuda", "surt"), un formulari amb una llista de reparacions i indicadors d'estat, un projecte de proves amb 6 proves automatitzades, un paquet de distribució amb instal·lador i README, i un pla de proves amb 8 casos.

Tot el codi d'aquesta unitat prové d'aquest projecte.

2. Interfícies naturals d'usuari: concepte i tipus

Una interfície natural d'usuari (NUI, Natural User Interface) és aquella en què la interacció es basa en habilitats humanes ja apreses (parlar, gesticular, tocar, moure's), en lloc de requerir aprendre l'ús d'un dispositiu intermediari com el ratolí o el teclat.

TipusExempleViabilitat en un entorn d'aula estàndard
Veu (reconeixement i síntesi)Ordres de veu, lectura d'avisos en veu altaAlta: només cal micròfon i altaveus, habituals en qualsevol ordinador.
Gest / tactePantalles tàctils, gestos multitouchMitjana: requereix maquinari tàctil, no sempre disponible.
Moviment del cosSensors de profunditat tipus KinectBaixa: maquinari específic i poc habitual fora d'entorns dedicats.
Realitat augmentadaSuperposar informació digital sobre la càmera en temps realBaixa: requereix maquinari i biblioteques especialitzades.

Per aquest motiu, en un context de formació general, la veu és la via d'interfície natural més pràctica: no depèn de maquinari especial i es pot implementar amb biblioteques incloses al mateix sistema operatiu.

3. Separar la lògica del reconeixement de veu

Abans d'entrar en el codi de reconeixement, convé prendre una decisió d'arquitectura important: que el reconeixement de veu no contingui cap lògica de negoci. El reconeixement només ha de fer una cosa: convertir un so en un text. Què es fa amb aquest text ha de ser responsabilitat d'una altra classe, completament independent de com s'ha obtingut el text.

CSHARP 
public class GestorReparacions
{
    private readonly List<Reparacio> reparacions = new();
    public IReadOnlyList<Reparacio> Reparacions => reparacions;

    public string ProcessaOrdre(string ordre)
    {
        switch (ordre.Trim().ToLowerInvariant())
        {
            case "nova reparació": return NovaReparacio();
            case "marca acabada": return MarcaAcabada();
            case "llegeix pendents": return TextPendents();
            case "surt": SortidaSollicitada = true; return "Vols sortir de l'aplicació?";
            default: return "Ordre no reconeguda.";
        }
    }
    // ...
}
Èxit

Concepte clau: per què separar-ho

GestorReparacions.ProcessaOrdre(string) no sap res de micròfons ni de System.Speech: rep un text i actua. Això vol dir que es pot escriure una prova unitària que cridi ProcessaOrdre("nova reparació") directament, sense necessitat de cap micròfon ni de dir res en veu alta. És exactament el mateix principi que separar la interfície visual de la lògica de negoci (Unitat 1): la part que depèn d'un recurs difícil de controlar en una prova automàtica (el micròfon) queda aïllada en una capa prima, i tota la resta es pot testejar de manera normal.

El formulari només s'encarrega de connectar les dues coses: quan el reconeixedor de veu detecta una frase, en passa el text a ProcessaOrdre, i mostra o llegeix en veu alta el resultat.

4. Reconeixement de veu a .NET

A Windows, l'espai de noms System.Speech.Recognition (paquet NuGet System.Speech a partir de .NET 5) permet implementar reconeixement de veu sense dependre de serveis externs. El seu funcionament es basa a definir una gramàtica: el conjunt exacte de paraules o frases que el sistema ha de reconèixer.

BASH 
dotnet add package System.Speech
CSHARP 
using System.Speech.Recognition;

reconeixedor = new SpeechRecognitionEngine();

var ordres = new Choices();
ordres.Add(new string[]
{
    "nova reparació", "marca acabada", "llegeix pendents",
    "atura la lectura", "ajuda", "surt"
});
reconeixedor.LoadGrammar(new Grammar(new GrammarBuilder(ordres)));
reconeixedor.SpeechRecognized += Reconeixedor_SpeechRecognized;

reconeixedor.SetInputToDefaultAudioDevice();
reconeixedor.RecognizeAsync(RecognizeMode.Multiple);
ElementFunció
ChoicesLlista de paraules o frases vàlides.
GrammarBuilder / GrammarConstrueix la gramàtica final que el motor de reconeixement carregarà.
SpeechRecognizedEsdeveniment que es dispara quan es reconeix alguna de les frases de la gramàtica.
RecognizeAsync(RecognizeMode.Multiple)Inicia l'escolta contínua (reconeix diverses vegades, no només un cop).
Informació

Per què usar una gramàtica tancada

Restringir el reconeixement a un conjunt conegut de paraules (en lloc de dictat lliure) millora molt la precisió i la fiabilitat, i és suficient per implementar ordres de control d'una aplicació.

L'esdeveniment SpeechRecognized es dispara en un fil diferent del de la interfície gràfica, així que cal passar per Invoke abans de tocar qualsevol control:

CSHARP 
private void Reconeixedor_SpeechRecognized(object? sender, SpeechRecognizedEventArgs e)
{
    string ordre = e.Result.Text;
    if (InvokeRequired)
        Invoke(new Action(() => ProcessaOrdreReconeguda(ordre)));
    else
        ProcessaOrdreReconeguda(ordre);
}
Important

Parany habitual: tocar la interfície des del fil equivocat

Si s'actualitza un Label o una ListBox directament dins de SpeechRecognized sense passar per Invoke, l'aplicació pot llançar una excepció de "operació no vàlida entre fils" de manera intermitent, difícil de reproduir perquè només falla quan l'esdeveniment arriba en un moment concret.
