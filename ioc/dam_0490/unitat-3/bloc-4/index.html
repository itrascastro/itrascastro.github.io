1. Clau simètrica i clau asimètrica

Fins ara hem utilitzat hashes i TLS com a eines. Ara mirarem una de les peces criptogràfiques que ens ajuda a entendre com es construeixen sistemes més complets: la criptografia asimètrica.

Clau simètrica

En un sistema simètric, la mateixa clau secreta permet xifrar i desxifrar. És molt eficient, però totes les parts que necessiten llegir les dades han de disposar del secret.

TEXT 
clau secreta K
                  |
missatge -> [ xifrar ] -> dades xifrades
                  |
             clau secreta K
                  |
          [ desxifrar ] -> missatge

Clau asimètrica

En un sistema asimètric hi ha dues claus matemàticament relacionades:

  • clau pública: es pot distribuir;
  • clau privada: l'ha de conservar només el propietari.
Figura

Per protegir confidencialitat amb RSA, el patró conceptual és:

TEXT 
Emissor:
  missatge + clau pública del receptor
           -> xifrat

Receptor:
  dades xifrades + clau privada pròpia
           -> missatge
AspecteSimètricaAsimètrica
ClausUn secret compartitParella pública + privada
VelocitatMolt altaMés costosa
DistribucióCal compartir el secret de forma seguraLa pública es pot distribuir
Ús habitualXifrar grans quantitats de dadesIntercanvi de claus, signatures, autenticació i dades petites

Un tast de criptografia simètrica amb AES

A Java, una clau simètrica es representa amb SecretKey. Aquest exemple només genera una clau AES; ja permet veure la diferència essencial amb RSA: aquí hi ha una sola clau secreta.

JAVA 
import javax.crypto.KeyGenerator;
import javax.crypto.SecretKey;

KeyGenerator generador =
        KeyGenerator.getInstance("AES");

generador.init(256);

SecretKey clau =
        generador.generateKey();

System.out.println(
        "Algorisme: " + clau.getAlgorithm()
);

Per xifrar dades reals amb AES no n'hi ha prou amb indicar l'algorisme: també cal triar correctament el mode i gestionar valors addicionals com un nonce o vector d'inicialització. En codi nou, un mode autenticat com AES/GCM/NoPadding és una opció habitual. El mode ECB, encara que aparegui en exemples antics perquè és simple, revela patrons i no s'ha d'utilitzar per protegir dades reals.

Informació

No hi ha un "guanyador".

Els sistemes reals combinen les dues famílies. La criptografia asimètrica resol problemes de distribució i identitat, mentre que la simètrica xifra grans volums de dades amb molta eficiència.

2. Generar un parell de claus RSA

Les claus RSA han de complir propietats matemàtiques concretes. No les construirem a mà. Java ens proporciona KeyPairGenerator.

JAVA 
import java.security.KeyPair;
import java.security.KeyPairGenerator;
import java.security.PrivateKey;
import java.security.PublicKey;

KeyPairGenerator generador =
        KeyPairGenerator.getInstance("RSA");

generador.initialize(2048);

KeyPair parell =
        generador.generateKeyPair();

PublicKey publica =
        parell.getPublic();

PrivateKey privada =
        parell.getPrivate();

La mida de 2048 bits descriu el mòdul RSA. La generació necessita aleatorietat criptogràfica i pot trigar perceptiblement més que crear un objecte Java normal.

Inspeccionar la clau pública

Si volem observar els components matemàtics de la clau pública, podem convertir-la a RSAPublicKey:

JAVA 
import java.security.interfaces.RSAPublicKey;

RSAPublicKey rsa =
        (RSAPublicKey) publica;

String modulHex =
        rsa.getModulus().toString(16);

String exponentHex =
        rsa.getPublicExponent().toString(16);

System.out.println(
    "Mòdul: "
    + modulHex.substring(0, 16)
    + "..."
    + modulHex.substring(
        modulHex.length() - 16
      )
);

System.out.println(
    "Exponent: " + exponentHex
);

L'exponent públic habitual és 65537, que en hexadecimal és 10001. No cal memoritzar-ne la matemàtica per utilitzar correctament l'API.

Les claus canvien a cada execució

Si executeu el programa dues vegades, obtindreu parells diferents. Això és el comportament esperat. Si necessiteu mantenir la mateixa identitat entre execucions, les claus s'han de desar de forma segura, per exemple en un keystore.

Important

No imprimiu mai la clau privada en una aplicació real. Als exemples podem inspeccionar objectes per entendre'ls, però el secret criptogràfic perd el seu valor si apareix en logs, captures o repositoris.

3. Xifrar amb la pública i desxifrar amb la privada

La classe central del JCE per xifrar i desxifrar és Cipher. Farem un exemple complet amb un missatge curt.

JAVA 
import java.nio.charset.StandardCharsets;
import java.util.Base64;
import javax.crypto.Cipher;

String missatge =
        "Missatge secret de prova";

Cipher cipher =
        Cipher.getInstance(
                "RSA/ECB/PKCS1Padding"
        );

cipher.init(
        Cipher.ENCRYPT_MODE,
        publica
);

byte[] xifrat = cipher.doFinal(
        missatge.getBytes(
                StandardCharsets.UTF_8
        )
);

String xifratBase64 =
        Base64.getEncoder()
              .encodeToString(xifrat);

System.out.println(xifratBase64);

El resultat és binari. Base64 només ens permet mostrar-lo i transportar-lo com a text. Per recuperar el missatge:

JAVA 
cipher.init(
        Cipher.DECRYPT_MODE,
        privada
);

byte[] bytesXifrats =
        Base64.getDecoder()
              .decode(xifratBase64);

byte[] desxifrat =
        cipher.doFinal(bytesXifrats);

String recuperat = new String(
        desxifrat,
        StandardCharsets.UTF_8
);

System.out.println(recuperat);

System.out.println(
        missatge.equals(recuperat)
);
Figura

Una prova que ha de fallar

Genereu un segon parell de claus i intenteu desxifrar amb una clau privada que no correspon a la pública usada per xifrar. El procés ha de fallar. Aquesta prova és útil perquè confirma que no estem confonent la representació Base64 amb la protecció criptogràfica.

Informació

Patró mental

String -> bytes -> Cipher -> bytes xifrats -> Base64. Per tornar: Base64 -> bytes xifrats -> Cipher -> bytes -> String. Si teniu clar aquest recorregut, la major part del codi deixa de semblar màgia.

4. Padding, límits de RSA i xifrat híbrid

RSA no està pensat per xifrar un fitxer gran directament. Amb una clau RSA de 2048 bits, el bloc criptogràfic ocupa 256 bytes. Amb PKCS1Padding, una part d'aquests bytes es reserva per al padding, de manera que el missatge directe queda limitat aproximadament a 245 bytes.

TEXT 
2048 bits / 8 = 256 bytes de mòdul

PKCS#1 v1.5:
256 - 11 = 245 bytes màxims de dades

Per què hi ha padding?

El padding no és un farciment decoratiu. Forma part de l'esquema criptogràfic i evita propietats insegures del RSA "nu". En els exemples seguim RSA/ECB/PKCS1Padding perquè permet veure el mecanisme de manera directa.

Important

En dissenys moderns, no trieu padding RSA a cegues. OAEP és l'esquema habitual per a nou codi de xifrat RSA. PKCS1Padding apareix en molts sistemes i és útil per entendre APIs i compatibilitat, però la selecció criptogràfica real depèn del protocol i de les biblioteques utilitzades.

Xifrat híbrid

La solució habitual combina criptografia simètrica i asimètrica:

Figura
TEXT 
Emissor:
1. genera una clau AES aleatòria
2. xifra les dades amb AES
3. xifra la clau AES amb RSA pública
4. envia:
   - dades xifrades
   - clau AES xifrada

Receptor:
1. desxifra la clau AES amb RSA privada
2. usa la clau AES per desxifrar les dades

Aquest patró explica per què "TLS utilitza criptografia asimètrica" no significa que xifri cada byte de la connexió amb RSA. Els protocols moderns negocien secrets i després protegeixen el trànsit amb criptografia simètrica eficient.

Una prova pràctica del límit

JAVA 
StringBuilder gran = new StringBuilder();

while (gran.toString()
           .getBytes(StandardCharsets.UTF_8)
           .length < 300) {
    gran.append("A");
}

cipher.init(
    Cipher.ENCRYPT_MODE,
    publica
);

cipher.doFinal(
    gran.toString()
        .getBytes(StandardCharsets.UTF_8)
);

Amb la configuració indicada, aquest missatge és massa gran. L'error ens ajuda a recordar que RSA directe serveix per a dades petites, no com a substitut d'AES.

5. Signatures, certificats i com encaixa tot dins TLS

Una parella RSA no només es pot utilitzar per a confidencialitat. També pot participar en signatures digitals. El propòsit canvia:

  • per confidencialitat, xifrem per al propietari de la clau privada;
  • per signar, el propietari utilitza la seva clau privada i els altres verifiquen amb la pública.

Signar i verificar amb Java

JAVA 
import java.security.Signature;

byte[] dades =
        "document important"
        .getBytes(StandardCharsets.UTF_8);

Signature signador =
        Signature.getInstance(
                "SHA256withRSA"
        );

signador.initSign(privada);
signador.update(dades);

byte[] signatura =
        signador.sign();
JAVA 
Signature verificador =
        Signature.getInstance(
                "SHA256withRSA"
        );

verificador.initVerify(publica);
verificador.update(dades);

boolean valida =
        verificador.verify(signatura);

System.out.println(valida);

Si modifiqueu un sol byte de dades, la verificació ha de fallar.

On entra el certificat?

Una clau pública sola no ens diu a qui pertany. Un certificat associa una identitat amb una clau pública i incorpora una signatura de l'emissor. Això permet construir una cadena de confiança.

Èxit

Ja no són peces aïllades.

El hash us permet entendre integritat, l'autenticació us dona una identitat de sessió, TLS protegeix la transmissió, el certificat associa identitat i clau pública i RSA mostra com treballen les claus asimètriques. Quan aquestes peces es combinen, podeu raonar sobre un servei segur de principi a fi.
