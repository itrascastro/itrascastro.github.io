1. Autenticació, autorització i estat de sessió

Un servidor pot acceptar una connexió TCP sense saber encara qui hi ha a l'altre extrem. La connexió respon a una pregunta de transport: "amb quin procés estic parlant?". L'autenticació respon a una pregunta diferent: "quina identitat diu ser i ho pot demostrar?".

Definició

Autenticació: Procés de verificar la identitat d'un usuari, client o servei.

Definició

Autorització: Decisió sobre quines operacions pot executar una identitat que ja coneixem.

Figura

La sessió necessita memòria

En un protocol de text, cada línia arriba per separat, però el significat d'una ordre pot dependre de les ordres anteriors. Una variable booleana ja permet representar el cas més senzill:

JAVA 
private boolean authenticated = false;

void processar(String ordre) {

    if (ordre.startsWith("AUTH ")) {
        // verificar credencials...
        authenticated = true;
        return;
    }

    if (ordre.startsWith("ENVIAR ")) {

        if (!authenticated) {
            respondre("530 Authentication required");
            return;
        }

        // executar operació protegida
    }
}

La variable pertany a una sessió concreta. Si el servidor crea un objecte sessió per cada client, cada client ha de tenir el seu propi estat d'autenticació.

Problema

Error de disseny: declarar authenticated com a static. Si un client s'autentica, tots els objectes de sessió compartirien el mateix valor i altres clients podrien quedar autenticats sense haver presentat credencials.

Un estat una mica més expressiu

Quan el protocol creix, un booleà pot quedar curt. Podem combinar l'estat del diàleg amb la identitat autenticada:

JAVA 
enum SessionState {
    CONNECTED,
    GREETED,
    MAIL_FROM,
    RCPT_TO,
    DATA
}

private SessionState state =
        SessionState.CONNECTED;

private boolean authenticated = false;
private String authenticatedUser = null;

Ara podem distingir dues condicions independents: haver seguit correctament el protocol i haver demostrat una identitat.

Informació

Idea clau

L'autenticació no és una ordre aïllada. És un canvi d'estat de la sessió. A partir d'aquell moment, les decisions del servidor poden tenir en compte la identitat.

Exercici: Una porta abans de l'ordre
Partiu d'un protocol amb les ordres PING, SECRET i QUIT. PING ha de ser pública, SECRET només pot funcionar després d'autenticar-se i QUIT sempre ha de funcionar. Dibuixeu primer l'estat i després implementeu-lo.
Bàsic 12 min
Veure pistes
  • No cal xarxa per provar la lògica.
  • Feu una funció que rebi una línia i retorni una resposta.
  • Proveu SECRET abans i després d'autenticar.

2. AUTH PLAIN: format, NUL i Base64

Molts protocols defineixen exactament com s'han de representar les credencials. Un exemple senzill és el mecanisme AUTH PLAIN de SMTP. La informació abans de codificar té aquesta forma:

TEXT 
[NUL]usuari[NUL]contrasenya

Exemple conceptual:
\0alice\0s3cr3t

El byte NUL no és el text \ seguit del número 0. És un caràcter amb valor zero. A Java el podem construir així:

JAVA 
String tokenPlain =
        "\0" + usuari + "\0" + contrasenya;

String tokenBase64 =
        Base64.getEncoder().encodeToString(
                tokenPlain.getBytes(
                        StandardCharsets.UTF_8
                )
        );

out.println("AUTH PLAIN " + tokenBase64);
Figura

El servidor fa el camí invers

JAVA 
byte[] decoded =
        Base64.getDecoder().decode(token);

String contingut = new String(
        decoded,
        StandardCharsets.UTF_8
);

String[] parts =
        contingut.split("\0", -1);

if (parts.length != 3
        || !parts[0].isEmpty()) {
    // format incorrecte
}

String usuari = parts[1];
String contrasenya = parts[2];

El segon paràmetre -1 fa que split conservi els camps buits. Això és útil perquè el primer camp ha de quedar buit a causa del NUL inicial.

Base64 no protegeix AUTH PLAIN

Important

AUTH PLAIN només és raonable sobre un canal protegit. Qualsevol observador que capturi el token Base64 el pot decodificar i recuperar usuari i contrasenya. La protecció real del trànsit arribarà amb TLS.

Exercici: Construïu i desmunteu el token
Feu dues funcions: una que rebi usuari i contrasenya i retorni el token Base64, i una altra que rebi el token i mostri els tres camps resultants. Proveu també un token Base64 invàlid.
Bàsic 12 min
Veure pistes
  • Captureu IllegalArgumentException en decodificar.
  • No imprimiu contrasenyes en una aplicació real; aquí només és una prova local.
  • Comproveu el nombre de camps abans d'accedir-hi.

3. Verificar credencials al servidor

Un cop hem extret l'usuari i la contrasenya, el servidor ha de decidir si són correctes. Per mantenir l'exemple petit, podem representar els usuaris amb un Map<String, String> que associa cada nom amb un resum.

JAVA 
private static final Map<String, String>
        USERS = Map.of(
    "alice", sha256("s3cr3t"),
    "bob",   sha256("java2026")
);

La verificació té quatre passos:

  1. Comprovar que l'usuari existeix.
  2. Calcular el resum de la contrasenya rebuda.
  3. Comparar-lo amb el valor guardat.
  4. Canviar l'estat de la sessió només si coincideix.
JAVA 
private boolean autenticar(
        String usuari,
        String contrasenya) throws Exception {

    String esperat = USERS.get(usuari);

    if (esperat == null) {
        return false;
    }

    String rebut = sha256(contrasenya);

    return rebut.equals(esperat);
}

Processar AUTH sense trencar la sessió

JAVA 
if (linia.startsWith("AUTH PLAIN ")) {

    String token =
            linia.substring("AUTH PLAIN ".length())
                 .trim();

    try {
        Credencial c = decodeAuthPlain(token);

        if (autenticar(c.usuari(), c.contrasenya())) {
            authenticated = true;
            authenticatedUser = c.usuari();
            out.println(
                "235 2.7.0 Authentication successful"
            );
        } else {
            out.println(
                "535 5.7.8 Authentication credentials invalid"
            );
        }

    } catch (Exception e) {
        out.println(
            "535 5.7.8 Authentication credentials invalid"
        );
    }

    continue;
}

Fixeu-vos que un token mal format i unes credencials incorrectes generen una resposta d'error controlada. El servidor no ha de caure perquè un client enviï una entrada incorrecta.

Informació

Separar funcions simplifica la depuració.

Una funció decodifica el token, una altra calcula SHA-256, una altra verifica l'usuari i el bucle de sessió només decideix quina resposta del protocol ha d'enviar. Quan tot queda dins d'un únic if, és molt més difícil saber on falla.

No reveleu més informació de la necessària

Una resposta com "l'usuari existeix però la contrasenya és incorrecta" ajuda un atacant a descobrir noms d'usuari vàlids. És millor que els errors d'autenticació externs siguin genèrics, encara que internament disposem de logs de diagnòstic adequats.

Exercici: Autenticació resistent a entrades incorrectes
Implementeu una funció que processi AUTH PLAIN i retorni 235 o 535. Proveu usuari correcte, contrasenya incorrecta, usuari desconegut, token Base64 invàlid i token amb un nombre de camps incorrecte.
Mitjà 20 min
Veure pistes
  • Cada prova ha d'acabar amb una resposta, no amb una excepció no controlada.
  • Canvieu authenticated només després d'una verificació correcta.
  • Manteniu la resposta externa genèrica.

4. Bloquejar operacions fins que l'usuari s'autentiqui

Autenticar correctament no serveix de res si després oblidem comprovar l'estat abans d'una operació sensible. La política s'ha d'aplicar al servidor, perquè el client no és una font de confiança.

JAVA 
if (linia.startsWith("MAIL FROM:")) {

    if (!authenticated) {
        out.println("530 Authentication required");
        continue;
    }

    if (state != SessionState.GREETED) {
        out.println("503 Bad sequence of commands");
        continue;
    }

    // Ara sí: processar MAIL FROM
}

Aquí hi ha dues portes diferents:

  • la porta de seguretat: la sessió està autenticada?
  • la porta del protocol: l'ordre arriba en l'estat correcte?
Figura

El client també ha d'entendre la resposta

El client pot facilitar l'experiència de l'usuari, però no substitueix el control del servidor:

JAVA 
sendCommand(
        "AUTH PLAIN " + tokenBase64
);

String resposta = in.readLine();

if (resposta == null
        || !resposta.startsWith("235")) {

    System.out.println(
            "Autenticació fallida"
    );

    socket.close();
    return;
}

// Només ara continua la seqüència normal
sendCommand("MAIL FROM:<" + from + ">");
Problema

No confieu en "el meu client mai faria això". Qualsevol persona pot escriure un altre client, usar nc o enviar bytes manualment. Les regles de seguretat han d'estar al costat que protegeix el recurs.

Tancar o permetre reintents?

Un protocol pot decidir tancar la connexió després d'un error d'autenticació o permetre un nombre limitat de reintents. Les dues opcions són decisions de disseny. El més important és que el comportament sigui explícit i que un error no deixi la sessió en un estat ambigu.

Exercici: Proveu de saltar-vos la porta
Amb el vostre protocol de prova, intenteu executar l'ordre protegida abans d'AUTH, després d'un AUTH incorrecte i després d'un AUTH correcte. Escriviu el resultat esperat abans d'executar cada prova.
Mitjà 15 min
Veure pistes
  • La primera i la segona prova no poden modificar l'estat protegit.
  • Una autenticació fallida no ha de posar authenticated a true.
  • Comproveu també una seqüència d'ordres incorrecta.

5. Rols, polítiques d'accés i proves negatives

Un booleà respon "està autenticat?". En moltes aplicacions necessitem una pregunta més precisa: "què pot fer aquest usuari?". Un model senzill és associar un rol a cada identitat.

JAVA 
enum Rol {
    LECTOR,
    OPERADOR,
    ADMIN
}

record Usuari(
        String hashContrasenya,
        Rol rol) {}

Map<String, Usuari> usuaris = Map.of(
    "anna",
    new Usuari(
        sha256("demo1"),
        Rol.OPERADOR
    ),
    "pol",
    new Usuari(
        sha256("demo2"),
        Rol.LECTOR
    )
);

La política és una regla explícita

JAVA 
boolean potEliminar(Rol rol) {
    return rol == Rol.ADMIN;
}

boolean potEnviar(Rol rol) {
    return rol == Rol.OPERADOR
        || rol == Rol.ADMIN;
}

boolean potConsultar(Rol rol) {
    return true;
}

Això és preferible a repartir condicions improvisades per tot el codi. Quan la política canvia, sabem on mirar.

AccióLECTOROPERADORADMIN
ConsultarSíSíSí
EnviarNoSíSí
EliminarNoNoSí

Les proves negatives són obligatòries en seguretat

Si només comprovem que el cas correcte funciona, no sabem si la protecció funciona. Hem de provar deliberadament intents que s'han de rebutjar.

TEXT 
Cas 1: sense autenticar -> ENVIAR      -> rebutjat
Cas 2: LECTOR autenticat -> ENVIAR     -> rebutjat
Cas 3: OPERADOR -> ENVIAR              -> acceptat
Cas 4: OPERADOR -> ELIMINAR            -> rebutjat
Cas 5: ADMIN -> ELIMINAR               -> acceptat
Cas 6: credencial incorrecta -> acció  -> rebutjat
Èxit

Una bona prova de seguretat intenta fer allò que no s'hauria de poder fer.

El resultat interessant no és només veure un 235. També és comprovar que una sessió anònima o un rol insuficient no pot arribar al codi que modifica el recurs.

Exercici: Matriu de permisos
Definiu tres rols i quatre operacions per a un servei inventat. Escriviu primer una taula de permisos i després implementeu una única funció autoritzat(rol, operacio). Prepareu com a mínim sis proves, tres de les quals han de ser negatives.
Mitjà 20 min
Veure pistes
  • No barregeu verificació de contrasenya amb autorització.
  • La política ha de ser fàcil de llegir.
  • Una operació desconeguda s'ha de rebutjar per defecte.
