1. Per què un Socket normal no protegeix les dades

Un Socket TCP ens dona un canal fiable i ordenat, però no xifra automàticament el contingut. Si el protocol envia una línia amb usuari, contrasenya o dades privades, aquests bytes poden circular llegibles per la xarxa.

TEXT 
C: AUTH PLAIN AGFsaWNlAHMzY3IzdA==
S: 235 Authentication successful
C: MAIL FROM:<alice@example.org>
C: RCPT TO:<bob@example.org>
C: DATA
C: Missatge confidencial...

Encara que el token d'autenticació estigui en Base64, continua sent reversible. Si el canal és en text pla, un observador pot capturar els bytes i reconstruir la conversa.

Figura

Què aporta TLS?

  • Confidencialitat: el trànsit queda xifrat.
  • Integritat: les alteracions del trànsit es detecten.
  • Autenticació del servidor: habitualment el client valida la identitat del servidor mitjançant un certificat.
  • Autenticació del client opcional: TLS també pot treballar amb certificats de client.

TLS no substitueix el protocol d'aplicació. Abans, el codi feia servir un Socket per obtenir els seus fluxos i parlar el protocol directament.

Figura
Informació

Idea clau

TLS protegeix el canal. L'autenticació de l'aplicació continua sent útil perquè respon a una altra pregunta: quin usuari està operant dins del servei?

Exercici: Què protegeix cada capa?

2. Certificat, clau privada, keystore i truststore

Perquè un servidor TLS pugui demostrar la seva identitat necessita una clau privada i un certificat associat. El certificat conté informació pública, inclosa la clau pública. La clau privada no s'ha de distribuir.

Definició

Certificat digital: Document signat que associa una identitat amb una clau pública i inclou informació com el subjecte, l'emissor i el període de validesa.

Definició

Keystore: Magatzem que pot contenir claus privades i certificats protegits per contrasenya.

Definició

Truststore: Magatzem de certificats o autoritats que una aplicació considera de confiança per validar l'altre extrem.

Figura

Certificat autosignat

En desenvolupament podem generar un certificat en què el subjecte i l'emissor són la mateixa entitat. És útil per fer proves locals, però un client real no l'ha de considerar de confiança només perquè existeixi.

ElementEs pot compartir?Funció
Clau públicaSíForma part del certificat i permet operacions criptogràfiques públiques.
CertificatSíPresenta la identitat i la clau pública.
Clau privadaNoDemostra possessió de la identitat criptogràfica i permet operacions privades.
Contrasenya del keystoreNoProtegeix l'accés al magatzem.

Què passa durant el handshake?

Quan el client obre una connexió TLS, abans de transmetre les dades de l'aplicació hi ha una negociació. De manera simplificada:

TEXT 
1. Client -> proposa paràmetres TLS
2. Servidor -> respon amb els paràmetres triats
3. Servidor -> presenta el certificat
4. Client -> valida la confiança i la identitat
5. Les parts estableixen claus de sessió
6. Comença el trànsit de l'aplicació protegit
Important

Xifrar sense validar la identitat pot ser insuficient. Si el client accepta qualsevol certificat sense comprovar-lo, pot establir un canal xifrat amb un servidor impostor. Més endavant utilitzarem temporalment un trust-all per a proves locals i deixarem clar per què no és una configuració de producció.

  • La confiança del client no és el mateix que la identitat privada del servidor.

3. Crear i inspeccionar un certificat amb keytool

El JDK inclou keytool, una eina de línia d'ordres per gestionar claus i certificats. Per a una prova local podem generar un parell RSA i un certificat autosignat dins d'un keystore.

BASH 
keytool -genkeypair   -alias smtp-server   -keyalg RSA   -keysize 2048   -validity 365   -storetype JKS   -keystore smtp.keystore   -storepass smtp1234   -dname "CN=localhost, O=Exemple, C=ES"

Hem indicat explícitament -storetype JKS perquè després carregarem el fitxer amb KeyStore.getInstance("JKS"). En JDK moderns el tipus per defecte pot ser diferent, així que és millor que la comanda i el codi coincideixin. JKS és un format propi de Java; PKCS12 és un estàndard i, a partir de Java 9, el tipus per defecte. A la secció 6 el fareu servir.

Inspeccionar el contingut

BASH 
keytool -list -v   -keystore smtp.keystore   -storepass smtp1234

Busqueu, com a mínim:

  • l'àlies smtp-server;
  • el tipus d'entrada, que ha de contenir una clau privada;
  • l'algorisme RSA i la mida de clau;
  • el subjecte i l'emissor;
  • les dates de validesa.

Exportar el certificat públic

BASH 
keytool -exportcert   -alias smtp-server   -keystore smtp.keystore   -storepass smtp1234   -rfc   -file smtp-server.crt

El fitxer exportat conté el certificat, no la clau privada. Es podria importar en un truststore de client:

BASH 
keytool -importcert   -alias smtp-server   -file smtp-server.crt   -keystore client-truststore.jks   -storetype JKS
Informació

Eviteu la màgia.

Abans de programar TLS, comproveu amb keytool -list -v que el fitxer existeix, que l'àlies és el que espereu i que la contrasenya és correcta. Molts errors atribuïts a "SSL" són simplement una ruta, un tipus de magatzem o una contrasenya incorrectes.

4. Servidor TLS amb KeyStore i SSLServerSocket

Construirem el servidor en capes. Primer carreguem el keystore, després preparem les claus que usarà TLS, creem un SSLContext i finalment obtenim un SSLServerSocket.

1. Carregar el keystore

JAVA 
KeyStore ks = KeyStore.getInstance("JKS");

try (FileInputStream in =
        new FileInputStream("smtp.keystore")) {

    ks.load(
        in,
        "smtp1234".toCharArray()
    );
}

2. Preparar el KeyManagerFactory

JAVA 
KeyManagerFactory kmf =
        KeyManagerFactory.getInstance(
                KeyManagerFactory
                        .getDefaultAlgorithm()
        );

kmf.init(
        ks,
        "smtp1234".toCharArray()
);

3. Crear el context TLS

JAVA 
SSLContext sslContext =
        SSLContext.getInstance("TLS");

sslContext.init(
        kmf.getKeyManagers(),
        null,
        null
);

4. Obrir el sòcol d'escolta

JAVA 
SSLServerSocketFactory factory =
        sslContext.getServerSocketFactory();

try (SSLServerSocket serverSocket =
        (SSLServerSocket)
        factory.createServerSocket(2526)) {

    System.out.println(
            "Servidor TLS al port 2526"
    );

    while (true) {

        SSLSocket socket =
                (SSLSocket) serverSocket.accept();

        new Thread(
            new SmtpSession(socket)
        ).start();
    }
}

La part més interessant és l'última línia del bucle: SSLSocket hereta de Socket. Si la lògica de sessió ja treballa amb un Socket, podem reutilitzar-la. Això separa molt bé dues responsabilitats:

Figura
Problema

Si el servidor falla abans d'acceptar connexions, reviseu primer la ruta del keystore, el tipus JKS, la contrasenya del magatzem i la contrasenya de la clau. Si falla quan connecta el client, llavors investigueu el handshake.

5. Client TLS, confiança i depuració del handshake

El client també necessita un SSLContext. La diferència principal és que ha de decidir quins certificats accepta.

Opció de desenvolupament: acceptar qualsevol certificat

Per a una prova local controlada podem crear temporalment un TrustManager que no rebutgi cap certificat:

JAVA 
TrustManager[] trustAll =
        new TrustManager[] {
    new X509TrustManager() {

        public X509Certificate[]
        getAcceptedIssuers() {
            return new X509Certificate[0];
        }

        public void checkClientTrusted(
                X509Certificate[] chain,
                String authType) {
        }

        public void checkServerTrusted(
                X509Certificate[] chain,
                String authType) {
        }
    }
};
Important

Aquesta configuració és només per a desenvolupament.

Un trust-all elimina la validació de la identitat del servidor. La connexió pot quedar xifrada, però el client acceptaria també un certificat presentat per un servidor impostor. En producció s'ha d'utilitzar la validació normal o un truststore controlat.

Crear i connectar l'SSLSocket

JAVA 
SSLContext sslContext =
        SSLContext.getInstance("TLS");

sslContext.init(
        null,
        trustAll,
        new SecureRandom()
);

SSLSocketFactory factory =
        sslContext.getSocketFactory();

try (SSLSocket socket =
        (SSLSocket)
        factory.createSocket(
                "localhost",
                2526
        )) {

    socket.startHandshake();

    // A partir d'aquí:
    // mateixos streams i mateix protocol
}
Figura

Client amb truststore

Una alternativa més propera a un entorn real és importar el certificat de prova en un truststore i deixar que Java faci la validació. Es pot configurar amb propietats del sistema abans d'obrir la connexió:

JAVA 
System.setProperty(
    "javax.net.ssl.trustStore",
    "client-truststore.jks"
);

System.setProperty(
    "javax.net.ssl.trustStorePassword",
    "contrasenya-del-truststore"
);

System.setProperty(
    "javax.net.ssl.trustStoreType",
    "JKS"
);
Important

Les propietats javax.net.ssl.* són globals. Canvien la configuració de tota la JVM: qualsevol altra connexió TLS del mateix procés les heretarà, i una prova que les canvia pot alterar les altres. Una alternativa més neta és construir un SSLContext propi per a cada client, amb un TrustManagerFactory, tal com es mostra a la secció 7.

Quan el handshake falla

Els errors TLS poden semblar opacs. Per a una sessió de depuració local, Java pot mostrar informació del handshake:

JAVA 
System.setProperty(
    "javax.net.debug",
    "ssl,handshake"
);

Activeu-ho només quan ho necessiteu: la sortida és molt extensa. Abans de llegir centenars de línies, reviseu els errors més habituals:

SímptomaPrimera comprovació

Error carregant keystoreRuta, tipus de magatzem i contrasenya.
SSLHandshakeException al clientEl certificat és de confiança i encara és vàlid?
El servidor rep connexió però no dadesHa acabat el handshake? Les dues parts parlen TLS?

6. PKCS12: magatzems de claus per a certificats i claus secretes

Un magatzem PKCS12 pot guardar claus privades amb els seus certificats i també claus secretes, per exemple una clau AES. Cada entrada té un àlies, el nom amb què la trobareu. Aquesta secció mostra com crear una clau AES al magatzem i com recuperar-la des de Java.

Crear una clau AES amb keytool

BASH 
export MAGATZEM_PASS='contrasenya-de-prova-26'

keytool -genseckey -keyalg AES -keysize 256 \
        -alias notes -storetype PKCS12 \
        -keystore claus.p12 -storepass:env MAGATZEM_PASS
ParàmetreSignificat
-genseckeyGenera una clau secreta nova i aleatòria.
-keyalg AES -keysize 256La clau és AES de 256 bits.
-alias notesNom de l'entrada dins del magatzem.
-storetype PKCS12Format del fitxer.
-keystore claus.p12Fitxer de destinació; es crea si no existeix.
-storepass:env MAGATZEM_PASSLlegeix la contrasenya d'una variable d'entorn, de manera que no queda escrita a l'ordre ni a l'historial del terminal.

A PowerShell, definiu la variable amb $env:MAGATZEM_PASS='contrasenya-de-prova-26'. Una contrasenya escrita en un exemple és només de prova: en una aplicació real no s'escriu mai al codi.

Inspeccionar el magatzem

BASH 
keytool -list -storetype PKCS12 -keystore claus.p12 \
        -storepass:env MAGATZEM_PASS

Heu de veure l'entrada notes de tipus SecretKeyEntry. keytool no mostra els bytes de la clau.

Carregar la clau des de Java

JAVA ClauDesadaPkcs12.java 
import java.io.InputStream;
import java.nio.file.Files;
import java.nio.file.Path;
import java.security.GeneralSecurityException;
import java.security.Key;
import java.security.KeyStore;
import javax.crypto.SecretKey;

public class ClauDesadaPkcs12 {

    // Recupera la clau AES guardada amb l'àlies indicat.
    static SecretKey carregarClauAes(Path fitxer, char[] contrasenya, String alies) throws Exception {
        KeyStore magatzem = KeyStore.getInstance("PKCS12");
        try (InputStream in = Files.newInputStream(fitxer)) {
            magatzem.load(in, contrasenya);     // contrasenya incorrecta -> IOException
        }
        Key clau = magatzem.getKey(alies, contrasenya);
        if (!(clau instanceof SecretKey secreta) || !"AES".equals(secreta.getAlgorithm()))
            throw new GeneralSecurityException("No hi ha cap clau AES amb l'àlies " + alies);
        return secreta;
    }

    public static void main(String[] args) throws Exception {
        char[] contrasenya = System.getenv("MAGATZEM_PASS").toCharArray();
        SecretKey clau = carregarClauAes(Path.of(args[0]), contrasenya, "notes");
        System.out.println("Algorisme: " + clau.getAlgorithm() + ", bits: " + clau.getEncoded().length * 8);
        SecretKey altra = carregarClauAes(Path.of(args[0]), contrasenya, "notes");
        System.out.println("La mateixa clau a cada càrrega: " + java.util.Arrays.equals(clau.getEncoded(), altra.getEncoded()));
        try { carregarClauAes(Path.of(args[0]), "incorrecta".toCharArray(), "notes"); }
        catch (java.io.IOException e) { System.out.println("Contrasenya incorrecta -> " + e.getClass().getSimpleName()); }
        try { carregarClauAes(Path.of(args[0]), contrasenya, "inexistent"); }
        catch (GeneralSecurityException e) { System.out.println("Àlies inexistent -> " + e.getMessage()); }
    }
}
TEXT 
Algorisme: AES, bits: 256
La mateixa clau a cada càrrega: true
Contrasenya incorrecta -> IOException
Àlies inexistent -> No hi ha cap clau AES amb l'àlies inexistent
  • KeyStore.load comprova la contrasenya: si és incorrecta llança IOException.
  • getKey(alies, contrasenya) retorna un Key; comproveu que és un SecretKey i que l'algorisme és AES abans de fer-lo servir.
  • Un àlies que no existeix retorna null, no una excepció: gestioneu-ho explícitament.

Tres coses que no s'han de confondre

ElementQuè ésDurada
Contrasenya del magatzemProtegeix l'accés al fitxer. No és la clau de xifrat.La decidiu vosaltres.
Clau AESUn secret aleatori guardat dins del magatzem. No es dedueix de cap contrasenya.Es conserva entre execucions.
ÀliesEl nom de l'entrada. No és un secret.Fix.
Important

Una clau perduda no es recupera. Si torneu a crear un magatzem amb el mateix nom i la mateixa contrasenya, keytool genera una clau diferent: les dades xifrades amb l'anterior ja no es podran desxifrar. Conserveu el fitxer original i la contrasenya que el protegeix, i no regenereu l'entorn si ja hi ha dades xifrades.

7. Client TLS amb un context propi: TrustManagerFactory i verificació del nom

Un servidor demostra la seva identitat amb un certificat. El client decideix en quins certificats confia i, a més, ha de comprovar que el certificat correspon al nom amb què s'ha connectat. Aquí ho fem sense confiar en tot i sense tocar la configuració global de la JVM.

Preparar els magatzems

BASH 
export MAGATZEM_PASS='contrasenya-de-prova-26'

# 1. Servidor: parella de claus i certificat, amb nom DNS localhost
keytool -genkeypair -alias servidor -keyalg RSA -keysize 2048 -validity 365 \
        -storetype PKCS12 -keystore servidor.p12 -storepass:env MAGATZEM_PASS \
        -dname "CN=localhost" -ext "san=dns:localhost"

# 2. Exportar només el certificat públic
keytool -exportcert -alias servidor -keystore servidor.p12 \
        -storepass:env MAGATZEM_PASS -rfc -file servidor.cer

# 3. Truststore del client: només conté el certificat públic
keytool -importcert -alias servidor -file servidor.cer \
        -keystore client.p12 -storetype PKCS12 \
        -storepass:env MAGATZEM_PASS -noprompt

El SAN (Subject Alternative Name) és la llista de noms per als quals el certificat és vàlid. Els clients TLS actuals comproven el SAN, no el camp CN. El truststore del client només té el certificat públic: servidor.p12, que conté la clau privada, no es distribueix mai.

El context del client

JAVA 
static SSLContext contextClient(Path truststore, char[] contrasenya)
        throws Exception {
    KeyStore magatzem = KeyStore.getInstance("PKCS12");
    try (InputStream in = Files.newInputStream(truststore)) {
        magatzem.load(in, contrasenya);
    }
    TrustManagerFactory fabrica = TrustManagerFactory.getInstance(
            TrustManagerFactory.getDefaultAlgorithm());
    fabrica.init(magatzem);                 // només confiarà en aquests certificats
    SSLContext context = SSLContext.getInstance("TLS");
    context.init(null, fabrica.getTrustManagers(), null);
    return context;
}

És el mateix patró que a la secció 4, però a l'inrevés: el servidor inicialitza el context amb KeyManagerFactory (la seva clau privada i el seu certificat) i el client amb TrustManagerFactory (en qui confia). El context no toca cap propietat global: dos clients del mateix programa poden tenir confiances diferents.

Comprovar també el nom del servidor

Un SSLSocket comprova que la cadena de certificats és de confiança, però no comprova per defecte que el certificat correspongui al nom del servidor. Cal activar-ho a SSLParameters abans del handshake:

JAVA 
SSLParameters parametres = socket.getSSLParameters();
parametres.setEndpointIdentificationAlgorithm("HTTPS");
socket.setSSLParameters(parametres);
socket.startHandshake();

Sense aquesta comprovació, un servidor amb un certificat de confiança però d'un altre nom seria acceptat. HttpClient i HttpsURLConnection ja ho fan per defecte; amb un sòcol cru, s'ha de demanar.

OpcióQuè validaQuan
Confiar en tot (trust-all)ResMai en una aplicació; només com a prova local molt controlada.
Propietats javax.net.ssl.*Valida amb el truststore, però afecta tota la JVMScripts simples d'un sol client.
SSLContext propi amb TrustManagerFactoryValida amb el truststore i només afecta aquest clientL'opció recomanada.

Un programa complet amb tres proves

El programa arrenca un servidor TLS de prova i es connecta tres vegades: amb el truststore correcte, amb un nom que no coincideix amb el certificat (127.0.0.1) i amb un truststore que no coneix el servidor. Cal haver preparat servidor.p12 i client.p12, i un tercer truststore altre.p12 amb un certificat diferent, a la carpeta que es passa com a argument.

JAVA TlsClient.java 
import java.io.*;
import java.nio.file.Files;
import java.nio.file.Path;
import java.security.KeyStore;
import javax.net.ssl.*;

public class TlsClient {

    static KeyStore carregar(Path fitxer, char[] contrasenya) throws Exception {
        KeyStore ks = KeyStore.getInstance("PKCS12");
        try (InputStream in = Files.newInputStream(fitxer)) { ks.load(in, contrasenya); }
        return ks;
    }

    // Context del servidor: la seva clau privada i el seu certificat.
    static SSLContext contextServidor(Path p12, char[] pass) throws Exception {
        KeyManagerFactory kmf = KeyManagerFactory.getInstance(KeyManagerFactory.getDefaultAlgorithm());
        kmf.init(carregar(p12, pass), pass);
        SSLContext ctx = SSLContext.getInstance("TLS");
        ctx.init(kmf.getKeyManagers(), null, null);
        return ctx;
    }

    // Context del client: només confia en els certificats del truststore indicat.
    static SSLContext contextClient(Path truststore, char[] pass) throws Exception {
        TrustManagerFactory tmf = TrustManagerFactory.getInstance(TrustManagerFactory.getDefaultAlgorithm());
        tmf.init(carregar(truststore, pass));
        SSLContext ctx = SSLContext.getInstance("TLS");
        ctx.init(null, tmf.getTrustManagers(), null);
        return ctx;
    }

    static String demanar(SSLContext ctx, String host, int port) throws Exception {
        try (SSLSocket s = (SSLSocket) ctx.getSocketFactory().createSocket(host, port)) {
            SSLParameters p = s.getSSLParameters();
            p.setEndpointIdentificationAlgorithm("HTTPS");   // comprova que el nom coincideix amb el certificat
            s.setSSLParameters(p);
            s.startHandshake();
            new PrintWriter(s.getOutputStream(), true).println("hola");
            return new BufferedReader(new InputStreamReader(s.getInputStream())).readLine();
        }
    }

    // Missatge de l'error més profund: és el que explica per què s'ha rebutjat.
    static String causa(Throwable e) {
        while (e.getCause() != null) e = e.getCause();
        return e.getMessage();
    }

    public static void main(String[] args) throws Exception {
        char[] pass = System.getenv("MAGATZEM_PASS").toCharArray();
        Path dir = Path.of(args[0]);
        SSLServerSocket servidor = (SSLServerSocket) contextServidor(dir.resolve("servidor.p12"), pass)
                .getServerSocketFactory().createServerSocket(0, 5, java.net.InetAddress.getLoopbackAddress());
        int port = servidor.getLocalPort();
        Thread fil = new Thread(() -> {
            while (!servidor.isClosed()) {
                try (SSLSocket c = (SSLSocket) servidor.accept()) {
                    BufferedReader in = new BufferedReader(new InputStreamReader(c.getInputStream()));
                    PrintWriter out = new PrintWriter(c.getOutputStream(), true);
                    out.println("eco: " + in.readLine());
                } catch (IOException e) { /* handshake fallit: el servidor continua */ }
            }
        });
        fil.setDaemon(true);
        fil.start();

        SSLContext fiable = contextClient(dir.resolve("client.p12"), pass);
        System.out.println("1. localhost amb el truststore correcte: " + demanar(fiable, "localhost", port));
        try { demanar(fiable, "127.0.0.1", port); System.out.println("2. 127.0.0.1: acceptat (MALAMENT)"); }
        catch (SSLHandshakeException e) { System.out.println("2. 127.0.0.1 -> rebutjat: " + causa(e)); }
        SSLContext desconegut = contextClient(dir.resolve("altre.p12"), pass);
        try { demanar(desconegut, "localhost", port); System.out.println("3. truststore sense el certificat: acceptat (MALAMENT)"); }
        catch (SSLHandshakeException e) { System.out.println("3. truststore que no coneix el servidor -> rebutjat: " + causa(e)); }
        servidor.close();
    }
}
TEXT 
1. localhost amb el truststore correcte: eco: hola
2. 127.0.0.1 -> rebutjat: No subject alternative names matching IP address 127.0.0.1 found
3. truststore que no coneix el servidor -> rebutjat: unable to find valid certification path to requested target
Èxit

Les tres proves són el mínim. Una connexió de confiança s'accepta, un nom incorrecte es rebutja i un servidor desconegut es rebutja. Una SSLHandshakeException no s'ha d'ignorar ni convertir en un avís: vol dir que el client no sap amb qui parla.
