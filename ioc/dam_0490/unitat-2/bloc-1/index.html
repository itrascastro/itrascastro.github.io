1. Client, servidor, protocol i capes

Quan dues aplicacions s'executen en ordinadors diferents no poden compartir variables ni objectes. L'únic que poden fer és intercanviar dades a través de la xarxa. Per això, abans d'escriure cap línia de Java, necessitem un model mental molt simple.

Definició

Client: Aplicació que inicia una comunicació perquè necessita demanar una dada o un servei.

Definició

Servidor: Aplicació que queda disponible en una adreça i un port, espera peticions i genera les respostes corresponents.

Definició

Protocol: Conjunt de regles que defineix quins missatges es poden enviar, en quin format, en quin ordre i què significa cada resposta.

Figura

Imagineu un servei molt petit que converteix text a majúscules. El protocol podria ser:

TEXT 
Client  -> HOLA món
Servidor-> HOLA MÓN

Client  -> fi
Servidor-> ADEU

Aquest protocol no diu res de Java. Un client fet amb Java podria parlar amb un servidor fet amb Python si tots dos interpreten els mateixos bytes de la mateixa manera.

Per què parlem de capes?

La comunicació real és massa complexa per resoldre-la tota a la vegada. Per això es divideix en capes. Per programar aplicacions de xarxa ens interessa especialment aquesta simplificació:

CapaPregunta que resolExemples
AplicacióQuè signifiquen els missatges?HTTP, SMTP, el nostre protocol d'eco
TransportCom arriben les dades entre dos processos?TCP, UDP
XarxaCom arriba un paquet fins a una màquina?IP
EnllaçCom es transmet dins de la xarxa local?Ethernet, Wi-Fi
Informació

Idea clau

Quan programeu amb Socket o DatagramSocket no implementeu IP ni TCP des de zero. El sistema operatiu ja ho fa. El vostre codi treballa a la part alta de la pila: obre un punt de comunicació i decideix què signifiquen les dades que envia i rep.

Una petició no és el mateix que una connexió

Una connexió és un canal de transport establert entre dos extrems. Una petició és un missatge del protocol d'aplicació. En una mateixa connexió TCP podem enviar una petició, deu peticions o mantenir una conversa durant minuts.

Exercici: Dissenyeu un protocol mínim
Imagineu un servidor que rep un número i retorna el seu quadrat. Definiu tres exemples de missatges vàlids, una ordre per finalitzar i una resposta d'error.
Bàsic 8 min
Veure pistes
  • No cal escriure Java.
  • Decidiu exactament què envia el client.
  • Decidiu com sabrà el client si la resposta és correcta o és un error.

2. Adreces IP, ports i endpoints

Per arribar a un servidor necessitem identificar la màquina i el procés que ofereix el servei. La combinació més habitual és una adreça IP i un port.

Definició

Adreça IP: Identificador d'una interfície de xarxa dins d'una xarxa IP. Pot ser IPv4, com 192.168.1.20, o IPv6, com 2001:db8::20.

Definició

Port: Número de 16 bits que permet al sistema operatiu dirigir el trànsit de transport cap al procés correcte. Els ports van de 0 a 65535.

Definició

Endpoint: Extrem d'una comunicació. En els casos habituals es descriu amb una adreça IP i un port.

Figura

Una mateixa màquina pot tenir molts serveis alhora:

TEXT 
192.168.1.50:22     -> servei SSH
192.168.1.50:80     -> servidor web
192.168.1.50:2525   -> servidor SMTP de proves
192.168.1.50:5000   -> el nostre servidor d'eco

localhost i loopback

Durant aquesta unitat provarem molts clients i servidors a la mateixa màquina. El nom localhost acostuma a resoldre cap a una adreça de loopback. En IPv4, l'adreça més coneguda és 127.0.0.1. El trànsit no surt físicament a la xarxa: torna a la mateixa màquina.

TEXT 
Servidor: escolta a localhost:5000
Client:   connecta a localhost:5000

Tots dos processos són a la mateixa màquina,
però continuen comunicant-se mitjançant la pila de xarxa.

Qui tria el port del client?

El servidor acostuma a escoltar en un port conegut o configurat. El client, en canvi, normalment deixa que el sistema operatiu li assigni un port efímer. Això permet que diversos clients es connectin al mateix servidor simultàniament.

Una connexió TCP queda identificada per quatre valors:

TEXT 
IP client : port client  <---->  IP servidor : port servidor

127.0.0.1 : 53142       <---->  127.0.0.1 : 5000
127.0.0.1 : 53143       <---->  127.0.0.1 : 5000

Els dos clients poden utilitzar el mateix servidor perquè el seu port local és diferent.

Important

Port no significa programa. Un port és un recurs del sistema operatiu. Si un procés ja està escoltant en una determinada combinació d'adreça i port, un segon procés normalment no podrà ocupar el mateix punt d'escolta.

Exercici: Qui és qui?
En una connexió 192.168.1.34:54120 -> 192.168.1.10:5000, identifiqueu l'endpoint del client i el del servidor. Expliqueu per què el port 54120 pot canviar en una execució posterior.
Bàsic 6 min
Veure pistes
  • El client inicia la connexió.
  • El servidor escolta en el port conegut.
  • El sistema operatiu pot assignar el port local del client.

3. DNS i InetAddress

Les persones recordem millor example.org que una adreça IP. El DNS permet associar noms amb informació de xarxa i, entre altres coses, resoldre un nom de host a una o més adreces IP.

Figura

A Java, la classe InetAddress ens dona una abstracció comuna per treballar amb adreces IPv4 i IPv6.

JAVA PrimeraResolucio.java 
import java.net.InetAddress;

public class PrimeraResolucio {
    public static void main(String[] args) throws Exception {
        InetAddress adreca =
                InetAddress.getByName("localhost");

        System.out.println("Nom: " + adreca.getHostName());
        System.out.println("IP:  " + adreca.getHostAddress());
    }
}

No fem new InetAddress(...). Utilitzem mètodes estàtics de la classe:

MètodePer a què serveix
getByName(nom)Resol un nom o una representació textual d'una IP i retorna una adreça.
getAllByName(nom)Retorna totes les adreces que el sistema resol per al nom.
getLocalHost()Intenta obtenir el nom i l'adreça de la màquina local.
getLoopbackAddress()Retorna una adreça de loopback sense dependre del DNS.
getByAddress(bytes)Construeix una adreça a partir dels seus bytes.

Un resolutor una mica més útil

JAVA ResolutorDNS.java 
import java.net.InetAddress;
import java.net.UnknownHostException;

public class ResolutorDNS {

    public static void main(String[] args) {
        if (args.length != 1) {
            System.out.println("Ús: java ResolutorDNS <host>");
            return;
        }

        String host = args[0];

        try {
            InetAddress[] adreces =
                    InetAddress.getAllByName(host);

            System.out.println("Resultats per a " + host + ":");

            for (InetAddress adreca : adreces) {
                System.out.printf(
                        "  %-40s  tipus=%s%n",
                        adreca.getHostAddress(),
                        adreca.getClass().getSimpleName()
                );
            }

        } catch (UnknownHostException e) {
            System.out.println(
                    "No s'ha pogut resoldre: " + host
            );
        }
    }
}

Resolució inversa

Si partim d'una IP, podem demanar a Java el nom associat. Però no totes les adreces tenen resolució inversa i el resultat depèn de la configuració DNS.

JAVA 
InetAddress ip = InetAddress.getByName("8.8.8.8");

System.out.println(ip.getHostAddress());
System.out.println(ip.getHostName());
System.out.println(ip.getCanonicalHostName());

També podem preguntar per propietats de l'adreça:

JAVA 
InetAddress a = InetAddress.getLoopbackAddress();

System.out.println(a.isLoopbackAddress());
System.out.println(a.isSiteLocalAddress());
System.out.println(a.isMulticastAddress());
Informació

DNS no és màgia dins d'InetAddress.

InetAddress demana al sistema la resolució corresponent. El resultat pot venir de DNS, del fitxer de hosts, de memòries cau o d'altres mecanismes configurats al sistema operatiu.

Exercici: Mini nslookup
Creeu una utilitat que rebi un host per argument, mostri totes les IP resoltes i indiqui si cada adreça és IPv4 o IPv6. Proveu també una entrada que no existeixi i una adreça IP.
Mitjà 20 min
Veure pistes
  • Useu getAllByName.
  • Captureu UnknownHostException.
  • Podeu observar el tipus amb getClass().getSimpleName().

4. TCP i UDP: què garanteix cadascun

IP ens permet moure paquets entre màquines. A la capa de transport, els dos protocols que treballarem són TCP i UDP. No són dues maneres equivalents de fer el mateix: ofereixen contractes diferents.

Figura
CaracterísticaTCPUDP
Connexió prèviaSíNo
Unitat que veu l'aplicacióFlux de bytesDatagrama
OrdreEls bytes es lliuren en ordreEls datagrames poden arribar desordenats
PèrduaTCP retransmet per oferir un flux fiableUn datagrama es pot perdre
DuplicatsEl flux no entrega bytes duplicats a l'aplicacióL'aplicació ha d'estar preparada per possibles duplicats
Broadcast/multicastNoÉs possible
Usos típicsWeb, SSH, correu, protocols que necessiten fiabilitatDNS, streaming en temps real, descoberta, telemetria, multicast

TCP no conserva els missatges

Aquesta idea és fonamental. TCP conserva l'ordre dels bytes, però no sap on acaba un missatge del nostre protocol i comença el següent.

TEXT 
El client escriu:
"HOLA" + "MÓN"

TCP transporta un flux:
H O L A M Ó N

El receptor necessita una regla pròpia:
- una línia acaba amb \n
- o primer enviem la longitud
- o usem un format que permeti detectar el final

Als primers exemples utilitzarem un protocol de línies de text. Això permet treballar amb readLine(): cada salt de línia marca el final d'un missatge.

UDP sí conserva cada datagrama

Amb UDP, cada DatagramPacket és una unitat independent. Si enviem tres datagrames, el receptor farà tres recepcions si tots arriben. Però no tenim garantia que arribin tots ni en el mateix ordre.

Important

No confongueu "send ha funcionat" amb "el receptor ho ha rebut". En UDP, send() pot acabar correctament encara que no hi hagi cap aplicació escoltant al destí. El protocol no estableix una connexió que ho comprovi abans.

Com escollir?

No trieu TCP o UDP perquè un sigui "millor". Pregunteu què necessita el protocol:

  • si perdre una dada és inacceptable i voleu un flux ordenat, TCP és el punt de partida natural;
  • si cada missatge és independent, una pèrdua puntual es pot tolerar o gestionar a l'aplicació, i valoreu poca latència o multicast, UDP pot encaixar millor.
Exercici: TCP o UDP?
Justifiqueu quin transport provaríeu primer per a: transferir un fitxer, enviar la posició d'un jugador 30 vegades per segon, una sessió de terminal remota i anunciar un servei a molts equips d'una xarxa local.
Bàsic 8 min
Veure pistes
  • Pregunteu què passa si es perd una actualització.
  • Pregunteu si l'ordre és imprescindible.
  • Pregunteu si cal enviar el mateix missatge a molts receptors.

5. Operacions bloquejants, errors i timeouts

La programació de xarxa obliga a pensar en el temps. Moltes operacions són bloquejants: el fil que les executa queda esperant fins que passa alguna cosa.

OperacióQuè pot estar esperant?
ServerSocket.accept()Que arribi una connexió.
BufferedReader.readLine()Que arribin bytes suficients per completar una línia o que es tanqui el flux.
DatagramSocket.receive()Que arribi un datagrama.
Socket.connect(...)Que la connexió s'estableixi o falli.

Bloquejar-se no és necessàriament un error. Un servidor existeix precisament per esperar peticions. El problema és esperar per sempre quan el programa necessita poder continuar.

Timeout en un Socket

JAVA 
import java.net.Socket;
import java.net.SocketTimeoutException;

try (Socket socket = new Socket()) {

    socket.connect(
            new java.net.InetSocketAddress(
                    "localhost", 5000),
            2_000
    );

    socket.setSoTimeout(3_000);

    try {
        int byteRebut = socket.getInputStream().read();
        System.out.println(byteRebut);

    } catch (SocketTimeoutException e) {
        System.out.println(
                "No ha arribat cap dada en 3 segons"
        );
    }
}

El timeout de connexió limita el temps d'establiment. setSoTimeout() limita quant pot esperar una operació de lectura. Són dos problemes diferents.

Timeout en UDP

JAVA 
DatagramSocket socket = new DatagramSocket();
socket.setSoTimeout(2_000);

try {
    socket.receive(paquetResposta);
} catch (SocketTimeoutException e) {
    System.out.println("No s'ha rebut resposta");
}

Errors que heu de saber interpretar

SituacióQuè significa habitualment?
Client TCP connecta a un port sense servidorLa connexió falla, sovint amb ConnectException.
readLine() retorna nullL'altre extrem ha tancat el flux de manera ordenada.
UDP envia però no arriba respostaPot no haver-hi servidor, haver-se perdut el paquet o haver-se perdut la resposta.
El servidor no pot obrir un portEl port pot estar ocupat o no estar disponible.
Informació

Un programa de xarxa robust no assumeix que l'altre extrem sempre respon.

Cal decidir quines esperes poden ser indefinides, quines necessiten timeout i què farà l'aplicació després d'una desconnexió o d'una resposta absent.

Exercici: Fer visible un bloqueig
Creeu un DatagramSocket, prepareu un paquet de recepció i executeu receive sense enviar-li res. Observeu que el programa espera. Afegiu després un timeout de dos segons i gestioneu SocketTimeoutException.
Mitjà 12 min
Veure pistes
  • Primer experimenteu el problema.
  • Després afegiu setSoTimeout(2000).
  • El timeout no tanca necessàriament el socket: decideix què ha de fer el programa.
