1. Per què un servidor seqüencial no escala

El servidor TCP del bloc anterior tenia una limitació deliberada: acceptava un client i dedicava tot el fil principal a conversar amb ell. Mentre aquell client no acabava, el servidor no tornava a accept().

JAVA 
try (ServerSocket servidor = new ServerSocket(5000)) {

    Socket client = servidor.accept();

    // El fil principal queda aquí atenent el client.
    atendre(client);

    // Només després podria acceptar-ne un altre.
}

Si el primer client està cinc minuts sense enviar res, el fil del servidor pot estar cinc minuts bloquejat a readLine(). El servidor continua tenint un port d'escolta, però el nostre codi no està acceptant i atenent noves sessions.

Figura

Primer intent: acceptar en un bucle

JAVA 
while (true) {
    Socket client = servidor.accept();
    atendre(client);
}

Això permet atendre molts clients al llarg del temps, però encara no simultàniament. El segon accept() no s'executa fins que atendre(client) retorna.

Informació

Concurrència de xarxa

Per atendre diversos clients que poden estar bloquejats en lectures independents necessitem que cada sessió pugui avançar sense ocupar l'únic fil que accepta connexions noves.

Què pot passar amb el segon client?

En TCP, el sistema operatiu disposa d'una cua de connexions pendents. Per això un segon client pot arribar a completar temporalment l'establiment de la connexió encara que el nostre programa no hagi cridat de nou accept(). Però això no significa que l'aplicació ja l'estigui atenent. Les dades poden quedar esperant fins que el servidor reculli aquella connexió.

Important

Connectat no significa atès.

Quan proveu un servidor seqüencial amb diversos clients, fixeu-vos en el moment en què cada client rep una resposta, no només en si el constructor de Socket ha retornat.

2. Un fil per client

El patró més senzill per fer concurrent un servidor TCP és crear un fil independent per a cada connexió acceptada.

JAVA 
try (ServerSocket servidor = new ServerSocket(PORT)) {

    while (true) {
        Socket client = servidor.accept();

        Thread fil = new Thread(() -> {
            atendre(client);
        });

        fil.start();
    }
}

Ara el fil principal torna gairebé immediatament a accept(). La conversa amb cada client queda bloquejada, si cal, al seu propi fil.

TEXT 
Fil main:
accept -> client A -> crea fil A -> torna a accept
accept -> client B -> crea fil B -> torna a accept
accept -> client C -> crea fil C -> torna a accept

Fil A: readLine -> processa -> println -> ...
Fil B: readLine -> processa -> println -> ...
Fil C: readLine -> processa -> println -> ...

Una classe ClientHandler

Per no barrejar tota la lògica dins del main, podem encapsular la sessió d'un client en una classe.

JAVA EchoTcpClientHandler.java 
import java.io.BufferedReader;
import java.io.InputStreamReader;
import java.io.PrintWriter;
import java.net.Socket;
import java.nio.charset.StandardCharsets;

public class EchoTcpClientHandler extends Thread {

    private final Socket socket;

    public EchoTcpClientHandler(Socket socket) {
        this.socket = socket;
    }

    @Override
    public void run() {

        String id = socket.getRemoteSocketAddress().toString();

        try (socket;
             BufferedReader entrada =
                     new BufferedReader(
                             new InputStreamReader(
                                     socket.getInputStream(),
                                     StandardCharsets.UTF_8));
             PrintWriter sortida =
                     new PrintWriter(
                             socket.getOutputStream(),
                             true,
                             StandardCharsets.UTF_8)) {

            System.out.println("Connectat " + id);

            String linia;

            while ((linia = entrada.readLine()) != null) {

                if (linia.equalsIgnoreCase("fi")) {
                    sortida.println("ADEU");
                    break;
                }

                sortida.println(linia.toUpperCase());
            }

        } catch (Exception e) {
            System.err.println(
                    "Error amb " + id + ": "
                    + e.getMessage()
            );
        } finally {
            System.out.println("Desconnectat " + id);
        }
    }
}

I el servidor queda reduït a la seva responsabilitat principal:

Informació

Projecte de dos fitxers.

Deseu EchoTcpClientHandler.java i EchoTcpServer.java a la mateixa carpeta abans de compilar.

JAVA EchoTcpServer.java 
import java.net.ServerSocket;
import java.net.Socket;

public class EchoTcpServer {

    private static final int PORT = 5000;

    public static void main(String[] args) throws Exception {

        try (ServerSocket servidor =
                     new ServerSocket(PORT)) {

            System.out.println(
                    "Servidor escoltant al port " + PORT
            );

            while (true) {
                Socket client = servidor.accept();
                new EchoTcpClientHandler(client).start();
            }
        }
    }
}
Èxit

Prova decisiva

Obriu tres clients alhora. Escriviu una frase en cadascun abans de tancar-ne cap. Si tots obtenen resposta, ja no teniu el coll d'ampolla del servidor seqüencial.

Qui tanca cada recurs?

El ServerSocket pertany al servidor principal i ha de continuar obert mentre el servei estigui disponible. Cada Socket de client pertany a la seva sessió i l'ha de tancar el ClientHandler quan aquella sessió acaba.

Important

No tanqueu el ServerSocket des del handler.

Si un client pogués tancar el sòcol d'escolta compartit, deixaria sense servei la resta. La propietat dels recursos ha de quedar clara en el disseny.

Exercici: Tres clients reals

  • Mostreu Thread.currentThread().getName().
  • Cada handler ha de tancar només el seu Socket.
  • El main només accepta i delega.

3. Separar acceptació i sessió amb Runnable

Heretar de Thread és fàcil d'entendre, però barreja dues idees: la feina que cal fer i el mecanisme que l'executa. És més flexible descriure la sessió amb Runnable.

JAVA 
import java.net.Socket;

public class EchoSession implements Runnable {

    private final Socket socket;

    public EchoSession(Socket socket) {
        this.socket = socket;
    }

    @Override
    public void run() {
        // tota la conversa amb un client
    }
}

El servidor decideix després com executar aquella tasca:

JAVA 
Socket client = servidor.accept();

Runnable sessio = new EchoSession(client);

Thread fil = new Thread(sessio);
fil.start();

A primera vista sembla el mateix, però la separació ens permet canviar l'estratègia d'execució sense tocar la lògica del protocol. Al següent apartat substituirem new Thread(...) per un ExecutorService.

Separar encara més: transport, sessió i protocol

Una estructura fàcil de provar és dividir responsabilitats:

PeçaResponsabilitat
ServerEscoltar, acceptar connexions i delegar-les.
SessionLlegir/escriure al socket i controlar la vida de la conversa.
ProtocolInterpretar una petició i construir una resposta.
JAVA EchoProtocol.java 
public class EchoProtocol {

    public String respondre(String peticio) {

        if (peticio.equalsIgnoreCase("fi")) {
            return "ADEU";
        }

        return peticio.toUpperCase();
    }

    public boolean finalitza(String peticio) {
        return peticio.equalsIgnoreCase("fi");
    }
}

Ara aquesta lògica es pot provar sense obrir cap socket:

JAVA 
EchoProtocol p = new EchoProtocol();

System.out.println(p.respondre("hola"));
// HOLA

System.out.println(p.finalitza("fi"));
// true
Informació

Un protocol de xarxa és molt més fàcil de depurar si la seva lògica no depèn directament de la xarxa.

Podeu provar centenars de peticions en memòria i deixar per a les proves d'integració només allò que realment necessita sockets.

Una sessió completa amb Runnable

JAVA EchoSession.java 
import java.io.BufferedReader;
import java.io.IOException;
import java.io.InputStreamReader;
import java.io.PrintWriter;
import java.net.Socket;
import java.nio.charset.StandardCharsets;

public final class EchoSession implements Runnable {

    private final Socket socket;
    private final EchoProtocol protocol =
            new EchoProtocol();

    public EchoSession(Socket socket) {
        this.socket = socket;
    }

    @Override
    public void run() {

        try (socket;
             BufferedReader in =
                     new BufferedReader(
                             new InputStreamReader(
                                     socket.getInputStream(),
                                     StandardCharsets.UTF_8));
             PrintWriter out =
                     new PrintWriter(
                             socket.getOutputStream(),
                             true,
                             StandardCharsets.UTF_8)) {

            String peticio;

            while ((peticio = in.readLine()) != null) {

                out.println(
                        protocol.respondre(peticio)
                );

                if (protocol.finalitza(peticio)) {
                    break;
                }
            }

        } catch (IOException e) {
            System.err.printf(
                    "[%s] %s%n",
                    Thread.currentThread().getName(),
                    e.getMessage()
            );
        }
    }
}
Informació

Projecte reutilitzable.

Deseu EchoProtocol.java i la versió completa d'EchoSession.java a la mateixa carpeta. El servidor amb pool de l'apartat següent reutilitza aquests dos fitxers.

4. Pools de fils, límits i tancament

El patró un fil per connexió funciona bé per entendre la concurrència i per a un nombre moderat de clients. Però té un problema evident: si arriben milers de connexions, crear un fil nou per a cadascuna pot consumir massa memòria i temps de planificació.

Un ExecutorService permet limitar el nombre de sessions que s'executen simultàniament i reutilitzar els fils treballadors.

JAVA EchoPoolServer.java 
import java.net.ServerSocket;
import java.net.Socket;
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;

public class EchoPoolServer {

    private static final int PORT = 5000;
    private static final int FILS = 8;

    public static void main(String[] args) throws Exception {

        ExecutorService pool =
                Executors.newFixedThreadPool(FILS);

        try (ServerSocket servidor =
                     new ServerSocket(PORT)) {

            while (true) {
                Socket client = servidor.accept();
                pool.submit(new EchoSession(client));
            }

        } finally {
            pool.shutdown();
        }
    }
}

La idea és senzilla:

  • el main continua acceptant connexions;
  • cada connexió es converteix en una tasca;
  • el pool té un nombre limitat de fils;
  • si hi ha més tasques que fils, algunes esperen a la cua.
Important

Un pool fixa els fils, no necessàriament la cua.

Executors.newFixedThreadPool() utilitza una cua que pot créixer molt. En serveis de producció, limitar només el nombre de fils pot no ser suficient: també cal pensar en el nombre màxim de connexions pendents i en polítiques de rebuig.

Quan volem controlar també la cua

JAVA 
ThreadPoolExecutor pool =
        new ThreadPoolExecutor(
                4,                      // fils mínims
                8,                      // fils màxims
                60, TimeUnit.SECONDS,
                new ArrayBlockingQueue<>(100),
                new ThreadPoolExecutor.AbortPolicy()
        );

Aquest exemple explicita un límit de 100 tasques a la cua. Si el sistema arriba als seus límits, és millor tenir una política definida que deixar que el consum de recursos creixi sense control.

El cas subtil: què fem amb el Socket si submit falla?

Si una tasca és rebutjada, ningú atendrà aquell client. Per tant, el servidor ha de tancar el socket que acabava d'acceptar.

JAVA 
Socket client = servidor.accept();

try {
    pool.execute(new EchoSession(client));

} catch (RejectedExecutionException e) {

    try {
        client.close();
    } catch (IOException ignored) {
    }
}

Aturada ordenada

Quan el servei deixa d'acceptar clients, primer tanquem el ServerSocket o sortim del bucle d'acceptació. Després demanem al pool que acabi les sessions actives.

JAVA 
pool.shutdown();

try {
    if (!pool.awaitTermination(
            10, TimeUnit.SECONDS)) {

        pool.shutdownNow();
    }

} catch (InterruptedException e) {
    pool.shutdownNow();
    Thread.currentThread().interrupt();
}
Informació

Disponibilitat no significa recursos infinits.

Un servidor robust ha de continuar prestant servei sota càrrega raonable i ha de degradar-se de manera controlada quan arriba als seus límits.

5. Provar, depurar i observar un servei de xarxa

Un servidor pot "estar en marxa" i, tot i així, funcionar malament. Per això no n'hi ha prou amb comprovar que el procés existeix. Hem de poder observar connexions, sessions, errors i temps d'espera.

Logs amb context

Un missatge com Error de lectura diu molt poc. En un servidor concurrent és millor afegir com a mínim client i fil:

JAVA 
System.out.printf(
        "client=%s fil=%s event=%s%n",
        socket.getRemoteSocketAddress(),
        Thread.currentThread().getName(),
        "peticio_rebuda"
);

Proves que hauríeu de fer sempre

ProvaQuè voleu descobrir?
Client vàlidEl camí normal funciona.
Client tanca sense enviar fiEl servidor detecta EOF i allibera recursos.
Ordre incorrectaEl protocol respon amb un error controlat.
Diversos clients alhoraUna sessió no bloqueja les altres.
Client molt lentEntenem quant temps pot ocupar recursos.
Servidor aturatEl client informa del problema i no queda en un estat confús.

Un client de prova automàtic

No cal escriure a mà totes les proves. Podem crear un client que obri una connexió, enviï una petició coneguda i comprovi la resposta.

JAVA 
static boolean comprovarServei()
        throws IOException {

    try (Socket socket =
                 new Socket("localhost", 5000);
         BufferedReader in =
                 new BufferedReader(
                         new InputStreamReader(
                                 socket.getInputStream(),
                                 StandardCharsets.UTF_8));
         PrintWriter out =
                 new PrintWriter(
                         socket.getOutputStream(),
                         true,
                         StandardCharsets.UTF_8)) {

        socket.setSoTimeout(2_000);

        out.println("hola");
        String resposta = in.readLine();

        return "HOLA".equals(resposta);
    }
}

Això és una verificació funcional mínima: no només mira si el port està obert, sinó si el protocol respon correctament.

Mesures útils

Quan el servei creix, és útil mantenir comptadors senzills:

  • connexions acceptades;
  • sessions actives;
  • peticions processades;
  • errors;
  • temps de resposta;
  • tasques en cua si utilitzem un pool.
JAVA 
AtomicInteger sessionsActives =
        new AtomicInteger();

sessionsActives.incrementAndGet();

try {
    // atendre la sessió
} finally {
    sessionsActives.decrementAndGet();
}

Recordeu la unitat anterior: si diversos fils modifiquen el mateix estat, necessitem mecanismes segurs per concurrència. Un AtomicInteger és adequat per a un comptador simple.

Logs i monitoratge

Durant les pràctiques, System.out és suficient per veure què passa. En un servei mantingut convé utilitzar un sistema de logging que permeti nivells, format i destinacions configurables.

JAVA 
private static final Logger LOG =
        Logger.getLogger(
                EchoPoolServer.class.getName());

LOG.info("Servidor iniciat");

LOG.log(
        Level.WARNING,
        "Error atenent el client {0}",
        socket.getRemoteSocketAddress()
);

Java també disposa de JMX per exposar mètriques i estat intern a eines de monitoratge. No cal implementar JMX per entendre la unitat, però sí retenir la idea: un servei observable ofereix informació sobre el seu estat sense obligar-nos a endevinar què passa des de fora.

Disponibilitat i fallades parcials

En una aplicació local, si una crida de mètode arriba al mètode, sabem que tots dos viuen al mateix procés. En xarxa apareix una dificultat nova: podem deixar de rebre resposta sense saber exactament què ha passat a l'altre costat.

TEXT 
Client envia petició
        |
        +-- es perd la connexió abans d'arribar?
        |
Servidor processa la petició
        |
        +-- cau abans de respondre?
        |
Servidor envia resposta
        |
        +-- es perd la connexió durant la resposta?
        |
Client espera...
Important

Timeout no sempre significa "el servidor no ho ha fet".

Pot significar que la petició no va arribar, que el servidor continua treballant o que la resposta es va perdre. Aquesta ambigüitat és una de les raons per les quals els protocols reals defineixen identificadors, operacions idempotents i estratègies de reintent.
