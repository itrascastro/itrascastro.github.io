1. De Thread a ExecutorService

Crear fils manualment és útil per entendre el mecanisme, però no és la millor opció quan tenim moltes tasques semblants. Si arriben cent tasques, crear cent objectes Thread pot ser innecessari i difícil de controlar.

La idea d'un pool de fils és separar dues coses:

  • les tasques que volem executar;
  • els fils treballadors que les executaran.
Figura
JAVA 
ExecutorService executor =
        Executors.newFixedThreadPool(3);

executor.submit(() -> System.out.println(
        Thread.currentThread().getName()
));

executor.shutdown();

newFixedThreadPool(3) crea un executor amb tres fils treballadors. Podem enviar-hi deu, cent o mil tasques. No cal crear un fil nou per a cadascuna.

Informació

ExecutorService no és un fil.

És un gestor de tasques i fils. Rep feina, la posa en una cua quan cal i reutilitza els fils del pool per executar-la.

Quina mida ha de tenir el pool?

No existeix un número universal. Depèn del tipus de feina i de la màquina:

  • en tasques molt intensives de CPU, un valor proper al nombre de nuclis sol ser un bon punt de partida;
  • en tasques que passen molta estona esperant entrada i sortida, pot ser raonable tenir més fils que nuclis;
  • en qualsevol cas, cal mesurar i evitar crear més concurrència de la que el sistema pot aprofitar.
Important

Un pool més gran no garanteix més rendiment. Si tots els fils competeixen per la mateixa CPU, el mateix disc o el mateix bloqueig, afegir-ne més pot empitjorar el temps total.

Suggeriment

Altres executors que convé conèixer: ScheduledExecutorService permet programar tasques retardades o periòdiques. ForkJoinPool està pensat per problemes que es divideixen recursivament en subtasques i utilitza tècniques com el work-stealing. No sempre calen, però formen part de l'ecosistema de concurrència de Java.

Exercici: Veure la reutilització
Creeu un pool de tres fils i envieu-hi deu tasques que només imprimeixin el número de tasca i el nom del fil actual. Observeu quants noms de fil diferents apareixen.
Bàsic 10 min
Veure pistes
  • Useu Executors.newFixedThreadPool(3).
  • Mostreu Thread.currentThread().getName().
  • No oblideu shutdown.

2. Runnable, Callable i Future

Runnable: una acció sense resultat directe

JAVA 
Runnable tasca = () -> {
    int suma = 2 + 3;
    System.out.println("Suma=" + suma);
};

executor.submit(tasca);

Runnable és adequat quan volem executar una acció i no necessitem que la tasca retorni un valor directament.

Callable: una tasca que retorna un resultat

JAVA 
Callable<Integer> tasca = () -> {
    return 12 * 12;
};

Future<Integer> futur = executor.submit(tasca);

Callable<T> retorna un valor de tipus T. Quan enviem la tasca a l'executor, obtenim immediatament un Future<T>.

Definició

Future: Representa un resultat que potser encara no està disponible. Permet esperar-lo, consultar si ha acabat, obtenir-lo o intentar cancel·lar la tasca.

JAVA 
Integer resultat = futur.get();
System.out.println(resultat);

get() bloqueja el fil que el crida fins que el resultat està preparat. Això és útil, però també pot eliminar la concurrència si s'utilitza massa aviat.

Patró important: enviar primer, recollir després

JAVA 
List<Future<Integer>> futurs = new ArrayList<>();

// Fase 1: enviem totes les tasques
for (int n : nombres) {
    futurs.add(executor.submit(() -> n * n));
}

// Fase 2: recollim els resultats
for (Future<Integer> futur : futurs) {
    System.out.println(futur.get());
}
Problema

Antipatró freqüent: fer submit() i immediatament get() dins del mateix bucle. Això pot convertir una execució que podria ser concurrent en una cadena pràcticament seqüencial.

Solució

Separeu l'enviament de la recollida quan les tasques siguin independents. Així el pool pot començar a treballar en moltes tasques abans que el fil principal esperi els resultats.

Què pot passar quan fem get()?

Cal tenir presents tres situacions:

  • InterruptedException: el fil que esperava ha estat interromput;
  • ExecutionException: la tasca ha llançat una excepció;
  • TimeoutException: hem establert un temps màxim i s'ha superat.
Exercici: Quadrats en paral·lel
Envieu vint Callable a un pool de quatre fils. Cada tasca calcula el quadrat d'un nombre. Deseu tots els Future i recolliu els resultats només després d'haver enviat les vint tasques.
Mitjà 15 min
Veure pistes
  • Utilitzeu una List>.
  • No feu get al mateix bucle que submit.
  • Tanqueu l'executor quan ja no accepteu més tasques.

3. Timeouts, cancel·lació i tancament del pool

Esperar un Future amb temps màxim

JAVA 
try {
    String resultat = futur.get(2, TimeUnit.SECONDS);
    processar(resultat);

} catch (TimeoutException e) {
    futur.cancel(true);
    System.out.println("La tasca ha superat el temps màxim");
}

cancel(true) intenta interrompre la tasca si està en execució. La paraula important és intenta. La cancel·lació és cooperativa.

Respondre correctament a una interrupció

JAVA 
Callable<String> tasca = () -> {
    try {
        Thread.sleep(10_000);
        return "acabat";
    } catch (InterruptedException e) {
        Thread.currentThread().interrupt();
        return "interromput";
    }
};

Quan capturem InterruptedException, una pràctica habitual és restaurar l'estat d'interrupció amb Thread.currentThread().interrupt() si no podem completar la tasca de manera normal.

Important

Cancel·lar un Future no és matar màgicament un fil. Si el codi ignora les interrupcions i continua treballant, la cancel·lació pot no aturar-lo immediatament.

Tancar correctament l'ExecutorService

Un patró robust és:

JAVA 
executor.shutdown();

try {
    if (!executor.awaitTermination(5, TimeUnit.SECONDS)) {
        executor.shutdownNow();

        if (!executor.awaitTermination(2, TimeUnit.SECONDS)) {
            System.err.println("El pool no ha finalitzat");
        }
    }
} catch (InterruptedException e) {
    executor.shutdownNow();
    Thread.currentThread().interrupt();
}

shutdown() deixa d'acceptar tasques noves però permet acabar les que ja s'han enviat. shutdownNow() intenta interrompre les tasques en execució i retorna les que encara no havien començat.

Informació

Ordre mental

Primer deixem d'acceptar feina nova. Després donem temps perquè acabi la feina pendent. Només si no finalitza dins del límit passem a una cancel·lació més agressiva.

Exercici: Una tasca que es passa de temps
Envieu una tasca ràpida i una tasca que dormi deu segons. Intenteu obtenir els dos resultats amb un timeout de dos segons. Cancel·leu la tasca lenta i tanqueu correctament el pool.
Mitjà 15 min
Veure pistes
  • Captureu TimeoutException.
  • Comproveu isCancelled i isDone.
  • Feu que la tasca lenta gestioni InterruptedException.

4. Estat compartit, coherència i mesura del temps

Un executor no elimina els problemes de memòria compartida. Si diverses tasques modifiquen el mateix objecte, l'objecte continua necessitant una estratègia de sincronització.

Un acumulador coherent

JAVA Estadistiques.java 
class Estadistiques {
    private int processats;
    private int correctes;
    private int errors;
    private long tempsAcumulatMs;

    public synchronized void registrar(
            boolean correcte,
            long tempsMs) {

        processats++;

        if (correcte) {
            correctes++;
        } else {
            errors++;
        }

        tempsAcumulatMs += tempsMs;
    }

    public synchronized String resum() {
        return "processats=" + processats
                + ", correctes=" + correctes
                + ", errors=" + errors
                + ", tempsAcumulatMs=" + tempsAcumulatMs;
    }
}

La modificació dels quatre camps forma una única operació lògica. Protegir-la amb el mateix monitor evita que els fils deixin l'objecte en un estat impossible.

Invariants

Definició

Invariant: Propietat que ha de continuar sent certa si l'estat de l'objecte és coherent.

En l'exemple anterior, una propietat natural és:

TEXT 
processats == correctes + errors

Els invariants són excel·lents per provar concurrència. No només comprovem que el programa "no peta"; comprovem que les dades finals tenen sentit.

Temps acumulat i temps real

Suposem quatre tasques que triguen dos segons cadascuna. El temps acumulat de treball és d'uns vuit segons. Si s'executen en paral·lel amb quatre treballadors, el temps real transcorregut pot ser d'uns dos segons.

Figura
JAVA 
long inici = System.nanoTime();

// enviament i recollida de tasques

long fi = System.nanoTime();

long tempsRealMs =
        TimeUnit.NANOSECONDS.toMillis(fi - inici);

Prova d'estrès

Per detectar errors de sincronització, utilitzeu moltes tasques i repetiu la prova. Un cas petit pot no produir l'intercalat que fa visible l'error.

JAVA 
int total = 100_000;

ExecutorService executor =
        Executors.newFixedThreadPool(10);

Estadistiques estadistiques = new Estadistiques();

for (int i = 0; i < total; i++) {
    executor.submit(() -> {
        estadistiques.registrar(true, 1);
    });
}

executor.shutdown();
executor.awaitTermination(30, TimeUnit.SECONDS);

System.out.println(estadistiques.resum());
Èxit

Una prova concurrent bona té una afirmació verificable. Per exemple: s'han enviat 100.000 elements, s'han processat exactament 100.000 i la suma de categories coincideix amb el total.

5. Construir i provar una aplicació concurrent completa

Arribats aquí ja tenim totes les peces. Ara les combinarem en un exemple complet, però encara senzill: un simulador que processa peticions independents.

La responsabilitat de cada classe serà clara:

  • Peticio: dades d'entrada;
  • ResultatPeticio: dades de sortida d'una tasca;
  • TascaPeticio: feina concurrent;
  • Estadistiques: estat compartit protegit;
  • SimuladorConcurrent: crea el pool, envia tasques, recull resultats i tanca recursos.
Informació

Aquesta separació és intencionada.

La concurrència és més fàcil de raonar quan les dades, la tasca, l'estat compartit i l'orquestració no estan barrejats en un únic mètode enorme.

1. Dades d'entrada i resultat

JAVA 
record Peticio(int id, int duradaMs) {}

record ResultatPeticio(
        int id,
        boolean correcte,
        long tempsMs,
        String nomFil
) {}
Informació

Si no heu utilitzat record abans: penseu-hi com una forma compacta de declarar una classe de dades immutable amb constructor i mètodes d'accés. Aquí l'utilitzem per evitar codi repetitiu i centrar-nos en la concurrència.

2. Estat compartit

JAVA 
class Estadistiques {
    private int processats;
    private int correctes;
    private int errors;
    private long tempsAcumulatMs;

    public synchronized void registrar(ResultatPeticio resultat) {
        if (resultat == null) {
            throw new IllegalArgumentException("El resultat no pot ser null");
        }

        processats++;

        if (resultat.correcte()) {
            correctes++;
        } else {
            errors++;
        }

        tempsAcumulatMs += resultat.tempsMs();
    }

    public synchronized int getProcessats() {
        return processats;
    }

    public synchronized int getCorrectes() {
        return correctes;
    }

    public synchronized int getErrors() {
        return errors;
    }

    public synchronized boolean esCoherent() {
        return processats == correctes + errors;
    }
}

3. Tasca concurrent

JAVA TascaPeticio.java 
class TascaPeticio implements Callable<ResultatPeticio> {

    private final Peticio peticio;
    private final Estadistiques estadistiques;

    TascaPeticio(Peticio peticio, Estadistiques estadistiques) {
        this.peticio = peticio;
        this.estadistiques = estadistiques;
    }

    @Override
    public ResultatPeticio call() throws Exception {
        long inici = System.nanoTime();

        Thread.sleep(peticio.duradaMs());

        boolean correcte = peticio.id() % 7 != 0;

        long tempsMs = TimeUnit.NANOSECONDS.toMillis(
                System.nanoTime() - inici
        );

        ResultatPeticio resultat = new ResultatPeticio(
                peticio.id(),
                correcte,
                tempsMs,
                Thread.currentThread().getName()
        );

        estadistiques.registrar(resultat);
        return resultat;
    }
}

La tasca calcula un resultat local i només entra a l'objecte compartit per registrar-lo. Aquesta separació redueix el temps dins de la secció crítica.

4. Orquestració

JAVA SimuladorConcurrent.java 
public class SimuladorConcurrent {

    public static void main(String[] args) throws Exception {

        int total = 200;
        int midaPool = 4;

        ExecutorService executor =
                Executors.newFixedThreadPool(midaPool);

        Estadistiques estadistiques = new Estadistiques();
        List<Future<ResultatPeticio>> futurs = new ArrayList<>();

        long inici = System.nanoTime();

        // Fase 1: crear i enviar
        for (int i = 1; i <= total; i++) {
            Peticio peticio = new Peticio(i, 20 + (i % 30));

            futurs.add(
                executor.submit(
                    new TascaPeticio(peticio, estadistiques)
                )
            );
        }

        // Fase 2: recollir
        List<ResultatPeticio> resultats = new ArrayList<>();

        for (Future<ResultatPeticio> futur : futurs) {
            try {
                resultats.add(
                    futur.get(2, TimeUnit.SECONDS)
                );
            } catch (TimeoutException e) {
                futur.cancel(true);
            }
        }

        // Fase 3: tancar
        executor.shutdown();

        if (!executor.awaitTermination(5, TimeUnit.SECONDS)) {
            executor.shutdownNow();
        }

        long tempsRealMs = TimeUnit.NANOSECONDS.toMillis(
                System.nanoTime() - inici
        );

        long filsUtilitzats = resultats.stream()
                .map(ResultatPeticio::nomFil)
                .distinct()
                .count();

        boolean coherent =
                estadistiques.esCoherent()
                && estadistiques.getProcessats() == total
                && resultats.size() == total;

        System.out.println("TOTAL=" + total);
        System.out.println("RESULTATS=" + resultats.size());
        System.out.println("PROCESSATS=" + estadistiques.getProcessats());
        System.out.println("CORRECTES=" + estadistiques.getCorrectes());
        System.out.println("ERRORS=" + estadistiques.getErrors());
        System.out.println("POOL=" + midaPool);
        System.out.println("FILS_UTILITZATS=" + filsUtilitzats);
        System.out.println("TEMPS_REAL_MS=" + tempsRealMs);
        System.out.println("COHERENT=" + coherent);
    }
}

Què heu de ser capaços d'explicar d'aquest programa?

No n'hi ha prou amb fer-lo funcionar. Heu d'entendre el paper de cada peça:

  • per què les tasques són independents i es poden enviar al pool;
  • per què Callable encaixa quan volem un resultat;
  • per què els Future es guarden abans de recollir-los;
  • què passa si una tasca excedeix el timeout;
  • per què Estadistiques necessita sincronització;
  • per què l'informe final s'ha de construir quan les tasques ja no poden modificar l'estat;
  • com sabem que el resultat és coherent;
  • per què temps acumulat i temps real són mesures diferents.
Exercici: Projecte de consolidació
Creeu un sistema concurrent propi amb almenys 100 elements, un pool de quatre o més fils, una tasca Runnable o Callable, un objecte d'estat compartit que realment necessiti sincronització i una comprovació final de coherència. El context pot ser comandes, reserves, paquets, imatges, simulacions o qualsevol altre domini.
Avançat 45-60 min
Veure pistes
  • Comenceu modelant només un element de dades.
  • Feu funcionar una sola tasca abans d'afegir l'executor.
  • Afegiu l'estat compartit després que les tasques ja funcionin.
  • Feu una prova d'estrès final i definiu un invariant clar.
Èxit

Si podeu construir aquest patró sense copiar-lo mecànicament, heu arribat a l'objectiu de la unitat. Heu de poder canviar el context del problema i continuar sabent quines peces necessiteu i per què.

Depurar i documentar concurrència

La concurrència és molt més fàcil de depurar si cada tasca deixa rastres clars. Poseu noms útils als fils quan sigui possible i incloeu l'identificador de la tasca als missatges de diagnòstic.

JAVA 
System.out.printf(
        "tasca=%d fil=%s estat=%s%n",
        peticio.id(),
        Thread.currentThread().getName(),
        Thread.currentThread().getState()
);

Els IDE permeten inspeccionar diversos fils durant una sessió de depuració. També és útil revisar thread dumps quan sospitem un bloqueig. En la documentació de classes compartides, expliqueu quin estat es comparteix i quin mecanisme el protegeix. Aquest contracte és tan important com explicar què retorna un mètode.

Important

Compte amb el depurador. Aturar un sol fil amb un breakpoint pot canviar completament l'ordre temporal del programa. Els logs, les proves repetides i els invariants complementen el debugging tradicional.
