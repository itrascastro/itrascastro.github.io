1. Per què utilitzar un pool de fils?

Aquest codi crea un fil nou per cada element:

JAVA 
for (Tasca tasca : tasques) {
    new Thread(() -> processar(tasca)).start();
}

Amb deu tasques pot semblar raonable. Amb milers de tasques, no.

Cada fil consumeix recursos. Massa fils impliquen més memòria, més canvis de context i més dificultat per controlar la finalització.

Un pool de fils reutilitza un nombre limitat de treballadors.

JAVA 
ExecutorService executor = Executors.newFixedThreadPool(3);
TEXT 
+-- fil 1
TASQUES -----> +-- fil 2
   cua         +-- fil 3

Si enviem deu tasques, els tres fils van agafant feina de la cua.

2. Runnable, Callable i Future

Runnable representa una tasca que no retorna un resultat.

JAVA 
Runnable tasca = () -> {
    System.out.println("Processant...");
};

executor.submit(tasca);

Callable<T> representa una tasca que retorna un valor.

JAVA 
Callable<Integer> tasca = () -> 6 * 7;
Future<Integer> futur = executor.submit(tasca);

El Future representa un resultat que potser encara no està disponible.

JAVA 
int resultat = futur.get();

El fil que crida get() espera fins que la tasca acaba.

Podem posar un límit:

JAVA 
int resultat = futur.get(3, TimeUnit.SECONDS);

Aquesta família de classes es troba a java.util.concurrent, que proporciona abstraccions de nivell més alt que la gestió manual de fils. També hi trobem eines com Semaphore, BlockingQueue, AtomicInteger o ScheduledExecutorService.

Enviar primer i recollir després

Aquest codi utilitza un executor, però pràcticament serialitza el treball:

JAVA 
for (int n : numeros) {
    Future<Integer> futur = executor.submit(() -> calcular(n));
    System.out.println(futur.get());
}

Cada iteració espera abans d'enviar la següent tasca.

La versió concurrent separa l'enviament de la recollida:

JAVA 
List<Future<Integer>> futurs = new ArrayList<>();

for (int n : numeros) {
    futurs.add(executor.submit(() -> calcular(n)));
}

for (Future<Integer> futur : futurs) {
    System.out.println(futur.get());
}

És el mateix patró que hem vist amb processos.

TEXT 
1. crear o enviar totes les tasques
2. deixar que avancin
3. esperar i recollir els resultats

3. Timeout, cancel·lació i tancament

Un Future també pot quedar esperant massa temps.

JAVA 
try {
    String resultat = futur.get(3, TimeUnit.SECONDS);
    System.out.println(resultat);

} catch (TimeoutException e) {
    futur.cancel(true);
    System.out.println("Tasca cancel·lada per timeout");

} catch (ExecutionException e) {
    System.out.println("La tasca ha fallat: " + e.getCause());

} catch (InterruptedException e) {
    Thread.currentThread().interrupt();
}

Les tres situacions són diferents:

  • TimeoutException: no tenim resultat dins del temps permès.
  • ExecutionException: la tasca ha acabat amb una excepció.
  • InterruptedException: el fil que estava esperant ha estat interromput.

cancel(true) intenta interrompre la tasca, però la cancel·lació és cooperativa. El codi de la tasca ha de reaccionar a la interrupció.

JAVA 
try {
    Thread.sleep(10_000);
} catch (InterruptedException e) {
    Thread.currentThread().interrupt();
    return;
}

Tancar correctament l'executor

Un ExecutorService manté fils vius. S'ha de tancar de forma explícita.

JAVA 
executor.shutdown();

try {
    if (!executor.awaitTermination(5, TimeUnit.SECONDS)) {
        executor.shutdownNow();
    }
} catch (InterruptedException e) {
    executor.shutdownNow();
    Thread.currentThread().interrupt();
}

shutdown() deixa d'acceptar tasques noves i permet acabar les pendents.

awaitTermination(...) espera un temps màxim.

shutdownNow() intenta interrompre la feina que encara continua. No és una garantia de finalització instantània.

4. Construir una aplicació concurrent completa

Aquest exemple utilitza un context diferent del de l'EAC. Volem processar diversos fitxers i obtenir un resultat per a cadascun.

Les dades

JAVA 
record FitxerTreball(String nom, long tempsMs) {}

El resultat

JAVA 
record ResultatFitxer(
        String nom,
        boolean correcte,
        long tempsMs,
        String fil
) {}

La tasca

JAVA 
import java.util.concurrent.Callable;

class ProcessarFitxer implements Callable<ResultatFitxer> {

    private final FitxerTreball fitxer;

    ProcessarFitxer(FitxerTreball fitxer) {
        this.fitxer = fitxer;
    }

    @Override
    public ResultatFitxer call() throws Exception {
        long inici = System.nanoTime();

        Thread.sleep(fitxer.tempsMs());

        boolean correcte = !fitxer.nom().contains("corrupt");
        long temps = (System.nanoTime() - inici) / 1_000_000;

        return new ResultatFitxer(
                fitxer.nom(),
                correcte,
                temps,
                Thread.currentThread().getName()
        );
    }
}

Cada tasca pot executar-se de manera independent i retorna el seu propi resultat.

Estat compartit

Ara volem acumular estadístiques globals:

JAVA 
class EstadistiquesFitxers {
    private int total;
    private int correctes;
    private int errors;
    private long tempsAcumulatMs;

    public synchronized void registrar(ResultatFitxer resultat) {
        if (resultat == null) {
            throw new IllegalArgumentException("El resultat no pot ser null");
        }

        total++;

        if (resultat.correcte()) {
            correctes++;
        } else {
            errors++;
        }

        tempsAcumulatMs += resultat.tempsMs();
    }

    public synchronized String resum() {
        return "total=" + total
                + ", correctes=" + correctes
                + ", errors=" + errors
                + ", tempsAcumulatMs=" + tempsAcumulatMs;
    }
}

La sincronització és necessària perquè moltes tasques poden cridar registrar() sobre el mateix objecte.

Crear el pool i enviar tasques

JAVA 
ExecutorService executor = Executors.newFixedThreadPool(4);
List<Future<ResultatFitxer>> futurs = new ArrayList<>();

for (FitxerTreball fitxer : fitxers) {
    futurs.add(executor.submit(new ProcessarFitxer(fitxer)));
}

Recollir resultats

JAVA 
EstadistiquesFitxers estadistiques = new EstadistiquesFitxers();

for (Future<ResultatFitxer> futur : futurs) {
    try {
        ResultatFitxer resultat = futur.get(3, TimeUnit.SECONDS);
        estadistiques.registrar(resultat);

        System.out.printf(
                "%s -> %s (%s)%n",
                resultat.nom(),
                resultat.correcte() ? "OK" : "ERROR",
                resultat.fil()
        );

    } catch (TimeoutException e) {
        futur.cancel(true);
        System.out.println("TIMEOUT");

    } catch (ExecutionException e) {
        System.out.println("ERROR TASCA: " + e.getCause());

    } catch (InterruptedException e) {
        Thread.currentThread().interrupt();
        break;
    }
}

Quan no queden tasques pendents, podem construir el resum final.

Temps real i temps acumulat

Suposem quatre tasques de dos segons.

En seqüencial:

TEXT 
temps acumulat = 2 + 2 + 2 + 2 = 8 s
temps real aproximat = 8 s

Amb quatre tasques executant-se alhora:

TEXT 
temps acumulat = 2 + 2 + 2 + 2 = 8 s
temps real aproximat = 2 s

El temps acumulat suma el temps dedicat a totes les tasques. El temps real mesura quant ha trigat el programa vist des de fora.

Aquesta diferència és molt útil per comprovar si hi ha hagut concurrència real en el nostre disseny.

Comprovar que l'estat compartit és coherent

Una prova petita pot no mostrar cap error. Per això és útil una prova d'estrès.

JAVA 
int total = 100_000;
Comptador marcador = new Comptador();
ExecutorService executor = Executors.newFixedThreadPool(10);

for (int i = 0; i < total; i++) {
    executor.submit(marcador::incrementar);
}

executor.shutdown();
executor.awaitTermination(30, TimeUnit.SECONDS);

System.out.println("ESPERAT=" + total);
System.out.println("OBTINGUT=" + marcador.getValor());

Sense sincronització podem perdre actualitzacions. Amb una protecció correcta, el resultat final ha de respectar els invariants.

En un marcador amb totals, per exemple:

TEXT 
totalProcessats = totalCorrectes + totalErrors

També és important construir l'informe final quan totes les tasques que poden modificar el marcador ja han acabat. Un marcador ben sincronitzat no evita que llegim un resultat massa aviat.

5. Preparació de l'EAC i síntesi final

La fase amb fils segueix aquest esquema:

TEXT 
CarregadorLliuraments
    |
    v
List<Lliurament>
    |
    v
CorrectorExecutor
    |
    | envia una TascaCorreccio per lliurament
    v
ExecutorService
    |
    +-- fil 1 -> TascaCorreccio -> ResultatCorreccio
    +-- fil 2 -> TascaCorreccio -> ResultatCorreccio
    +-- fil 3 -> TascaCorreccio -> ResultatCorreccio
    |
    v
MarcadorCorreccions compartit
    |
    v
informe final coherent

Per arribar-hi, cal dominar aquestes peces:

Part de l'EACConeixement necessari
CorrectorLliuramentPath, Files, validació, excepcions, separació de responsabilitats
CorrectorProcessosProcessBuilder, procés pare i fill, arguments, redirecció, codis de retorn, timeout, llançament abans de recollida
CorrectorExecutorExecutorService, pool fix, Callable, Future, timeout, cancel·lació, tancament

Una seqüència de pràctiques que prepara l'EAC

Dos fils i un ordre imprevisible

Creeu dos fils. Un imprimeix A1, A2, A3 i l'altre B1, B2, B3. Executeu el programa diverses vegades.

La sortida no ha de tenir sempre el mateix ordre.

Esperar amb join()

Afegiu un FINAL que només aparegui quan hagin acabat els dos fils.

Provocar una condició de cursa

Creeu quatre fils que incrementin 100.000 vegades el mateix comptador. Proveu-lo sense synchronized i després amb synchronized.

Pool de tres fils

Creeu deu tasques i executeu-les amb:

JAVA 
Executors.newFixedThreadPool(3)

Cada tasca ha d'imprimir el nom del fil. Hauríeu de veure que el pool reutilitza els mateixos treballadors.

Timeout d'una tasca

Creeu una tasca que trigui deu segons i proveu:

JAVA 
futur.get(1, TimeUnit.SECONDS)

Quan es produeixi el timeout, cancel·leu la tasca.

Procés fill

Creeu una classe que rebi arguments i finalitzi amb tres codis diferents:

TEXT 
0: operació correcta
2: dades no vàlides
10: arguments incorrectes

Executeu-la des d'un altre programa amb ProcessBuilder. Després llanceu cinc processos abans d'esperar-ne cap.
