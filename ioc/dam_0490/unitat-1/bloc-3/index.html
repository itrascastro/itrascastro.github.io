1. Crear, esperar i entendre els fils

La manera més simple d'entendre un fil és començar amb una tasca molt petita.

JAVA 
public class PrimerFil {
    public static void main(String[] args) throws InterruptedException {
        Runnable tasca = () -> {
            System.out.println(
                    "Hola des de " + Thread.currentThread().getName()
            );
        };

        Thread fil = new Thread(tasca, "fil-treballador");
        fil.start();

        fil.join();
        System.out.println("Programa acabat");
    }
}

start() crea un nou flux d'execució. Cridar directament run() no ho fa.

JAVA 
fil.start(); // nou fil
fil.run();   // crida normal de mètode

També es pot heretar de Thread:

JAVA 
class FilSalutacio extends Thread {
    @Override
    public void run() {
        System.out.println("Hola des de " + getName());
    }
}

Per separar millor la tasca del mecanisme que l'executa, normalment és més flexible treballar amb Runnable o, més endavant, amb Callable.

Esperar un fil amb join()

JAVA 
Thread f1 = new Thread(() -> feina("A"));
Thread f2 = new Thread(() -> feina("B"));

f1.start();
f2.start();

f1.join();
f2.join();

System.out.println("Totes les tasques han acabat");

join() fa que el fil actual esperi que un altre fil finalitzi.

Estats i context d'execució d'un fil

Java defineix aquests estats a Thread.State:

TEXT 
NEW
RUNNABLE
BLOCKED
WAITING
TIMED_WAITING
TERMINATED

Una lectura pràctica és aquesta:

  • NEW: l'objecte Thread existeix però encara no s'ha iniciat.
  • RUNNABLE: està preparat o executant-se.
  • BLOCKED: espera entrar en una secció protegida per un monitor.
  • WAITING: espera sense límit de temps.
  • TIMED_WAITING: espera amb un límit de temps, per exemple amb sleep().
  • TERMINATED: el mètode run() ja ha acabat.
JAVA 
Thread fil = new Thread(() -> {
    try {
        Thread.sleep(1000);
    } catch (InterruptedException e) {
        Thread.currentThread().interrupt();
    }
});

System.out.println(fil.getState());
fil.start();
fil.join();
System.out.println(fil.getState());

L'estat pot canviar entre dues instruccions. getState() serveix per observar i depurar, no per construir una coordinació fiable basada en sondejar contínuament el fil.

Cada fil també té el seu propi context: pila de crides, variables locals, punt d'execució, nom, prioritat i estat.

JAVA 
Thread actual = Thread.currentThread();
System.out.println("Nom: " + actual.getName());
System.out.println("Prioritat: " + actual.getPriority());
System.out.println("Estat: " + actual.getState());

2. Prioritat, fils dimoni i grups

La prioritat d'un fil va d'1 a 10:

JAVA 
Thread.MIN_PRIORITY
Thread.NORM_PRIORITY
Thread.MAX_PRIORITY

Podem canviar-la:

JAVA 
fil.setPriority(Thread.MAX_PRIORITY);

La prioritat és una indicació al planificador. No garanteix l'ordre d'execució. Un programa no ha de dependre de la idea que un fil amb prioritat 10 s'executarà abans que un fil amb prioritat 5.

Un fil dimoni és un fil de suport que no impedeix que la JVM finalitzi quan ja no queden fils d'usuari.

JAVA 
Thread fil = new Thread(() -> feinaEnSegonPla());
fil.setDaemon(true);
fil.start();

No s'ha d'utilitzar per a una feina que s'hagi de completar obligatòriament.

Java també té ThreadGroup. Forma part del model clàssic de fils, però avui és més habitual agrupar i gestionar tasques amb executors.

3. Compartir dades i sincronitzar

Mirem aquest comptador:

JAVA 
class Comptador {
    int valor = 0;

    void incrementar() {
        valor++;
    }
}

valor++ sembla una sola acció, però conceptualment implica diverses operacions:

TEXT 
llegir valor
sumar 1
escriure valor

Dos fils poden intercalar-se així:

TEXT 
valor inicial = 10

Fil A llegeix 10
Fil B llegeix 10
Fil A calcula 11
Fil B calcula 11
Fil A escriu 11
Fil B escriu 11

Esperàvem 12 i obtenim 11. S'ha perdut una actualització.

Això és una condició de cursa: el resultat depèn de l'ordre imprevisible en què diversos fils accedeixen a un estat compartit.

Figura

Com provocar l'error

JAVA 
public class ProvaCursa {

    static class Comptador {
        int valor;

        void incrementar() {
            valor++;
        }
    }

    public static void main(String[] args) throws InterruptedException {
        Comptador comptador = new Comptador();

        Runnable tasca = () -> {
            for (int i = 0; i < 100_000; i++) {
                comptador.incrementar();
            }
        };

        Thread f1 = new Thread(tasca);
        Thread f2 = new Thread(tasca);

        f1.start();
        f2.start();

        f1.join();
        f2.join();

        System.out.println("Esperat: 200000");
        System.out.println("Obtingut: " + comptador.valor);
    }
}

L'error no ha d'aparèixer sempre. Aquesta és una de les dificultats de la concurrència: una execució correcta no demostra que el programa estigui ben sincronitzat.

Protegir una secció crítica amb synchronized

Una secció crítica és una part del codi que accedeix a estat compartit i que ha d'estar coordinada amb altres accessos.

Podem sincronitzar tot un mètode:

JAVA 
class Comptador {
    private int valor;

    public synchronized void incrementar() {
        valor++;
    }

    public synchronized int getValor() {
        return valor;
    }
}

O només un bloc:

JAVA 
synchronized (bloqueig) {
    // secció crítica
}

La idea clau és que totes les operacions que s'han de coordinar utilitzin el mateix monitor o bloqueig.

Protegir diversos camps junts

JAVA 
class Estadistiques {
    private int total;
    private int correctes;
    private int errors;

    public synchronized void registrar(boolean correcte) {
        total++;

        if (correcte) {
            correctes++;
        } else {
            errors++;
        }
    }
}

Aquí hi ha una relació que volem conservar:

TEXT 
total = correctes + errors

Aquesta relació és un invariant. Si el programa està ben sincronitzat, l'invariant s'ha de complir quan construïm el resultat final.

synchronized en mètodes estàtics

Un mètode d'instància synchronized bloqueja l'objecte actual. Un mètode estàtic synchronized bloqueja l'objecte Class.

JAVA 
public static synchronized void registrarGlobal() {
    // bloqueig associat a LaClasse.class
}

No és el mateix bloqueig que el d'una instància concreta.

4. Visibilitat i interbloqueig

volatile serveix per fer visible entre fils el valor actual d'una variable.

JAVA 
class Control {
    volatile boolean actiu = true;
}

És útil per a un senyal simple com aquest. Però no converteix una operació composta en una operació indivisible.

JAVA 
volatile int contador = 0;
contador++;

L'increment continua tenint lectura, càlcul i escriptura. Dos fils encara poden perdre actualitzacions.

Per a un únic comptador podem utilitzar synchronized o classes com AtomicInteger. Si hem de modificar diversos camps mantenint una relació entre ells, protegir tota l'operació amb el mateix bloqueig acostuma a ser més clar.

Interbloqueig

Un interbloqueig o deadlock apareix quan diversos fils s'esperen mútuament i cap pot continuar.

TEXT 
Fil A té X i espera Y
Fil B té Y i espera X

Un exemple perillós és adquirir els mateixos bloquejos en ordres diferents.

JAVA 
synchronized (compteA) {
    synchronized (compteB) {
        // ...
    }
}

I en un altre lloc:

JAVA 
synchronized (compteB) {
    synchronized (compteA) {
        // ...
    }
}

Una mesura habitual és adquirir els bloquejos sempre en el mateix ordre. També ajuda reduir el nombre de bloquejos i mantenir petites les seccions crítiques.

5. Coordinació i depuració

De vegades un fil no ha de continuar fins que es compleixi una condició.

Un exemple és una bústia amb capacitat per a un sol missatge:

JAVA 
class Bustia {
    private String missatge;

    public synchronized void posar(String text) {
        while (missatge != null) {
            try {
                wait();
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
                return;
            }
        }

        missatge = text;
        notifyAll();
    }

    public synchronized String agafar() {
        while (missatge == null) {
            try {
                wait();
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
                return null;
            }
        }

        String resultat = missatge;
        missatge = null;
        notifyAll();
        return resultat;
    }
}

Cal entendre quatre idees:

  • wait() posa el fil en espera i allibera temporalment el monitor.
  • notify() desperta un dels fils que espera aquell monitor.
  • notifyAll() desperta tots els que hi esperen.
  • la condició s'ha de tornar a comprovar amb while quan el fil es desperta.

Aquest patró permet entendre el problema productor-consumidor. En aplicacions modernes també podem utilitzar estructures de nivell més alt, com BlockingQueue.

Semàfors i monitors

Un semàfor controla quantes tasques poden accedir a un recurs al mateix temps. El podem imaginar com un comptador de permisos.

JAVA 
Semaphore places = new Semaphore(3);

places.acquire();
try {
    utilitzarRecurs();
} finally {
    places.release();
}

Amb tres permisos, poden entrar com a màxim tres fils alhora.

Un monitor associa dades, exclusió mútua i operacions d'espera i notificació. En Java, synchronized, wait() i notifyAll() permeten construir aquest tipus de coordinació.

Per a l'EAC no cal implementar un semàfor propi. El que sí cal és entendre per què existeixen aquests mecanismes: evitar col·lisions i coordinar l'accés a recursos compartits.

Depurar un programa multifil

Un bon missatge de depuració ha d'indicar quina tasca s'està executant i quin fil la processa.

JAVA 
System.out.printf(
        "[%s] processant %s%n",
        Thread.currentThread().getName(),
        idTasca
);

Amb un JDK podem obtenir un thread dump:

BASH 
jstack <PID>

Això permet veure els fils, els seus estats i la seva pila de crides. És especialment útil quan sospitem que hi ha fils bloquejats o un interbloqueig.

Per provar sincronització, no n'hi ha prou amb una execució petita. Convé repetir proves, augmentar el nombre d'operacions i comprovar invariants.
