1. Crear, iniciar i esperar fils

Un procés Java comença amb un fil: main. A partir d'aquest fil podem crear-ne d'altres perquè diverses tasques estiguin en progrés dins de la mateixa JVM.

Informació

Recordeu la diferència

Un fil nou no crea una JVM nova. Continua dins del mateix procés i comparteix els objectes del heap amb la resta de fils del procés.

La forma més simple: Runnable + Thread

JAVA PrimerFil.java 
public class PrimerFil {
    public static void main(String[] args) throws InterruptedException {

        Runnable feina = () -> {
            String nom = Thread.currentThread().getName();
            System.out.println("Treballant des de " + nom);
        };

        Thread fil = new Thread(feina, "treballador-1");

        fil.start();

        System.out.println("El main continua");
        fil.join();

        System.out.println("Tots dos han acabat");
    }
}

Runnable descriu una tasca que no retorna un valor. Thread representa el fil que l'executarà. start() demana a la JVM que iniciï el nou fil.

Problema

Error típic: cridar fil.run() pensant que és equivalent a fil.start().

Solució

run() és només un mètode normal. Si el crideu directament, s'executa en el fil actual. start() crea el nou camí d'execució i la JVM acaba invocant run() des d'aquest fil.

Per què serveix join()?

join() permet que un fil esperi la finalització d'un altre. No decideix en quin ordre s'executaran les instruccions anteriors. Només garanteix que, quan join() retorna, el fil esperat ja ha finalitzat.

JAVA 
Thread a = new Thread(() -> System.out.println("A"));
Thread b = new Thread(() -> System.out.println("B"));

a.start();
b.start();

a.join();
b.join();

System.out.println("FINAL");

A i B poden aparèixer en qualsevol ordre. FINAL, en canvi, apareixerà després de tots dos.

Exercici: Ordre no determinista
Creeu dos fils. Un imprimeix A1, A2, A3 i l'altre B1, B2, B3. Executeu el programa diverses vegades. Afegiu després un FINAL que només aparegui quan els dos fils hagin acabat.
Bàsic 10 min
Veure pistes
  • Useu start per iniciar els dos fils abans d'esperar.
  • Useu join només després d'haver iniciat tots dos.
  • No intenteu forçar un ordre entre A i B.

2. Estats, context, prioritat i fils dimoni

Un fil canvia d'estat durant la seva vida. Java ho representa amb Thread.State.

Figura
EstatIdea principalExemple
NEWCreat però encara no iniciatAbans de start()
RUNNABLEPot executar-se o s'està executantTreball normal
BLOCKEDEspera entrar en una zona sincronitzada ocupadaUn altre fil té el monitor
WAITINGEspera sense temps màximwait(), join()
TIMED_WAITINGEspera amb límit temporalsleep(), join(timeout)
TERMINATEDHa acabatEl mètode run() ha finalitzat
JAVA 
Thread fil = new Thread(() -> {
    try {
        Thread.sleep(500);
    } catch (InterruptedException e) {
        Thread.currentThread().interrupt();
    }
});

System.out.println(fil.getState()); // NEW
fil.start();

Thread.sleep(50);
System.out.println(fil.getState()); // sovint TIMED_WAITING

fil.join();
System.out.println(fil.getState()); // TERMINATED

Context d'execució

Cada fil té el seu propi context: pila de crides, variables locals de les seves crides, comptador d'instruccions i informació d'estat. En canvi, els objectes que hi ha al heap poden ser compartits.

JAVA 
Thread actual = Thread.currentThread();

System.out.println(actual.getName());
System.out.println(actual.getId());
System.out.println(actual.getState());
System.out.println(actual.getPriority());

Prioritat

La prioritat d'un fil és una pista per al planificador, no una ordre exacta. Java permet valors entre Thread.MIN_PRIORITY i Thread.MAX_PRIORITY, però el comportament concret depèn de la JVM i del sistema operatiu.

Important

No utilitzeu la prioritat per garantir l'ordre d'un programa. Si necessiteu que una operació passi abans que una altra, feu servir mecanismes de sincronització.

Fils dimoni

Un fil dimoni dona suport a altres tasques, però no manté la JVM viva per si sol. Quan només queden fils dimoni, la JVM pot finalitzar.

JAVA 
Thread monitor = new Thread(() -> {
    while (true) {
        // tasca auxiliar
    }
});

monitor.setDaemon(true);
monitor.start();
Suggeriment

Per ampliar: ThreadGroup permet agrupar fils, consultar-los i aplicar algunes operacions conjuntes. És una API antiga i avui és més habitual estructurar la concurrència amb executors, però ajuda a entendre que els fils tenen context i organització pròpia dins de la JVM.

3. Recursos compartits i condicions de cursa

La memòria compartida és útil perquè els fils poden treballar sobre els mateixos objectes. El problema apareix quan més d'un fil modifica el mateix estat.

JAVA 
class Comptador {
    private int valor = 0;

    public void incrementar() {
        valor++;
    }

    public int getValor() {
        return valor;
    }
}

A primera vista sembla impossible que valor++ falli. Però aquesta expressió implica diversos passos conceptuals:

TEXT 
1. llegir valor
2. calcular valor + 1
3. escriure el resultat

Dos fils poden intercalar aquests passos:

Figura
JAVA 
Comptador comptador = new Comptador();

int fils = 4;
int incrementsPerFil = 100_000;

List<Thread> llista = new ArrayList<>();

for (int i = 0; i < fils; i++) {
    Thread fil = new Thread(() -> {
        for (int j = 0; j < incrementsPerFil; j++) {
            comptador.incrementar();
        }
    });

    llista.add(fil);
    fil.start();
}

for (Thread fil : llista) {
    fil.join();
}

System.out.println("ESPERAT=" + (fils * incrementsPerFil));
System.out.println("OBTINGUT=" + comptador.getValor());

És possible que el resultat sigui inferior a l'esperat. Potser una execució concreta surt bé, però això no demostra que el codi sigui segur.

Definició

Condició de cursa: Error en què el resultat depèn de l'ordre temporal amb què diversos fils accedeixen a dades compartides.

Important

Els errors de concurrència poden ser intermitents. Un programa que funciona cent vegades pot fallar a la cent una. Per això cal raonar sobre l'accés compartit i fer proves d'estrès.

Exercici: Provoca l'error
Executeu la prova del comptador diverses vegades. Augmenteu el nombre de fils o d'increments fins que observeu una pèrdua d'actualitzacions.
Mitjà 15 min
Veure pistes
  • No afegiu encara synchronized.
  • Executeu la prova repetidament.
  • Compareu sempre ESPERAT i OBTINGUT.

4. synchronized, volatile i atomicitat

Protegir una secció crítica

Una secció crítica és una part del codi que accedeix a un recurs compartit i que no volem que sigui executada simultàniament per diversos fils.

Definició

Exclusió mútua: Propietat que garanteix que només un fil pot executar una determinada secció crítica en cada moment.

JAVA 
class Comptador {
    private int valor = 0;

    public synchronized void incrementar() {
        valor++;
    }

    public synchronized int getValor() {
        return valor;
    }
}

Quan un fil entra en un mètode synchronized d'un objecte, adquireix el monitor d'aquell objecte. Un altre fil que vulgui entrar en una zona sincronitzada protegida pel mateix monitor haurà d'esperar.

Informació

La pregunta correcta no és "hi ha synchronized?"

La pregunta correcta és: totes les operacions que han de veure un estat coherent estan protegides pel mateix mecanisme? Sincronitzar només una part d'una operació composta pot continuar deixant inconsistències.

Bloc synchronized

No sempre cal sincronitzar tot el mètode:

JAVA 
public void processar() {
    ferCalculIndependent();

    synchronized (this) {
        totalProcessats++;
        tempsAcumulat += 10;
    }
}

La zona protegida convé que sigui tan petita com sigui possible, però prou gran per mantenir els invariants de l'objecte.

Mètodes estàtics sincronitzats

JAVA 
public static synchronized void incrementarGlobal() {
    totalGlobal++;
}

En un mètode estàtic, el monitor és l'objecte Class de la classe, no una instància concreta.

Què resol volatile?

volatile ajuda amb la visibilitat: una escriptura feta per un fil és visible per als altres fils que llegeixen aquella variable.

JAVA 
class Control {
    private volatile boolean aturar = false;

    public void demanarAturada() {
        aturar = true;
    }

    public void treballar() {
        while (!aturar) {
            // feina
        }
    }
}

Aquí volatile és adequat perquè només ens interessa publicar un valor simple.

Important

volatile no converteix una operació composta en atòmica. Posar volatile a un enter no fa segur contador++, perquè l'increment continua implicant llegir, calcular i escriure.

Atomicitat

Una operació és atòmica quan els altres fils no poden observar-la a mig fer. Per a comptadors simples, Java també ofereix classes com AtomicInteger:

JAVA 
AtomicInteger comptador = new AtomicInteger();

comptador.incrementAndGet();

Les classes atòmiques són molt útils per a operacions simples. Quan l'estat coherent depèn de diverses variables que s'han d'actualitzar juntes, un bloc synchronized acostuma a expressar millor la secció crítica.

Exercici: Repara el comptador
Afegiu sincronització al comptador de la secció anterior. Repetiu la prova d'estrès i comproveu que el resultat final compleix sempre l'invariant.
Mitjà 15 min
Veure pistes
  • Protegiu tant la modificació com les lectures que necessitin coherència.
  • Feu moltes iteracions.
  • No reduïu la prova fins que sigui massa fàcil.

5. Coordinació: deadlock, wait/notify i semàfors

Deadlock

Sincronitzar evita unes errades, però pot crear-ne d'altres si diversos fils adquireixen bloquejos en ordres incompatibles.

Figura
JAVA 
synchronized (recursA) {
    synchronized (recursB) {
        // feina
    }
}

Si un altre lloc del programa adquireix primer recursB i després recursA, els dos fils es poden quedar esperant indefinidament.

Èxit

Una prevenció molt efectiva: establiu un ordre global per adquirir els bloquejos i respecteu-lo a tot el programa.

wait(), notify() i notifyAll()

Hi ha situacions en què un fil no ha d'avançar fins que una condició sigui certa. En lloc de consultar-la constantment, pot esperar sobre el monitor d'un objecte.

JAVA Bustia.java 
class Bustia {
    private String missatge;

    public synchronized void posar(String nou) {
        while (missatge != null) {
            try {
                wait();
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
                return;
            }
        }

        missatge = nou;
        notifyAll();
    }

    public synchronized String agafar() {
        while (missatge == null) {
            try {
                wait();
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
                return null;
            }
        }

        String resultat = missatge;
        missatge = null;
        notifyAll();
        return resultat;
    }
}

wait() allibera temporalment el monitor i posa el fil en espera. notifyAll() desperta els fils que esperen aquell mateix monitor perquè tornin a comprovar la condició.

Important

Comproveu la condició amb while, no amb if. Quan un fil es desperta, la condició pot haver deixat de ser certa abans que recuperi el monitor.

Productor-consumidor

El patró productor-consumidor apareix quan unes tasques generen dades i unes altres les processen. El repte és coordinar els dos ritmes: el consumidor no ha d'intentar agafar dades inexistents i el productor no ha d'escriure sobre un espai ple.

Informació

Idea moderna

Amb Java actual, una BlockingQueue resol molts casos de productor-consumidor sense haver de programar manualment wait() i notifyAll(). Entendre el mecanisme manual ajuda a entendre què està fent la cua per vosaltres.

Semàfors

Un semàfor limita quants fils poden accedir simultàniament a un recurs. Java ofereix Semaphore dins de java.util.concurrent.

JAVA 
Semaphore places = new Semaphore(3);

places.acquire();
try {
    utilitzarRecursLimitat();
} finally {
    places.release();
}

Un semàfor amb tres permisos deixa entrar fins a tres fils al mateix temps. És útil quan el recurs admet una concurrència limitada, per exemple un conjunt petit de connexions.

Suggeriment

Altres problemes i eines que convé reconèixer

El problema de lectors i escriptors estudia com permetre moltes lectures simultànies però protegir les escriptures. La inanició apareix quan un fil podria esperar indefinidament perquè altres obtenen sempre el recurs abans que ell. synchronized, wait() i notifyAll() es basen en monitors, i Java també ofereix eines de més alt nivell com Lock, Condition, BlockingQueue i col·leccions concurrents.
